## 1. 一句话结论

> 用五版实现把"超卖"这件事从「必然发生」做到「并发 300、零超卖、P95 66 ms」，
> 并且每一版都用数据库自己记的账（`Com_update` 增量）、库存守恒、成功单数三重证据交叉验证；

## 2. 五版演进总表

| 版本 | 核心手段 | 成功单 | 超卖 | P95 | 相对上一版 | 结论 |
|---|---|---|---|---|---|---|
| **v0** baseline | 无任何保护，读-改-写 | 300 | **+200（200%）** | 572 ms | — | 必然超卖，作为对照基准 |
| **v1** 数据库锁 | `UPDATE ... WHERE stock > 0` 看 affected rows | 100 | 0 | 339 ms | 快 41% | 正确，但排队在 DB 行锁 |
| **v2** Redis + Lua | 库存门禁前置，挡住无效请求 | 100 | 0 | 322 ms | 快 5% | 挡掉 200 个无效请求，但成功请求仍排队 |
| **v3** MQ 异步 | 把排队挪出 HTTP 请求路径 | 100 | 0 | **66 ms** | **快 4.9 倍** | 请求路径不再等 DB 行锁 |
| v4 调优 | 容量探测 + JVM 观测 | — | — | — | 跳过 | 探测出真实上限 1600 RPS（CPU 仅 20%） |
| v5 分表 | ShardingSphere 4 分片 | 100 | 0 | 87.91 ms @1200rps | **慢 4.4 倍** | 纯亏，已回退 |

> 所有数字的口径：课程 88、capacity=100、300 并发（k6 `per-vu-iterations`）、MySQL REPEATABLE-READ。
> 极少数轮次（如 v1 首轮的 94 个 rejected）是冷启动噪声，报告里逐条标注了。

## 3. 每一版到底解决了什么

### 3.1 v0 → v1：从"必然超卖"到"零超卖"

**v0 的罪证**（`docs/压测报告.md`）：

| 并发 | 名额 | 卖出 | 超卖 | stock 实际值 |
|---|---|---|---|---|
| 1（串行） | 100 | 100 | **0** | 0 |
| 110 | 100 | 110 | +10 | 98 |
| 300 | 100 | **300** | **+200** | 96 |

看清楚这三行：

- **串行 1 个请求时完全正确**（100 单、缺口 0）→ 排除"代码逻辑写错"、"种子数据有问题"、"压测工具造假"。
- 剩下的唯一变量就是**并发**。
- **300 单卖出，但 `stock` 只从 100 掉到 96** —— 这是**丢失更新**的直接指纹：
  多个线程都读到 `stock=100`，都算出 99，都写回 99，100 次覆盖成 1 次。

**一个反直觉的点**：`CHECK (stock >= 0)` 完全没防住超卖。因为 `stock` 根本没掉到负数（还在 96）。
这个约束只保证"库存不为负"，不保证"订单数 ≤ 名额"。**两个是不同的事。**

**v1 的关键认知**：`UPDATE ... WHERE stock > 0` 的**返回值（affected rows）是数据库对并发做出的裁决**，
是唯一可信的答案。`getStock()` 读到的只是"某一时刻的快照"，用它做判断就是 v0。

```
❌ v0：读 stock → 判 >0 → 算 newStock → 写回        （三步之间别人能插进来）
✅ v1：UPDATE ... SET stock=stock-1 WHERE stock>0    （五步原子：加锁/读/判/写/释放）
       → affected==1 表示抢到，==0 表示没抢到
```

### 3.2 v1 → v2：把无效请求拦在数据库外面

v1 已经正确了，为什么还要 v2？

**v1 的问题不是超卖，是浪费**：300 个请求抢 100 个名额，**200 个注定失败的请求也要各占一次
Hikari 连接 + 一次行锁排队**。数据库在做无用功。

**v2 的做法**：库存预热进 Redis，用 Lua 脚本原子扣减。返回 -1（未预热）/ -2（不足）/ ≥0（剩余）。

**怎么证明它真的生效了？** 这里用了本报告最硬的一个证据 —— **数据库自己记的账**：

```sql
SHOW GLOBAL STATUS LIKE 'Com_update';   -- 压测前后各读一次
```

| 版本 | Com_update 增量 | 成功单 | 比例 |
|---|---|---|---|
| v1-optimistic | 300 | 100 | **3.0** |
| v2-redis-lua | **100** | 100 | **1.0** |

**300 → 100，精确 3:1** = 200 个请求在 Redis 就被挡回，一次数据库都没碰。
这个数字不是我们统计的，是 MySQL 自己数的，改不了。

**为什么不能只看 P95 变快**：P95 从 339 → 322 ms 只快了 5%，看起来像"没效果"。
但 `Com_update` 说了实话 —— 机制生效了，只是**瓶颈转移**了。

**瓶颈转到哪了**：剩下 100 个成功请求仍然串行在**同一行** MySQL 行锁上
（`UPDATE course_stock WHERE course_id=88`），100 次 × 约 2 ms ≈ 200 ms 就是新的下限。
这正是 v3 的靶子。

### 3.3 v2 → v3：把排队挪出请求路径

**v3 做的事**：HTTP 请求只做三件快事（Redis 门禁 → INSERT 待处理订单 → 发消息确认），
真正的扣库存交给消费者线程异步做。

**效果**：P95 322 → **66 ms**，快 4.9 倍。

**代价（必须说清楚）**：**HTTP 200 ≠ 已选上**。

| 版本 | 抢课返回 200 时 | 客户端要做什么 |
|---|---|---|
| v0 / v1 / v2 | 订单已经是 `status=1`，真的选上了 | 直接信 |
| **v3** | 订单是 `status=0` 待处理，**还在队列里** | 轮询 `GET /api/course/{id}` 等 `myOrderStatus` 变 1 |

这是一个**接口语义的破坏性变更**，不是"顺手优化"。前端必须配合改，否则用户会以为选上了。

**最终一致延迟实测**（300 并发）：

```
t=23.5s  total=100  success=99   pending=1
t=24.0s  total=100  success=100  pending=0
```

按 `TIMESTAMPDIFF(SECOND, create_time, update_time)` 统计：**lag=0 秒 23 单 / lag=1 秒 77 单**。
100 条订单的 `create_time` 全在同一秒。结论：**最终一致延迟 ≤ 1 秒**。

**v3 引入的三个新问题**（这是 v3 真正的技术含量，`docs/压测报告-v3.md` §7）：

1. **消息会丢** —— 三个位置：生产者→broker（用 publisher confirm）、broker 自己（durable + persistent）、
   broker→消费者（手动 ack）。**ack 必须在事务提交之后**，否则"消息确认了但订单没落"，
   而且日志里一条 ERROR 都没有。
2. **消息会重复** —— AMQP 是 at-least-once。用 `INSERT mq_consume_log` 撞 `uk_msg_id` 做幂等闸，
   **必须和业务同事务**（否则幂等记录提交了、业务回滚了，重投时被误判成重复）。
3. **消息会失败** —— 要分级：业务失败（库存不足）标 `status=2` 并**正常 ack**；
   技术异常 `basicNack(tag, false, false)` 进死信。**requeue 写 true 会让毒消息无限重投**，
   表现成队列深度永远降不下去、CPU 打满，但一条 ERROR 都没有。

## 4. v4：为什么"调优"跳过了

调优前先做了一件事：**测出真实上限**，否则不知道要调什么。

**容量扫描**（逐步加压，每轮复位，学生 2400，课程容量放大到 100000）：

| 目标 RPS | P95 | 失败率 | 丢弃 |
|---|---|---|---|
| 800 | 17.84 ms | 0% | 0 |
| 1200 | 20.16 ms | 0% | 0 |
| **1600** | **120.8 ms** | **0%** | **0** |
| 2000+ | 1.7~1.8 s | 0% | 大量 | ← 是 VU 池不够，不是系统上限 |

**同时跑的 JVM 观测**（`jvm-probe.ps1`，JDK 自带 jcmd/jstat 零安装）：

- 堆：min 86.5 / max 247.3 / avg 168 MB
- **FullGC 0 次**
- **CPU 平均 3.1% / 峰值 15.1%**

**结论：1600 RPS 时 CPU 只用了 15%、一次 FullGC 都没有。**
说明瓶颈不在 JVM 侧，而在"排队"本身 —— 而排队已经在 v3 用 MQ 挪走了。
所以 v4 剩下的调优空间很小（把 66 ms 再压到 40 ms 这种量级），
**性价比不如把已有成果收尾干净**。这是主动跳过，不是放弃。

> 顺带记两个把测量搞砸过的坑（`docs/压测报告-v3.md` §8 与本文 §7）：
> ①`maxVUs` 设 4000 但学生池只有 900 → 多个 VU 抢同一学生 → 撞唯一索引 → 12.62% 假失败。
> 压到 900 后同一 1600 RPS 变成 0% 失败、P95 从 711 ms 降到 110 ms。
> **"拐点"一度被误报成 1200，实际是脚本自己造的。**

## 5. v5 分表：一次有价值的失败

**背景**：任务书 §0 一开始就写了判断 —— 「分表解决的是**数据量大**，本项目的核心矛盾是**并发高**，
两个不是同一个问题」。但判断要用数据支撑，所以还是做了。

**做了什么**：ShardingSphere-JDBC 5.5.3，`seckill_order` 按 `student_id % 4` 分 4 片；
Mapper 的两条热 UPDATE 全部加 `student_id` 分片键（避免广播）；主键改雪花（避免跨片冲突）。

**结果**：

| 版本 | 目标 RPS | P95 | 失败率 | 丢弃 |
|---|---|---|---|---|
| v3（不分表） | 1200 | **20.16 ms** | 0% | 0 |
| v5（已分表） | 1200 | **87.91 ms** | 0% | 0 |
| v3（不分表） | 1600 | **120.8 ms** | 0% | 0 |
| v5（已分表） | 1600 | **2.78 s** | 0% | **5412** |

**1200 RPS 慢 4.4 倍，1600 RPS 直接崩。**

**逐项排除**（这部分才是价值所在 —— 排除比发现更难）：

| 怀疑对象 | 怎么排除的 | 结果 |
|---|---|---|
| 连接池太小 | `maximumPoolSize` 20 → 50 重测 | **更差**（P95 1.81s → 2.78s） |
| JVM / GC | `jvm-probe.ps1` 全程采样 | CPU 峰值 20.8%、**FullGC 0 次** |
| MySQL 连接不够 | 压测中查 `Threads_connected` | 只有 12（上限 151） |
| 数据库锁/死锁 | 日志关键字统计 | `Deadlock`/`Timeout`/`Connection is not available` 全 0 |
| 分片键改造无效（广播） | `Com_update` 增量 / 成功单 | **4.17 次/单**（广播会接近 7）→ 改造有效 |
| 单请求本身慢 | 串行 10 次 | 平均 38.4 ms（含 curl 启动约 10ms）→ 单发正常 |

**剩下的唯一解释**：ShardingSphere 的 SQL 解析 → 改写 → 路由 → 结果归并这一层，
**每个请求多了一层固定开销，且随并发线性放大**。单发时看不出来（28 ms 和 20 ms 差不多），
并发时就变成排队。

**三个"分表后会坏掉但没人告诉你"的事实**（实测，`docs/阶段6-任务书-v5-sharding.md` §3）：

1. **`uk_order_no` 跨分片完全失效** —— 同一个 `order_no` 成功同时存在于 `seckill_order_0` 和
   `seckill_order_3`。全局唯一键在分片后必须自己保证。
2. **`uk_student_course` 侥幸还有效** —— 因为分片键就是 `student_id`，同学生必落同一片。
   这是"运气好"，改分片键就没了。
3. **没在 yaml 里登记的表直接报 `Table or view 'xxx' does not exist`** ——
   不是权限问题，是 ShardingSphere 元数据里没它。「只分一张表、其它照旧」这条最直觉的路走不通，
   必须给每张普通表加一条 `!SINGLE` 规则。

**处置**：`git stash`（stash@{0}，19 个文件）+ 删除 4 张分表 + 复位数据。代码与数据库均已回到 v3 状态。

**这次失败的价值**：面试时被问"为什么不分库分表"，可以拿出 `1200 RPS: 20ms vs 88ms` 这组实测数据，
而不是背"分表会增加复杂度"这种空话。

### 5.1 补测：2000 万行时结论会变吗？（2026-11-26）

v5 的结论只在 1 万行量级成立，当时明确写了"2000 万行必须重测"。补测完成，报告见
`docs/A8-分表2000万行实测报告.md`。**结论没变，但理由完全变了，而且更有说服力。**

造数：20 万学生 × 100 课程 = **2000 万行**，表空间 4096 MB，耗时 **71 分钟**（单批从 11.6s 涨到 54.9s）。

三个关键实测：

**① 慢查询的根因不是"表有 2000 万行"。**

| 查询 | 中位数 | EXPLAIN 预估扫描行数 |
|---|---|---|
| `WHERE id = ?` | **0.062 ms** | 1（主键） |
| `WHERE student_id = ? AND status = 1` | **1.42 ms** | **100**（`uk_student_course`） |
| `WHERE order_no = ?` | **0.087 ms** | 0 |
| `WHERE course_id = 50 AND status = 1 LIMIT 20` | **0.25 ms** | 398,820（`idx_course_status`） |
| 同上 `LIMIT 100000, 20` | **270 ms** | 398,820 |
| `COUNT(*) WHERE course_id = 50 AND status = 1` | **79 ms** | 398,820 |

**慢的不是"表大"，是"这门课有 39.8 万人"。** 索引已把定位做到极致（`type: ref`），
慢在必须逐行处理 39.8 万条匹配记录。分表后每片仍有 10 万条要扫，**扫描总量不变**。

**② 加内存完全无效 —— 这排除了 I/O 假设。**

buffer pool 从 128 MB 提到 **2 GB（16 倍）**：

| 查询 | 128 MB | 2 GB |
|---|---|---|
| 深分页 | 270 ms | **272 ms** |
| COUNT | 79 ms | **96 ms** |

**一点没变快。** 证明瓶颈是 CPU 逐行处理，不是磁盘。所以"加内存救慢查询"这条路在这里是死的。

**③ 跨分片唯一索引失效，这次在 2000 万行规模上重新实测确认。**

```
order_no='DUP_TEST_001', student_id=150000 → 进 _0 片，成功
order_no='DUP_TEST_001', student_id=150001 → 进 _1 片，成功
→ 两片各 1 行，同一订单号共存（全局唯一性失效）

同片内重复插入 → ERROR 1062 Duplicate entry 'DUP_TEST_001' for key 'seckill_order_0.uk_order_no'
```

**这是正确性缺陷，不是性能问题。** 它不报错、不告警，只会在某天对账时发现账不平。

**意外收获：找到了真正该做的事。**

既然瓶颈是"扫描大量行"，那就别扫。同一张 2000 万行表上实测：

| 方案 | 耗时 |
|---|---|
| `LIMIT 100000, 20`（offset 分页） | **280 ms** |
| `WHERE id > ? ORDER BY id LIMIT 20`（游标分页） | **0.18 ~ 0.32 ms** |

**快 1000 倍。** 这比"上分库分表"便宜得多，效果却好得多。

> 这次补测让我明白一件事：**先搞清楚慢在哪，再决定加什么。**
> 我原本以为 2000 万行会改变结论，结果发现我从一开始就问错了问题 ——
> 问题不是"数据量多大该分表"，而是"这个查询为什么慢"。

## 6. 正确性验证：不只看"有没有报错"

超卖这个问题最坑的地方是：**系统可以账目守恒、无异常、无错误日志，但依然少卖一半。**
（v1-pessimistic 的重复扣减弱点就是这样：`stock+sold=100` 完美守恒，但只服务了 50 个人。）

所以验证必须**同时看多个维度**：

| 维度 | 判据 | 为什么必须要 |
|---|---|---|
| **超卖** | `success_orders ≤ capacity` | 核心目标 |
| **少卖** | `success_orders == capacity` | 守恒只能证明"没凭空多/少库存"，不能证明"名额用满" |
| **守恒** | `stock + sold == capacity` | 抓住丢失更新/重复扣减 |
| **残留** | `status=0` 的订单数 == 0（压测后等队列排空） | 消息丢了/消费卡住 |
| **重复** | 同 `(student_id, course_id)` 的 `status=1` 订单 ≤ 1 | 幂等失效 |
| **Redis 对账** | `Redis stock == MySQL stock` | 补偿/归还逻辑对不对 |

这几条全部写进了 `loadtest/verify-v3.ps1`，退出码 0/1，可以进 CI/脚本流水线。
**并且做了反向验证**：人为造 `sold=105`（超卖）和 `stock=99`（少卖），脚本必须报红。
报告里记录的两次反向测试都正确变红了 —— 判据有牙齿，不是摆设。

## 7. 踩过的坑（面试常被追问"你遇到过什么困难"）

### 7.1 测量类（最致命，因为会让你得出错误结论）

| 坑 | 症状 | 根因 | 教训 |
|---|---|---|---|
| **k6 只看 HTTP 状态码** | 压测报告显示 100% 成功率 | `response.status >= 400` 才算失败；若失败请求返回 HTTP 200，全部数据作废 | 业务成败必须单独打点，不能靠状态码 |
| **`maxVUs` > 学生池** | 1600 RPS 出现 12.62% 失败 | 多个 VU 共用同一学生 → 撞 `uk_student_course` | 压测参数必须与数据规模匹配 |
| **复位没 purge 队列** | 日志刷满「订单状态已更改」37679 条 | 上一轮的消息在下一轮被消费，订单已 TRUNCATE | 异步系统的复位要清**三个**存储：DB、Redis、队列 |
| **测内存时先 purge 再读** | 50 万条消息"只占 197 MB" | 读的是回收后的残留值 | 测峰值必须在释放前测 |
| **`Com_update` 数出两倍** | 每单 8.3 次 UPDATE，看起来在广播 | MySQL general_log 每条语句记 `Prepare` + `Execute` 两行 | 只数 `Execute` 行 |
| **压测时在旁边查库** | 某一轮 P95 突然 258 ms | 我的采样查询抢了资源 | 测量者不能干扰被测系统（那一轮已作废并标注） |

### 7.2 框架/语言类

| 坑 | 症状 | 根因 |
|---|---|---|
| **Jackson 3 的 ObjectMapper** | 启动报 `No qualifying bean of type 'com.fasterxml.jackson.databind.ObjectMapper'` | Boot 4 用 `tools.jackson`，但注解包仍是 `com.fasterxml.jackson.annotation`；`com.fasterxml...` 那个 class 是 jjwt 带进来的，能编译但**没有 Bean** |
| **Spring AMQP 两个转换器** | 同上，二选一 | `Jackson2JsonMessageConverter`（Jackson 2）vs `JacksonJsonMessageConverter`（Jackson 3）—— 必须用后者 |
| **MyBatis-Plus TableInfo 是全局静态缓存** | 纯 Mockito 单测报 `can not find lambda cache for this entity`；**本地绿、CI 红** | 缓存由 `@SpringBootTest` 预热，测试通过与否取决于**执行顺序** |
| **`$Pid` 是 PowerShell 只读变量** | 脚本一运行就报"无法覆盖变量 PID" | `$Pid`/`$args`/`$Host` 等都是自动变量，不能当形参 |
| **`.ps1` 必须 UTF-8 带 BOM** | `Unexpected token '鐩戞帶'` | PowerShell 5.1 按 GBK 读无 BOM 的 .ps1，中文注释变乱码吃掉引号 |
| **`.java`/`.js`/`.yaml` 必须无 BOM** | `BUILD FAILURE`，`illegal character '\ufeff'` | 编译器和 Node 都不吃 BOM。**两类文件的要求正好相反** |
| **Maven 增量编译不删旧 class** | `ConflictingBeanDefinitionException: bean name 'xxx' conflicts with ...` | 包名改了/文件删了，`target/classes` 里旧 class 还在 → 必须 `clean` |

### 7.3 逻辑类（最值得讲，因为都是"看起来对但错得离谱"）

**① `&&` 写成 `||` 的双重损坏**（C-5 登录）：

```java
// 错误写法
if (stu == null && !passwordEncoder.matches(pwd, stu.getPassword())) { throw 401; }
```

- 账号**不存在**时：左边 `true` 必算右边 → `stu.getPassword()` → **NPE → 500**
- 账号**存在**时：左边 `false` **短路跳过**右边 → **密码校验被完全绕过，任何密码都能登录**

一个符号同时造成 500 和"零密码可登录"。而且只测 happy path 永远发现不了 ——
**必须配一条"密码错也应该失败"的反例**。

**② 悲观锁里重复扣减**：
`selectForUpdate` 后调了一次 `absoluteUpdate`（扣 1），紧接着又调了 `tryDecrement`（再扣 1）。
表现：**每个成功请求扣 2 个名额，100 个名额只服务 50 人**。
最坑的是：**账目守恒**（`stock+sold=100`）、**无异常**、**无 ERROR 日志**、**HTTP 全 200/409**。
只有把"成功单数"和"capacity"对比才看得出来。

**③ 事务快照让乐观锁重试全部失效**：
REPEATABLE-READ 下，事务内的普通 `SELECT` 读的是**事务开始时的快照**。
重试循环写在事务里 → 每次重试读到的 `version` 永远是同一个旧值 → 3 次重试用同一个过期答案交卷。
实测：300 并发只成功 18 单。**修法：把重试移到事务外**（外层循环无事务，内层每次 `TransactionTemplate` 新事务）。
知识点：**乐观锁的重试边界必须和事务边界对齐。**

**④ `finally` 里不带 `if (!success)`**：
抢课成功时也执行"失败补偿"，把 Redis 库存还回去了 → 超卖。
这类错误的表现是"库存数字乱七八糟"，但代码读起来很合理。

**⑤ CAS 的返回值被丢弃**（阶段 7 补修，本项目唯一"完全静默"的缺陷）：

```java
// 错误写法：调用完不看返回值
seckillOrderMapper.updateStatusIfMatch(existing.getId(), STATUS_PENDING, existing.getStatus());
```

`updateStatusIfMatch` 是条件更新（`WHERE id=? AND status=?`），返回 0 表示**别人抢先改了**。
不检查就继续往下走：并发双击（或退课后立刻重选）时两个请求都发消息、都扣 Redis，
消费者只处理成功一条 → **Redis 永久偏低 1 个名额**。

为什么它比前四条都难发现：
- **不超卖**（偏低是安全方向，不会卖多）
- **不报错**（HTTP 200，前端一切正常）
- **日志无 WARN/ERROR**
- 只在"同一学生并发双击 + 退课后重选"时触发，人工点一次永远复现不了

修法只有三行（`int claimed = ...; if (claimed == 0) throw new BusinessException(CONFLICT, ...)`），
但**必须靠单测把这条路径钉死**——`seckill_casLost_neverSendsMessage` 断言消息零发送，
`seckill_casLost_returnsRedisExactlyOnce` 断言 Redis 恰好补回 1 次。

**⑥ 清扫订单时多还一次 MySQL 库存**（阶段 7 补修，是我写任务书时搞错的）：

v3 的库存扣减在**消费者**里，抢课接口只做"Redis 门禁扣 1 + 插一条 PENDING 订单"，MySQL 一行没碰。
而清扫的前提恰恰是"消费者没跑" → MySQL 从来没被扣过 → 再 `returnStock()` 一次就是**凭空造名额**。

反例：课程 88 已有 50 个成功订单（`stock=50, sold=50`），清扫一条卡住的 PENDING 后
变成 `stock=51, sold=49`，**总和仍是 100**（账目守恒看不出来），但这门课能卖出 **101** 单。

正确做法：清扫**只还 Redis，不碰 MySQL**（`PendingOrderSweeper` 的构造器里干脆不要 `CourseStockMapper`，
让编译期就堵死这条路）。账由消费者自己平：它晚到时会发现 `updateStatusByOrderNo` 返回 0，自己调 `returnStock`。

> 这个错误如果先写测试就不会发生——用例 3 断言"CAS 返回 0 时 `returnStock` 零调用"，一跑就红。

**⑦ 死信队列的转换器陷阱**（阶段 8 补做死信消费者时实测踩到，是"我写任务书也写错了"的第二个例子）：

死信队列里躺着的**恰恰就是转不过去的坏消息**（`{"msgId":"dlq-test-bad","orderNo":` 这种不完整 JSON）。
如果死信监听器用默认的 `JacksonJsonMessageConverter`，body 一进 `onMessage` 就先解析 → 抛
`MessageConversionException` → 因为 `default-requeue-rejected: false`，消息被**丢弃**，证据没了。

更反直觉的是：**把方法签名改成 `org.springframework.amqp.core.Message` 也不管用**。
读 Spring AMQP 4.1.1 源码：

| 位置 | 行为 |
|---|---|
| `MessagingMessageListenerAdapter#onMessage`（:183） | **无条件**调 `toMessagingMessage(amqpMessage)` |
| `MessagingMessageListenerAdapter#toMessagingMessage`（:300） | `getMessagingMessageConverter().fromMessage(amqpMessage)` |
| `MessagingMessageConverter#fromMessage`（:129） | **无条件**调 `extractPayload(message)` → `payloadConverter.fromMessage(message)` |

payload 转换发生在"推断方法参数类型"**之前**，跟形参写什么完全无关。
`providedArgumentTypes` 只决定"要不要再转成业务对象"，不决定"会不会先解析一遍"。

正确做法：给死信监听器**单独一个容器工厂**，把转换器换成 `SimpleMessageConverter`：

```java
@Bean
SimpleRabbitListenerContainerFactory deadLetterContainerFactory(
        SimpleRabbitListenerContainerFactoryConfigurer configurer,
        ConnectionFactory connectionFactory) {
    SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
    configurer.configure(factory, connectionFactory);   // 先套上 yaml 的 manual ack / 并发 / prefetch
    factory.setMessageConverter(new SimpleMessageConverter());  // 再覆盖转换器
    return factory;
}
```

```java
@RabbitListener(queues = RabbitConfig.DLQ_QUEUE, containerFactory = "deadLetterContainerFactory")
public void onMessage(Message raw, Channel channel) throws IOException { ... }
```

`SimpleMessageConverter` 只在 `contentType` 以 `text` 开头时解码成 String、等于
`CONTENT_TYPE_SERIALIZED_OBJECT` 时做 Java 反序列化，**其余情况一律返回原始 `byte[]`，永不因内容不合法抛异常**。
body 自己 `new String(raw.getBody(), UTF_8)` 拿，解析失败就存 null，**原文照落库**。

> 两个容易漏的点：①`configurer.configure(factory, connectionFactory)` 必须在
> `setMessageConverter` **之前**调，否则 manual ack、并发数、prefetch 会被覆盖掉；
> ②`SimpleMessageConverter` 只保证"不抛异常"，不保证"能解析"——所以 `parse()` 里仍需
> try-catch，失败时字段存 null、body 存原文。

**⑧ 多实例下清扫与消费者抢同一张订单**（阶段 9 补修）：

先纠正一个常见误解：**幂等闸在单实例下看起来靠的是"表里有记录"，其实靠的是数据库唯一索引。**
`mq_consume_log.msg_id` 上的唯一索引 + InnoDB 行锁，两个实例同时 `INSERT` 同一条消息时只有一个能成功，
另一个拿到 `DuplicateKeyException`。所以**幂等闸本身不需要任何分布式锁**，扩到三实例也照样对。

真正出问题的是**清扫与消费者之间的竞争**。清扫的 SQL 原本是：

```sql
SELECT * FROM seckill_order WHERE status = 0 AND create_time < ? ORDER BY id LIMIT 200
```

它和消费者的时序撞在一起是这样：

| 时刻 | 消费者 | 清扫 |
|---|---|---|
| T1 | `updateStatusByOrderNo` 成功，订单 → `status=1` | — |
| T2 | — | 扫到这条（此刻还是 `status=0`） |
| T3 | 提交事务，MySQL `stock-1 sold+1` | `updateStatusAndFailReason` 影响 0 行，**但如果只看扫描结果就还 Redis** |
| T4 | — | `incrementIfPresent` → **Redis 多还 1 个名额** |

清扫这边其实有 CAS 保护（`updateStatusAndFailReason` 的 `WHERE order_no=? AND status=0` 返回 0 就 `continue`），
所以**只有"清扫先读到旧值、消费者后提交、清扫 CAS 之前"这个极窄窗口**才漏。但它确实存在。

修法是给扫描条件加一条：

```sql
AND update_time = create_time
```

`update_time` 是 `ON UPDATE CURRENT_TIMESTAMP`，**任何**状态变更都会让它和 `create_time` 不相等。
所以这条条件等价于"这条订单从创建到现在一次都没被碰过"，天然排除掉消费者正在处理（行已被 `SELECT ... FOR UPDATE`
或 `UPDATE` 锁定/改过 `update_time`）和已经处理完的订单。

> 注意这只是**缩小竞争窗口，不是消除竞争**。彻底消除要靠 `StockReconciler` 兜底（Redis 偏高 5 分钟内收回）。
> 工程上"缩小到可接受 + 有兜底"比"追求绝对无锁"更现实。

另一个同批次修的：**订单号撞 `uk_order_no` 时直接给用户 409「你已选过该课程」是错的**。
订单号里带学号尾 + 时间戳，多实例同毫秒生成时有概率撞号，跟"选过课"毫无关系。
修法是 `catch (DuplicateKeyException)` 后**看异常消息里是哪个索引名**：

```java
private boolean isOrderNoConflict(DuplicateKeyException e) {
    String msg = e.getMessage();
    return msg != null && msg.contains("uk_order_no");
}
```

- `uk_order_no` → 换号重试，最多 3 次，仍失败才 500
- 其它（`uk_student_course`）→ 真的是"已选过"，直接 409，**绝不重试**

这个取舍值得讲：靠异常消息里的索引名判断是脆弱的（改索引名就失效），
但方向是安全的——只在 `uk_order_no` 时重试，最坏结果是撞号又变回 409（体验问题），
而不是"重复选课被静默重试"（正确性问题）。

**关于 CI 里 `set -o pipefail`**：这是踩过的坑。

```bash
./mvnw test 2>&1 | tee build.log     # ❌ 管道退出码取 tee 的，永远是 0
set -o pipefail; ./mvnw test 2>&1 | tee build.log   # ✅
```

不写 `pipefail`，**挂掉的测试会被绿着放过** —— 这类假绿比直接报错危险得多。

**关于单测的边界**（诚实说明，不吹）：

- 能测：分支逻辑、返回值翻译、ack/nack 的参数、调用顺序。
- **不能测**：事务是否真的回滚（Mockito 里事务边界是假的）、真实 ack 是否到达 broker、
  并发下是否超卖。
- 后者只能靠**实机压测 + 数据库计数器**，见 §6。

写测试时还踩了两个坑，都值得记：

1. `executeWithoutResult` 的形参是 `Consumer` 不是 `TransactionCallback`，
   强转会在运行期抛 `ClassCastException`，**被被测代码的 `catch (Exception)` 吞掉**，
   表现成"所有用例都走了技术异常分支"，非常难看出真实原因。
2. `ArgumentCaptor` 保存的是**对象引用**不是快照。被测代码后续改了同一个对象的字段，
   事后断言看到的是最终值。想断言"insert 时的状态"必须用 `doAnswer` 当场取值。

**CourseService 那 14 条里最值钱的一条**（后来补的，值得单独说）：

`sys_user` 表里管理员的 id 是 1，`student` 表里 S000000001 的 id 也是 1 —— **两边撞号**。
如果 `currentStudentId()` 只看 principal 不判角色，管理员打开页面就会看到"学生 1 的选课状态"，
而且**不抛任何异常、日志里也没有任何痕迹**。所以那条用例故意用**同一个 id=1** 登录成 ADMIN，
断言 `myOrderStatus` 必须为 `null` 且订单表一次都不许查。反向验证时把角色判断删掉，
这条立刻变红 —— 这就是"用一个必然撞号的输入去逼出隐藏缺陷"的写法。

另外 `listCourses` 有一条断言 `verify(seckillOrderMapper, times(1)).selectList(any())`，
钉死"订单只查一次、不是每门课查一次"。100 门课循环查就是 100 次 SQL，
这种 N+1 在功能测试里完全看不出来（结果一样对），只能靠调用次数断言守住。

## 9. 已知局限（主动交代，不藏）

1. ~~**数据量只有 1 万行**。分表实验（v5）在这个量级下"纯亏"，但**不能推出**"2000 万行也不该分表"。
   正确的说法是：**在当前数据量下分表是亏的；数据量上去后需要重测**。~~
   **已补测（2026-11-26）**：造出 2000 万行实测，结论与 1 万行一致 —— **仍然不该分表**，
   但原因变了：不是"数据量太小看不出收益"，而是**慢查询的瓶颈根本不是表大小**。
   详见 `docs/A8-分表2000万行实测报告.md`。一句话：慢的是"单门课 39.8 万条匹配记录"，
   分表后每片仍有 10 万条要扫，总量不变；而 buffer pool 从 128MB 加到 2GB 也毫无改善，
   证明瓶颈是 CPU 逐行处理而非 I/O。**更严重的代价是跨分片唯一索引失效**（已实测证明同一
   `order_no` 可同时存在于两个分片），这是正确性缺陷，比慢几十毫秒严重得多。
2. **单机**。没有多实例、没有分布式锁、没有跨机器幂等。`@PreAuthorize` + JWT 是单机安全的，
   但"同一用户在两台机器上同时抢"这种情况没测。
3. **confirm 超时但消息其实到了** → 可能超卖。已知窗口（时间线分析见 `压测报告-v3.md` §9.1），
   本阶段未解决（需要生产者侧的定期对账或订单状态机补全）。
4. **Redis 未开持久化**（开发环境 `appendonly=no`）。Redis 重启 → 库存全丢 → 全部走"未预热"分支。
   生产必须开 AOF（compose 里已经开了）。
5. **没有 refreshToken**。JWT 2 小时过期后用户必须重新登录。
6. **前端是单文件原生 JS**。课程列表一次查全部 100 门（约 20 KB），
   上千门课必须改成分页。
7. **RabbitMQ 单节点**，且容器限 512 MB / 0.5 核。堆积 50 万条约 93.4 MB（196 字节/条）不会顶到
   500 MB，但**水位保护在这个容器里永不先触发**（它按宿主机 3.83 GB 算水位），
   真实失败方式是被内核 OOM 杀。排查第一句永远是
   `docker inspect seckill-rabbitmq --format '{{.State.OOMKilled}} {{.State.RestartCount}}'`。

## 10. 面试话术（20 分钟版）

### Q1：介绍一下这个项目

> 一个高并发选课的练习项目。核心是一条演进主线：同一个抢课接口写了 5 个版本，
> 从"必然超卖"做到"300 并发零超卖、P95 66 毫秒"，每一版都用**数据库自己的计数器**
> 和库存守恒做交叉验证。
>
> 业务很简单：100 个名额、1 万个学生、同一秒涌入。技术上真正的难点不是写代码，
> 而是**证明你的优化真的生效了** —— 我一开始就被一个脚本 bug 骗出过"1200 RPS 是上限"的错误结论。

### Q2：怎么复现超卖的？

> 先写一个故意没有并发保护的版本：读库存 → 判断 → 算新值 → 写回。四步之间别人能插进来。
>
> 300 并发抢 100 个名额，卖出 300 单，超卖 200%。
>
> **但光看"卖出 300 单"不够，我做了两个关键验证**：
>
> 第一，**串行对照**：1 个请求时完全正确（100 单、缺口 0）。这排除了"代码写错"、
> "数据有问题"、"压测工具造假"，剩下的唯一变量就是并发。
>
> 第二，看 `stock` 的实际值：300 单卖出去了，但 `stock` 只从 100 掉到 96。
> 这是**丢失更新**的指纹 —— 多个线程都读到 100、都算 99、都写回 99。
>
> 顺带一个反直觉的发现：我给 `stock` 加过 `CHECK (stock >= 0)` 约束，**它完全没防住超卖**。
> 因为库存根本没掉到负数。约束保证"库存不为负"，不保证"订单数 ≤ 名额"。

### Q3：v1 为什么用 `UPDATE ... WHERE stock > 0` 而不是先查再改？

> 因为 `getStock()` 读到的只是某一时刻的快照，用它判断就是 v0 的超卖。
>
> `UPDATE ... WHERE stock > 0` 内部是五步原子：加行锁 → 读值 → 判条件 → 写回 → 释放锁。
> 中间没人能插进来。而且它的**返回值（affected rows）就是数据库对并发做出的裁决**：
> 1 表示抢到，0 表示没抢到。
>
> 这是 v1 最核心的认知：**affected rows 是唯一可信的答案，读出来的值不是。**

### Q4：v1 已经零超卖了，为什么还要 v2？

> 因为 v1 的问题不是超卖，是**浪费**：300 个请求抢 100 个名额，200 个注定失败的请求
> 也要各占一次数据库连接 + 一次行锁排队。
>
> v2 把库存预热进 Redis，用 Lua 脚本原子扣减，挡掉这 200 个。
>
> **怎么证明挡掉了？** 这里我用了一个自己觉得最有说服力的方法：读 MySQL 的
> `Com_update` 计数器。v1 压一轮是 300 次 UPDATE，v2 是 100 次 —— **精确 3:1**。
> 这个数字不是我们统计的，是数据库自己数的。
>
> 只盯 P95 的话会得出错误结论：339 → 322 ms，只快 5%，看起来"没效果"。
> 实际上机制完全生效了，只是**瓶颈转移**了 —— 剩下 100 个成功请求还是串行在同一行行锁上。

### Q5：v3 异步之后，怎么保证"不超卖"且"不漏单"？

> 异步之后正确性地基变了：以前是"数据库行锁保证"，现在是"Redis 门禁 + MQ 至少一次投递 +
> 幂等闸 + 库存守恒"四件事一起保证。
>
> 具体三件事：
>
> **消息会丢** —— 三个位置都要管。生产者→broker 用 publisher confirm；
> broker 自己靠 durable + persistent；broker→消费者用手动 ack。
> **最容易错的是 ack 时机**：必须等事务提交之后再 ack。
> 反过来的话，ack 之后进程崩了，消息不会重投，但订单永远停在待处理 ——
> **而且日志里一条 ERROR 都没有**。
>
> **消息会重复** —— AMQP 是至少一次投递。我用 `mq_consume_log` 表，`msg_id` 上加唯一索引，
> 撞了就抛异常、正常 ack。关键是**幂等记录必须和业务在同一个事务里**，
> 否则记录提交了、业务回滚了，重投时会被误判成重复消息，订单永远落不下来。
>
> **消息会失败** —— 分两类。业务失败（库存不足）标 `status=2` 然后**正常 ack**，
> 因为重投一万次结果都一样，只会刷爆死信队列。技术异常才 `basicNack` 进死信，
> 而且 **requeue 必须是 false** —— 写 true 会让毒消息无限重投，CPU 打满但一条错误日志都没有。
>
> 最后用库存守恒 + 成功单数双向验证：不只看"有没有超卖"，也看"有没有少卖"。
> 这两种错误的症状完全不同：超卖是数字多了，少卖是"账目完美守恒但只服务了一半人"。

### Q6：你说分库分表是亏的，有什么依据？

> 有实测数据。我用 ShardingSphere-JDBC 5.5.3 按 `student_id % 4` 分了 4 片，
> 热 SQL 全部加上分片键（避免广播，实测每单 4.17 次 UPDATE，广播会接近 7 次）。
>
> 结果：
>
> | RPS | 不分表 | 分表 |
> |---|---|---|
> | 1200 | P95 20 ms | P95 **88 ms** |
> | 1600 | P95 121 ms | P95 **2.78 s**，丢弃 5412 |
>
> **1200 慢 4.4 倍，1600 直接崩。**
>
> 我没有停在"分表就是慢"，而是逐项排除了：连接池从 20 加到 50 **更差**；
> JVM 全程采样 CPU 峰值 20.8%、FullGC 0 次；MySQL 连接数只有 12（上限 151）；
> 日志里 `Deadlock`/`Timeout` 全 0；串行单发 38 ms 说明单请求没问题。
> 剩下的唯一解释是 ShardingSphere 的**解析→改写→路由→归并**这一层，
> 每个请求多一层固定开销，并发下线性放大。
>
> **所以结论是：分表解决"数据量大"，而我这个项目的核心矛盾是"并发高"，两个不是同一个问题。**
> 这也让我理解了为什么很多公司数据量不大却上了分库分表 —— 那是为了别的目的（隔离、扩容）。
>
> 顺带三个实测出来、文档上很少提的坑：跨分片的 `uk_order_no` **完全失效**（同一个订单号
> 能同时存在于两个分片）；没在 yaml 里登记的表直接报 `Table or view does not exist`，
> 「只分一张表」这条路走不通；`uk_student_course` 侥幸还有效，只是因为分片键正好是 `student_id`。

### Q7：这个项目最大的难点是什么？

> **让数字可信**，不是写代码。
>
> 我在这上面犯过至少六个错，每一个都会让我得出错误结论：
>
> - k6 只看 HTTP 状态码，如果失败请求返回 200，报告会显示 100% 成功率 —— 全部数据作废。
> - `maxVUs` 设成 4000 但学生池只有 900，多个虚拟用户抢同一个学生，撞唯一索引，
>   1600 RPS 出现 12.62% 假失败。我一度得出"1200 RPS 是上限"的结论，**是错的**。
>   压到 900 后同一负载变成 0% 失败、P95 从 711 ms 降到 110 ms。
> - 复位只清数据库、没清 MQ 队列，上一轮的消息在下一轮被消费，日志刷满 37679 条"订单状态已更改"。
> - 测 MQ 堆积内存时先 purge 再读，读的是回收后的残留值，把 93 MB 读成了"197 MB 但只有 30 万条"。
> - 数 `Com_update` 时把 `Prepare` 和 `Execute` 两行都算了，得到"每单 8.3 次 UPDATE"的假象。
> - 有一轮压测时我同时在旁边查数据库采样，那一轮的 P95 是 258 ms —— **我自己污染了测量**。
>
> 所以我现在养成三个习惯：**一次只改一个变量**；**任何"变快了"的结论必须找出机制解释**；
> **做完优化先想"如果这个优化没生效，我会看到什么"** —— 如果两种情况看到的现象一样，
> 说明这个测量方法不成立。

### Q8：如果继续做，下一步做什么？

> 三条，按性价比排：
>
> 1. ~~**补 PENDING 清扫**：现在 v3 里如果 confirm 超时但消息其实到了，订单会停在待处理。
>    需要定时任务扫 `status=0 且 create_time < now-30s` 的订单，去对账。~~
>    **已做**（阶段 7）：`PendingOrderSweeper` 每分钟扫一次，条件更新抢占后归还 Redis。
>    踩过的坑见 §7.3 ⑥——清扫**只能还 Redis，不能还 MySQL**，否则凭空造名额。
> 2. ~~**多实例**：现在所有设计都是单机。加两个实例就要面对"同一用户并发抢"、
>    "消费者多实例下的顺序性"这些新问题。~~
>    **已做**（阶段 9）：排查下来最有意思的结论是**幂等闸根本不需要分布式锁** ——
>    `mq_consume_log.msg_id` 的唯一索引 + InnoDB 行锁已经把跨实例并发解决掉了。
>    真正要修的是清扫与消费者抢同一张订单（扫描条件加 `AND update_time = create_time`），
>    以及订单号撞 `uk_order_no` 时要换号重试而不是给用户 409。详见 §7.3 ⑧。
> 3. ~~**数据量真上去之后重测分表**：v5 的结论只在 1 万行成立，2000 万行必须重测。~~
>    **已做**（`docs/A8-分表2000万行实测报告.md`）：造了 2000 万行实测，结论仍是"不该分表"。
>    但真正的收获不是这个结论，而是**发现了一个更该做的事** —— 深分页改游标分页，
>    同一张表上 `LIMIT 100000,20` 要 280ms，`WHERE id > ? LIMIT 20` 只要 0.2ms，**快 1000 倍**。
>    所以下一步该做的是**改查询**，不是分表。

## 12. 最后

这个项目教给我的最重要的一件事，不是"怎么用 Redis"或"怎么用 RabbitMQ"，
而是：

> **优化本身不难，难的是证明它真的优化了。**

五个版本里，有三个版本我第一次跑出来的数据是**假的** —— 有的是脚本 bug，
有的是我自己的采样干扰，有的是把框架的默认行为当成了业务逻辑。
每一次都是靠"再换一种方式量一遍"才发现的。

所以如果只带走一条经验，是这条：

> **任何性能结论，都要能找到一个独立于测量工具的第二证据。**
> P95 变快了不算证据；`Com_update` 从 300 变成 100 才算。
