## 0. 这份任务书要你做什么

一句话：**给 `/api/seckill/**` 加一个基于 Redis 的令牌桶限流器，超出配额返回 429，并用压测证明「有限流」比「无限流」在过载时表现更好。**

拆成 5 个任务：

| # | 任务 | 预计 | 能否跳过 |
|---|---|---|---|
| A | Lua 脚本（已实测可用，照抄） | 15 min | ❌ |
| B | Java 侧：Bean + Service | 40 min | ❌ |
| C | Filter + 挂到 Security 链 | 40 min | ❌ |
| D | 前端 429 分支 | 10 min | ✅ 可跳过，但会留个坑 |
| E | 压测脚本改造 + 对比实验 | 90 min | ❌ 这是本阶段的**唯一价值来源** |

**最重要的不是代码，是第 9 节那个对比实验。** 限流器写出来谁都会写，能拿出「同一负载下，关掉限流 P95 崩到 3 秒、丢 5000 个请求；打开限流 25% 拿到 429、成功的那部分 P95 稳定在 130ms」这组数字，才是这个阶段的意义。

## 2. 为什么选令牌桶

### 2.1 四种算法对比

| 算法 | 突发流量 | 实现复杂度 | 为什么不用 |
|---|---|---|---|
| **固定窗口**（每分钟计数，到点清零） | ❌ 窗口边界能过 2 倍流量 | 最低 | 秒杀场景最怕边界穿透：59.9 秒打满 + 60.1 秒打满 = 2 倍 |
| **滑动窗口日志**（存每个请求时间戳） | ✅ | 中 | 内存随 QPS 线性增长，1600 RPS 一分钟就是 9.6 万个时间戳 |
| **滑动窗口计数**（分桶近似） | ✅ 近似 | 中 | 要维护多个桶，代码量比令牌桶大，精度还不完美 |
| **令牌桶** ✅ | ✅ **允许突发到 capacity，长期平均被 refill 限制** | 低（一段 Lua） | —— |

令牌桶的关键性质：**`capacity` 和 `refillPerSecond` 是两个独立的旋钮**。

- `refillPerSecond` 决定长期吞吐上限（稳态下每秒最多放行这么多）
- `capacity` 决定允许多大的突发（空闲一段时间后攒下的令牌，可以一次性用掉）

对秒杀来说这个性质正好：平时没人抢课，桶是满的；开抢瞬间放进来一批（突发），之后按 refill 速率匀速放行。**固定窗口做不到这个区分。**

### 2.2 为什么不用现成库

bucket4j 本地仓库没有，项目一直是**离线构建**（`-o`），装新依赖要先联网下载一轮。更关键的理由：**这个项目从 v2 开始的核心叙事就是「用 Redis + Lua 做原子操作」**，库存扣减是这么做的，限流用同一个套路，面试时是一条连贯的线（「凡是需要跨实例原子的计数，我都放 Redis + Lua」），而不是「这里用 bucket4j、那里自己写」。

自己写的代价是要处理边界情况（见 §4.3 的实测表），但只有一段 30 行的脚本。

### 2.3 为什么放 Redis 而不是本地内存

单实例本地 `Semaphore` 更快（零网络开销），但：

1. **多实例下配额会被放大 N 倍**。三副本各限 1500/s = 实际 4500/s，限流器形同虚设。
2. 阶段 9 刚把系统做成可 `--scale app=3`，用本地计数器等于把这个能力废掉。

代价是每个请求多一次 Redis 往返（约 0.2~0.5 ms）。这个代价值不值，**第 9 节要实测出来**，不能靠嘴说。

## 3. 设计决策（先想清楚再动手）

这一节是整份文档最该慢慢读的部分。代码只有 150 行，但下面 5 个决策每一个选错都要返工。

### 3.1 限流放哪一层

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Servlet `Filter` | 最早拦下，不进 Controller、不占业务线程 | 拿不到方法参数 | ✅ **选这个** |
| `HandlerInterceptor` | 能拿到 handler 信息 | 已经在 DispatcherServlet 里了，晚一步 | ❌ |
| `@Aspect` 切 Service | 能精确到方法 | **太晚了** —— 请求已经进 Tomcat 线程池、Spring MVC 已解析完参数。过载时线程池先被打满，限流器还没执行 | ❌ 这是最常见的错误选择 |
| 网关/Nginx 限流 | 最省应用资源 | 本项目没有网关；且拿不到「哪个学生」这个维度 | ❌ |

**关键理解：限流的价值在于「在系统还没被压垮之前就拒绝」。** 放到 Service 层，请求已经占用了 Tomcat 线程（本项目 `max-threads: 200`），200 个线程全卡在等锁时，第 201 个请求连限流器都进不去 —— 它在等线程。

### 3.2 放在 JWT 之前还是之后（最容易踩的坑）

要按学生维度限流，就必须知道「当前是哪个学生」，而这个信息由 `JwtAuthenticationFilter` 写进 `SecurityContextHolder`。所以**必须放在 JWT 之后**。

但「之后」有两种实现方式，结果完全不同：

**❌ 错误做法：加 `@Component` 就完事**

```java
@Component   // Boot 会自动把它注册成 Servlet Filter
public class RateLimitFilter extends OncePerRequestFilter { ... }
```

Spring Boot 的 `ServletContextInitializer` 会把容器里所有 `Filter` 类型的 Bean **自动注册到 Servlet 容器**，而 Servlet 容器的 Filter 跑在 **Spring Security 的 `FilterChainProxy` 之前**。也就是说：

```
请求 → [RateLimitFilter]  ← 这里 SecurityContext 是空的！
     → [FilterChainProxy]
       → [JwtAuthenticationFilter]  ← 身份在这里才被解析出来
       → [AuthorizationFilter]
       → Controller
```

结果：`SecurityContextHolder.getContext().getAuthentication()` 永远是 `null`，所有请求都被当成同一个「匿名桶」，学生维度限流彻底失效 —— **而且不会报任何错**，你会以为它在工作。

**✅ 正确做法：挂进 Security 链，并关掉自动注册**

```java
// SecurityConfig 里
http.addFilterAfter(rateLimitFilter, JwtAuthenticationFilter.class);

// 同时必须加这个，否则会被执行两次（Servlet 容器一次 + Security 链一次）
@Bean
public FilterRegistrationBean<RateLimitFilter> rateLimitFilterRegistration(RateLimitFilter filter) {
    FilterRegistrationBean<RateLimitFilter> registration = new FilterRegistrationBean<>(filter);
    registration.setEnabled(false);
    return registration;
}
```

`JwtAuthenticationFilter` 现在就是这么干的（`SecurityConfig` 里已有 `jwtFilterRegistration`），照抄。

> **怎么验证自己有没有踩这个坑**：在 filter 里 `log.debug` 打出 `studentId`，用一个带 token 的请求打一次，如果打出来是 `null`，就是这个坑。

### 3.3 限几个维度

建议**两层，都做**：

| 维度 | key | capacity | refillPerSecond | 作用 |
|---|---|---|---|---|
| **全局** | `seckill:rate:global` | 2000 | 1500 | 保护系统不崩。这是主力 |
| **每学生** | `seckill:rate:student:{studentId}` | 5 | 1 | 防单个学生刷接口。公平性 |

为什么两个都要：全局桶挡不住「一个学生每秒点 100 次」这种局部问题（他只占全局配额的一小部分，但会把别人的机会挤掉一部分）；每学生桶挡不住「一万个学生同时点一次」这种全局问题。**两者解决的是不同的问题。**

为什么全局设 1500 而不是 1600：**限流阈值必须低于系统容量，否则限流器自己就是瓶颈。** 1600 是「零失败的极限」，不是「安全的运行点」，要留余量给清扫任务、对账任务、以及 P95 抖动。

> 这两个数字都要能配置，不要写死。压测时你需要改它们（见 §9.2）。

**明确不做「每课程」维度**：每门课的竞争由 Redis 库存门禁（`tryDecrement`）处理，再加一层限流是重复劳动。见 §12。

### 3.4 Redis 挂了怎么办：fail-open 还是 fail-closed

这是必须显式决定、不能含糊的一个选择。

| 策略 | 行为 | 后果 |
|---|---|---|
| **fail-open** ✅ | Redis 异常 → 打 `log.error` → **放行** | 限流失效，但系统还能跑（虽然可能被压垮） |
| fail-closed | Redis 异常 → 直接 429 | 所有请求被拒，**Redis 一挂全站不可用** |

**选 fail-open**，理由：

1. 抢课链路本来就依赖 Redis（`tryDecrement`），Redis 挂了之后业务自己会返回 500「系统繁忙」。限流器再叠一个 429 只是换了个错误码，没增加价值。
2. 限流是**保护性设施**，不是**正确性设施**。保护性设施失效时的正确行为是「降级到无保护」，不是「拒绝服务」。
3. fail-closed 会造成一个荒谬的场景：Redis 短暂抖动 2 秒，全站 429，比不加限流还糟。

⚠️ 但必须 `log.error` 并带上 key，否则你不知道它在失效。

### 3.5 多实例的时钟问题

令牌桶要算「距上次补充过了多少毫秒」，需要一个时间戳。两个选择：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **Java 传 `System.currentTimeMillis()`** ✅ | **可测试**（能注入假时间验证补充逻辑） | 多实例间有钟差（NTP 同步下通常 < 100 ms） |
| Lua 里 `redis.call('TIME')` | 全实例共用一个权威时钟 | 无法在单测里控制时间；且 `TIME` 在 Lua 里属于非确定性命令，虽然 Redis 5+ 用效果复制已经允许，但某些托管 Redis 会禁 |

**选 Java 传**。钟差的实际影响：3 个实例各差 50 ms，在 1500/s 的 refill 速率下相当于多补 75 个令牌 —— 占 capacity 2000 的 3.75%，可以忽略。而可测试性的收益是实打实的。

⚠️ 传参时用 `String.valueOf(long)`，不要 `int`（毫秒时间戳是 13 位，超 int 范围）。Lua 的 `tonumber` 处理 13 位整数**不丢精度** —— 这一点我实测过，见 §4.3 用例 D。

## 4. 任务 A：Lua 脚本

### 4.1 脚本全文（已实测可用，直接抄）

新建 `src/main/java/com/example/seckill/infra/cache/RateLimitLuaScript.java`：

```java
package com.example.seckill.infra.cache;

/**
 * 限流相关的 Lua 脚本。
 * <p>
 * 与 {@link StockLuaScript} 同样的组织方式：脚本文本放常量类，
 * RedisConfig 里包成 DefaultRedisScript Bean。
 */
public final class RateLimitLuaScript {

    private RateLimitLuaScript() {
        throw new AssertionError("常量类不允许实例化");
    }

    /**
     * 令牌桶取令牌。
     * <p>
     * KEYS[1] = 限流 key（如 seckill:rate:global）
     * ARGV[1] = capacity        桶容量，允许的突发量
     * ARGV[2] = refillPerSecond 每秒补充的令牌数（可以是小数）
     * ARGV[3] = nowMs           当前时间戳毫秒，**由 Java 传入**，理由见任务书 §3.5
     * ARGV[4] = want            本次要取的令牌数，通常 1
     * <p>
     * 返回三元素数组 {allowed, remaining, retryAfterMs}：
     * allowed      = 1 放行 / 0 拒绝
     * remaining    = 取完之后的剩余令牌（向下取整，只用于展示）
     * retryAfterMs = 建议等待多久再试（allowed=1 时恒为 0）
     */
    public static final String TOKEN_BUCKET = """
            local key = KEYS[1]
            local capacity = tonumber(ARGV[1])
            local refillPerSecond = tonumber(ARGV[2])
            local nowMs = tonumber(ARGV[3])
            local want = tonumber(ARGV[4])

            local data = redis.call('HMGET', key, 'tokens', 'ts')
            local tokens = tonumber(data[1])
            local ts = tonumber(data[2])

            if tokens == nil then
              tokens = capacity
              ts = nowMs
            end

            local elapsedMs = nowMs - ts
            if elapsedMs < 0 then elapsedMs = 0 end
            tokens = tokens + (elapsedMs / 1000) * refillPerSecond
            if tokens > capacity then tokens = capacity end

            local ttl = math.ceil(capacity / refillPerSecond) + 60

            if tokens < want then
              local waitMs = math.ceil((want - tokens) / refillPerSecond * 1000)
              redis.call('HSET', key, 'tokens', tokens, 'ts', nowMs)
              redis.call('EXPIRE', key, ttl)
              return {0, math.floor(tokens), waitMs}
            end

            tokens = tokens - want
            redis.call('HSET', key, 'tokens', tokens, 'ts', nowMs)
            redis.call('EXPIRE', key, ttl)
            return {1, math.floor(tokens), 0}
            """;
}
```

> ⚠️ Java 15+ 的文本块 `"""` 里，Lua 的 `\n` 不需要转义。用文本块而不是 `"..." + "..."` 拼接，避免出现阶段 9 那个「拼字符串吃掉空格」的坑。

### 4.2 逐行解释（为什么要这么写）

**为什么用 `HMGET` 存两个字段而不是两个 key**

一个 hash 两个字段，一次 `HMGET` 取回，一次 `HSET` 写回。如果用 `seckill:rate:global:tokens` 和 `seckill:rate:global:ts` 两个 key，脚本里就要两次 `GET` + 两次 `SET`，虽然 Lua 里也是原子的，但 key 数量翻倍，且两个 key 的 TTL 可能不一致（一个过期一个没过期 → 读到 `tokens` 但 `ts` 是 nil → 算出天文数字的补充量 → 直接爆表）。

**为什么 `tokens == nil` 时初始化为满桶**

新 key 意味着「这个学生/全局第一次请求」，给满桶是合理默认值。注意 `tonumber(nil)` 返回 `nil`（不是 0），所以这个判断能正确区分「不存在」和「存在但值为 0」。

**为什么 `elapsedMs < 0` 要钳到 0**

时钟回拨（NTP 校时、虚拟机迁移）时 `nowMs < ts`，`elapsedMs` 为负 → `tokens` 变小 → 令牌凭空消失。钳到 0 就是「回拨期间不补充也不扣除」。这一条我实测过（§4.3 用例 8）。

**为什么 `tokens > capacity` 要封顶**

空闲 1 小时后，`elapsedMs = 3600000`，按 1500/s 补能补出 540 万个令牌。不封顶的话桶容量形同虚设，一次突发能把系统打穿。这一条我实测过（§4.3 用例 6）。

**为什么 `math.floor` 只在返回值上做，不写回 Redis**

`tokens` 必须保留小数。假设 capacity=10、refill=10/s，每 50 ms 补 0.5 个令牌。如果每次写回时 `floor`，这 0.5 永远丢失，实际速率就变成「每 100 ms 才补 1 个」= 10/s 变成 5/s，**限流比配置的严格一倍**。实测确认 Redis 里存的是 `98.37` 这种小数（§4.3 用例 E）。

**为什么 TTL 是 `ceil(capacity / refillPerSecond) + 60`**

`capacity / refillPerSecond` 是「从空桶补满需要几秒」。超过这个时间没有任何请求，桶必然已满，key 留着没意义。加 60 秒是安全余量（防止边界上刚好被删导致状态丢失）。以全局桶 2000/1500 为例 → `ceil(1.33) + 60 = 62` 秒。

⚠️ **`refillPerSecond` 为 0 时这里会除零**。Java 侧必须校验 `refillPerSecond > 0`，见 §5.3。

| 2 | 紧接着再取 1（同一毫秒） | `1 / 1 / 0` | `1 1 0` | ✅ |
| 3 | 再取 1 | `1 / 0 / 0` | `1 0 0` | ✅ |
| 4 | 桶空再取 | `0 / 0 / 1000` | `0 0 1000` | ✅ 拒绝 + 正确的重试等待 |
| 5 | 前进 1000 ms 再取 | `1 / 0 / 0` | `1 0 0` | ✅ 补了 1 个刚好够用 |
| 6 | 前进 10000 ms（远超容量） | `1 / 2 / 0` | `1 2 0` | ✅ **封顶生效**，没补成 10 个 |
| 7 | `TTL` | > 0 | `63` | ✅ 与公式 `ceil(3/1)+60` 一致 |
| 8 | 时间回拨到 900000（早于 ts） | 不报错 | `1 / 1 / 0` | ✅ 钳位生效，没扣成负数 |
| 9 | capacity=10 refill=10/s，取满后前进 50 ms 再取 1 | 补 0.5 个，够用 | `1 / 0 / 0` | ✅ 小数补充生效 |

**用例 9 的补充证据**（直接读 Redis 里的原始值）：

```
HGET rl:probe tokens  →  98.37
HGET rl:probe ts      →  1794564516196
```

`98.37` 证明小数被完整保留，没有被 `floor` 吃掉。

### 4.4 🔴 一个必须知道的坑：`setResultType` 必须是 `List.class`

脚本返回 3 个值，Java 侧用 `DefaultRedisScript` 接。如果你顺手写成 `Long.class`（因为库存脚本就是 `Long`）：

```java
new DefaultRedisScript<>(scriptText, Long.class)   // ❌
```

**不会报错，会静默返回数组里的「最后一个值」，而且判定会彻底反转。** 我实测过两次，第二次才是真相。

第一次我用一个「返回 `{5, 7, 9}`」的探针脚本，以为能看出取的是哪个元素：

```
=== 脚本 return {5, 7, 9} ===
Long.class  -> 9          ← 不是第一个，是最后一个
List.class  -> [5, 7, 9]
```

**取的是最后一个元素。** 这一条直接推翻了「用 Long 接会拿到 0 所以全拒绝」的猜想 —— 因为最后一个元素是 `retryAfterMs`，它**在放行时恒为 0、在拒绝时是正数**。于是真正的后果是**判定反转**：

```
=== 真实令牌桶脚本 + Long.class（capacity=2，前两次应放行、第三次应拒绝）===
第1次  Long.class 拿到 = 0      ← 本应放行，却被当成【拒绝】
第2次  Long.class 拿到 = 0      ← 本应放行，却被当成【拒绝】
第3次  Long.class 拿到 = 1000   ← 本应拒绝，却被当成【放行】

--- 对照：List.class 看到的真实返回值 ---
第1次  List.class 拿到 = [1, 1, 0]
第2次  List.class 拿到 = [1, 0, 0]
第3次  List.class 拿到 = [0, 0, 1000]
```

**这是最坏的一种错误**：不是「全拒绝」（那样你一测就发现），而是**「该放的拦了、该拦的放了」** —— 限流器完全反向工作，正常用户被拒，超量请求反而放行。而且日志里一行异常都没有。

> 这也是为什么 §11 的变异测试第 4 项标了「单测抓不到」：`StringRedisTemplate` 在单测里被 mock 掉了，`setResultType` 的真实行为根本执行不到。**这类 bug 只能靠真机实测发现。**

顺带一提：`String.class` 也不行，会抛 `RedisSystemException: Unknown redis exception`（多值返回无法转成单个字符串）。**只有 `List.class` 是对的。**

正确写法：

```java
@Bean
public DefaultRedisScript<List> rateLimitScript() {
    DefaultRedisScript<List> script = new DefaultRedisScript<>();
    script.setScriptText(RateLimitLuaScript.TOKEN_BUCKET);
    script.setResultType(List.class);
    return script;
}
```

返回的 `List` 里每个元素都是 `java.lang.Long`，取值时用 `((Number) list.get(0)).longValue()` 最安全（避免装箱类型假设）。

### 5.2 Service 接口与实现

**接口** `src/main/java/com/example/seckill/infra/cache/RateLimitService.java`：

```java
package com.example.seckill.infra.cache;

/**
 * 限流服务。
 * <p>
 * 实现放在 Redis 上而不是本地内存：多实例下本地计数器会把配额放大 N 倍。
 */
public interface RateLimitService {

    /**
     * 尝试获取令牌。
     *
     * @param key              限流 key，如 seckill:rate:global
     * @param capacity         桶容量
     * @param refillPerSecond  每秒补充数
     * @param want             本次要几个令牌，通常 1
     * @return 判定结果，永不为 null（Redis 挂了也返回一个"放行"的结果，见实现里的 fail-open）
     */
    RateLimitResult tryAcquire(String key, int capacity, double refillPerSecond, int want);
}
```

**结果对象** `src/main/java/com/example/seckill/infra/cache/RateLimitResult.java`（用 record，与项目里 `CacheStockStatusVO` / `ReconcileResult` 风格一致）：

```java
package com.example.seckill.infra.cache;

/**
 * 一次限流判定的结果。
 *
 * @param allowed      是否放行
 * @param remaining    剩余令牌（向下取整，仅用于展示/响应头）
 * @param retryAfterMs 建议等待毫秒数，allowed=true 时恒为 0
 * @param degraded     是否因为 Redis 异常而降级放行（true 表示限流当前没在起作用）
 */
public record RateLimitResult(boolean allowed, long remaining, long retryAfterMs, boolean degraded) {

    public static RateLimitResult pass(long remaining) {
        return new RateLimitResult(true, remaining, 0L, false);
    }

    public static RateLimitResult reject(long remaining, long retryAfterMs) {
        return new RateLimitResult(false, remaining, retryAfterMs, false);
    }

    /** Redis 出问题时的降级结果：放行，但标记 degraded 让调用方打日志 */
    public static RateLimitResult degradedPass() {
        return new RateLimitResult(true, -1L, 0L, true);
    }
}
```

**实现** `src/main/java/com/example/seckill/infra/cache/impl/RateLimitServiceImpl.java`：

```java
package com.example.seckill.infra.cache.impl;

import com.example.seckill.infra.cache.RateLimitResult;
import com.example.seckill.infra.cache.RateLimitService;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Service;

import java.util.List;

@Slf4j
@Service
public class RateLimitServiceImpl implements RateLimitService {

    private final StringRedisTemplate stringRedisTemplate;
    private final DefaultRedisScript<List> rateLimitScript;

    public RateLimitServiceImpl(StringRedisTemplate stringRedisTemplate,
                                DefaultRedisScript<List> rateLimitScript) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.rateLimitScript = rateLimitScript;
    }

    @Override
    public RateLimitResult tryAcquire(String key, int capacity, double refillPerSecond, int want) {
        if (capacity <= 0 || refillPerSecond <= 0 || want <= 0) {
            // 配置错了：宁可放行也不要因为限流配置把全站拒掉，但必须喊出来
            log.error("限流参数非法，已跳过限流 key={} capacity={} refillPerSecond={} want={}",
                    key, capacity, refillPerSecond, want);
            return RateLimitResult.degradedPass();
        }
        if (want > capacity) {
            // 要的比桶还大，永远不可能满足；这是配置错误，不是运行时问题
            log.error("限流配置错误：want={} 大于 capacity={}，该请求将永远被拒 key={}", want, capacity, key);
            return RateLimitResult.reject(0L, 1000L);
        }
        try {
            List<?> raw = stringRedisTemplate.execute(
                    rateLimitScript,
                    List.of(key),
                    String.valueOf(capacity),
                    String.valueOf(refillPerSecond),
                    String.valueOf(System.currentTimeMillis()),
                    String.valueOf(want));
            if (raw == null || raw.size() < 3) {
                log.error("限流脚本返回异常，已降级放行 key={} raw={}", key, raw);
                return RateLimitResult.degradedPass();
            }
            boolean allowed = ((Number) raw.get(0)).longValue() == 1L;
            long remaining = ((Number) raw.get(1)).longValue();
            long retryAfterMs = ((Number) raw.get(2)).longValue();
            return allowed ? RateLimitResult.pass(remaining)
                           : RateLimitResult.reject(remaining, retryAfterMs);
        } catch (Exception e) {
            // fail-open：限流是保护性设施，不是正确性设施。
            // Redis 挂了之后抢课链路本来就会返回 500，再叠一个 429 没意义。
            log.error("限流执行失败，降级放行（限流当前未生效） key={}", key, e);
            return RateLimitResult.degradedPass();
        }
    }
}
```

⚠️ 三个容易写错的地方：
1. `System.currentTimeMillis()` 必须用 `String.valueOf`，不能直接传 `long`（`execute` 的可变参数是 `Object...`，传 `long` 会被装箱成 `Long`，Lettuce 序列化时可能变成二进制而不是字符串 → Lua 里 `tonumber` 拿到 `nil` → 报 `attempt to perform arithmetic on local 'nowMs' (a nil value)`。**这个报错我在调试脚本时真的遇到过一次**）。
2. `List.of(key)` 是 `KEYS`，后面 4 个参数是 `ARGV`。顺序不能错。
3. 返回的 `List` 元素是 `Long`，用 `((Number) x).longValue()` 而不是强转 `(Long)`。

## 6. 任务 C：Filter

### 6.1 代码

`src/main/java/com/example/seckill/security/RateLimitFilter.java`：

```java
package com.example.seckill.security;

import com.example.seckill.common.Result;
import com.example.seckill.common.ResultCode;
import com.example.seckill.infra.cache.RateLimitResult;
import com.example.seckill.infra.cache.RateLimitService;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import tools.jackson.databind.ObjectMapper;

import java.io.IOException;

/**
 * 抢课接口限流。
 * <p>
 * 挂载方式见 SecurityConfig：addFilterAfter(rateLimitFilter, JwtAuthenticationFilter.class)。
 * ⚠️ 必须放在 JWT 之后，否则 SecurityContext 是空的，拿不到 studentId，
 * 所有请求会被当成同一个匿名桶 —— 而且不会报错。
 * <p>
 * 只拦 POST /api/seckill/{courseId}（真正的抢课动作），
 * 不拦 cancel、不拦查询接口、不拦静态资源。
 */
@Slf4j
@Component
public class RateLimitFilter extends OncePerRequestFilter {

    private static final String GLOBAL_KEY = "seckill:rate:global";
    private static final String STUDENT_KEY_PREFIX = "seckill:rate:student:";

    private final RateLimitService rateLimitService;
    private final ObjectMapper objectMapper;

    private final boolean enabled;
    private final int globalCapacity;
    private final double globalRefill;
    private final int studentCapacity;
    private final double studentRefill;

    public RateLimitFilter(RateLimitService rateLimitService,
                           ObjectMapper objectMapper,
                           @Value("${seckill.rate-limit-enabled:true}") boolean enabled,
                           @Value("${seckill.rate-limit-global-capacity:2000}") int globalCapacity,
                           @Value("${seckill.rate-limit-global-refill-per-second:1500}") double globalRefill,
                           @Value("${seckill.rate-limit-student-capacity:5}") int studentCapacity,
                           @Value("${seckill.rate-limit-student-refill-per-second:1}") double studentRefill) {
        this.rateLimitService = rateLimitService;
        this.objectMapper = objectMapper;
        this.enabled = enabled;
        this.globalCapacity = globalCapacity;
        this.globalRefill = globalRefill;
        this.studentCapacity = studentCapacity;
        this.studentRefill = studentRefill;
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        if (!enabled) {
            return true;
        }
        // 只拦抢课本身：POST /api/seckill/{courseId}
        // 用精确匹配而不是 startsWith("/api/seckill")，否则 cancel 也会被限流
        if (!"POST".equalsIgnoreCase(request.getMethod())) {
            return true;
        }
        String uri = request.getRequestURI();
        return !uri.startsWith("/api/seckill/") || uri.endsWith("/cancel");
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {

        // 第一层：全局桶
        RateLimitResult global = rateLimitService.tryAcquire(
                GLOBAL_KEY, globalCapacity, globalRefill, 1);
        if (global.degraded()) {
            log.error("全局限流降级，本次请求放行（限流未生效） uri={}", request.getRequestURI());
        }
        if (!global.allowed()) {
            reject(response, global, "系统繁忙，请稍后重试");
            return;
        }

        // 第二层：每学生桶（匿名请求跳过 —— 它已经被全局桶挡住了）
        Long studentId = currentStudentId();
        if (studentId != null) {
            RateLimitResult student = rateLimitService.tryAcquire(
                    STUDENT_KEY_PREFIX + studentId, studentCapacity, studentRefill, 1);
            if (!student.allowed()) {
                // 注意：这里已经消耗了一个全局令牌。这是有意的 ——
                // 被学生桶拒掉的请求确实占用了系统资源（解析 JWT、查 Redis），
                // 不退还才符合"限流保护系统"的初衷。
                reject(response, student, "操作过于频繁，请稍后再试");
                return;
            }
        }

        filterChain.doFilter(request, response);
    }

    private Long currentStudentId() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth == null || !(auth.getPrincipal() instanceof Long id)) {
            return null;
        }
        boolean isStudent = auth.getAuthorities().stream()
                .anyMatch(a -> "ROLE_STUDENT".equals(a.getAuthority()));
        return isStudent ? id : null;
    }

    private void reject(HttpServletResponse response, RateLimitResult result, String message)
            throws IOException {
        long retryAfterSeconds = Math.max(1L, (result.retryAfterMs() + 999L) / 1000L);
        response.setStatus(ResultCode.TOO_MANY_REQUESTS);
        response.setContentType("application/json;charset=UTF-8");
        // RFC 9110：Retry-After 用秒（整数）
        response.setHeader("Retry-After", String.valueOf(retryAfterSeconds));
        response.setHeader("X-RateLimit-Remaining", String.valueOf(Math.max(0L, result.remaining())));
        objectMapper.writeValue(response.getWriter(),
                Result.error(ResultCode.TOO_MANY_REQUESTS, message));
        log.warn("限流拒绝 uri={} retryAfter={}s remaining={}",
                message, retryAfterSeconds, result.remaining());
    }
}
```

## 8. 任务 E：压测脚本改造

### 8.1 为什么必须改

`loadtest/seckill-v3.js` 现在这样分类：

```javascript
else if (res.status === 429) { biz_throttled.add(1); throttled_latency.add(res.timings.duration); }
else if (res.status === 409) {
  if (String(res.body).includes('名额已满')) biz_sold_out.add(1);
  else biz_duplicate.add(1);
} else biz_rejected.add(1);
```

> `throttled_latency` 这个指标很有用：429 的响应时间应该**远低于**成功请求（因为它没进业务逻辑），这本身就是「限流把负载挡在门外」的证据。

## 9. 对比实验（本阶段的全部价值在这里）

### 9.1 必须诚实面对的一个限制

**这台压测机可能打不出足够高的负载来演示「硬崩」。** 之前 v4 阶段实测过：k6 的 `maxVUs` 超过学生池会伪造瓶颈，而学生池只有 10000 个、实际可用 900~2400。2000 RPS 以上 `dropped_iterations` 暴涨，压不上去。

所以「把系统打到崩」这件事可能做不到。**这不影响本阶段的价值，但要换一种证明方式**：

- 不证明「限流把崩溃变成了 429」
- 而证明「**限流阈值生效，超出部分被挡在业务逻辑之外，且成功部分的延迟不受影响**」

这两件事用较低负载就能证明，而且是同一个机制。

### 9.2 三组实验

每组前都要复位（`loadtest/reset-v3.ps1`），且**关掉对账**（`--seckill.reconcile-enable=false`），否则对账任务的 Redis 往返会污染数据。

| 组 | 限流配置 | 负载 | 期望看到 |
|---|---|---|---|
| **基线** | `rate-limit-enabled=false` | 1200 RPS | P95 ≈ 20 ms，零 429。**这是参照物** |
| **A 不误伤** | 全局 1500/s，学生 1/s | 1200 RPS | 几乎零 429，P95 与基线差 **< 20 ms**。证明限流器本身开销可接受 |
| **B 生效** | 全局 **300/s**，学生 1/s | 1600 RPS | 约 **80% 拿到 429**，成功部分 P95 稳定，`throttled_latency` 远低于成功延迟，**系统不崩** |

**组 B 为什么要故意把阈值调到 300？** 因为 1600 RPS 是这台机器能稳定打出的上限，把限流设成 1500 的话几乎不会有 429，看不出效果。**把阈值调低是为了在有限压测能力下演示机制** —— 这一点必须在报告里写清楚，不能让人误以为「系统只能扛 300 RPS」。

### 9.3 要采集的数字

每组记录：

| 指标 | 从哪来 |
|---|---|
| `biz_queued` / `biz_throttled` / `biz_sold_out` / `biz_rejected` | k6 summary |
| `http_req_duration` 的 p50/p95/p99 | k6 summary |
| `throttled_latency` 的 p95 | k6 summary |
| 实际卖出的单数 | `SELECT COUNT(*) FROM seckill_order WHERE course_id=88` |
| Redis 库存 | `GET seckill:stock:88` |
| JVM CPU / GC | `loadtest/jvm-probe.ps1`（可选） |

**必须核对账目**：无论 429 多少，最终 `stock + sold = capacity` 且 `orders = success` 必须成立。限流不能破坏这个不变式。

### 9.4 报告要写成什么样

新建 `docs/压测报告-限流.md`，结构参考 `docs/压测报告-v3.md`。核心是一张三组对比表 + 一段「为什么限流器开销只有 X ms」的分析。

**结论必须是数据推出来的，不是「限流很重要」这种空话。**

## 12. 明确不做

| 不做 | 理由 |
|---|---|
| 每课程限流 | 每门课的竞争由 Redis 库存门禁处理，再加一层是重复劳动 |
| 基于 IP 限流 | 校园网/公司出口 NAT 后大量学生共用一个 IP，会误伤。而且本项目是登录制，学生维度更准 |
| 动态调整阈值（自适应限流） | 需要实时采集系统负载并反馈，属于另一个量级的工作。固定阈值 + 可配置已经够用 |
| 限流降级到本地令牌桶 | fail-open 已经是降级方案；再加一层本地桶会让「限流到底有没有生效」变得无法判断 |
| 排队（超限不是拒绝而是等待） | 需要额外的队列 + 长连接/轮询，与「秒杀」语义冲突（用户不会等 30 秒） |
| 引入 bucket4j / Sentinel | 见 §2.2 |

## 14. 做完能得到什么

### 面试可讲的三件事

**① 「限流器放在哪一层」不是一个随便的选择**

> 「一开始我想用 AOP 切 Service 方法，后来意识到那太晚了 —— 请求已经进了 Tomcat 线程池，过载时线程先被打满，限流器还没机会执行。必须放在 Servlet Filter，在占用业务线程之前就拒绝。」

**② 一个静默失败的 bug：`setResultType(Long.class)`**

> 「脚本返回 3 个值，我用 `Long.class` 接。Spring Data Redis 不报错，只取最后一个元素 —— 而最后那个是『建议重试毫秒数』，放行时是 0、拒绝时是正数。结果就是：**该放行的被当成拒绝，该拒绝的被当成放行**，限流器完全反向工作，日志里一行异常都没有。我第一次用 `{5,7,9}` 这种探针脚本才发现取的是最后一个元素。这种 bug 单测永远测不到，因为 Redis 被 mock 掉了。」

**③ fail-open 是一个有意的设计决策，不是偷懒**

> 「限流是保护性设施，不是正确性设施。Redis 挂了的时候，正确行为是降级到无保护继续跑，而不是把全站拒掉。因为抢课链路本来就依赖 Redis，它挂了业务自己会返回 500，再叠一个 429 没有增加任何价值。」

### 这一阶段补上了什么

README 已知局限第 4 条原文是「**没有限流。1600 RPS 以上是硬崩，不是优雅降级。**」

做完这一阶段，这句话可以划掉，换成一组实测数字。**这是整个项目里第一个「主动保护自己」的机制** —— 前面的 v1~v3 都是在提高「能扛多少」，这一阶段是第一次处理「扛不住的时候怎么办」。
