# 压测报告 v1：数据库层并发控制

> 项目：seckill-course 高并发选课引擎
> 阶段：阶段 3（v1-db-lock）
> 日期：2026-11-13
> 被测版本：v0-baseline、v1-optimistic、v1-pessimistic、v1-version-cas（共 4 个）

---

## 1. 这份报告要回答什么问题

v0 已经证明了超卖会发生（300 并发超卖 200%，详见 `docs/压测报告.md`）。
这一阶段用三种不同的数据库手段去修它，要回答的是四个问题：

1. **三种手段都能做到"零超卖"吗？** —— 能不能修好
2. **代价分别是什么？** —— 吞吐、延迟、代码复杂度
3. **哪个最快？** —— 这个答案反直觉，见 §5.1
4. **为什么版本号 CAS 需要重试 30 次？** —— 这个答案更重要，见 §5.2

**判定口径与 v0 保持一致**（`docs/压测报告.md` §4.4），只看两个硬指标：

- `success_orders`（`status=1` 的订单数）是否 ≤ `capacity`
- `stock + sold == capacity` 是否成立

补充第三个只有 CAS 才有的指标：`version` 是否等于 `success_orders`。

## 4. 结果总表

压测场景统一为：**课程 88，`capacity=100`，300 VU × 300 名学生，每人抢 1 次**。
数据每轮前用 `loadtest/reset.ps1` 复位（`stock=capacity, sold=0, version=0`，订单表 TRUNCATE）。

### 4.1 主表

| 版本 | 成功单 | 名额满(409) | 其它失败 | 超卖 | 守恒 | `stock` | `sold` | avg | P95 | P99 |
|---|---|---|---|---|---|---|---|---|---|---|
| **v0-baseline** | **300** | 0 | 0 | **+200** | ❌ 396≠100 | 96 | 300 | 211 ms | 572 ms | 615 ms |
| **v1-optimistic** | **100** | 200 | 0 | **0** | ✅ 100 | 0 | 100 | — | **339 ms** | **344 ms** |
| **v1-pessimistic** | **100** | 200 | 0 | **0** | ✅ 100 | 0 | 100 | — | **397 ms** | **406 ms** |
| **v1-version-cas** | **100** | 200 | 0~39 | **0** | ✅ 100 | 0 | 100 | 409~523 ms | **1.08~1.23 s** | **1.09~1.24 s** |

> v0 的"成功单 300"是超卖的另一种表述：100 个名额卖出了 300 份。
> v1-version-cas 的延迟取三轮范围，明细见 §4.3。

### 4.2 串行对照组（关键）

单线程 1 VU 顺序请求 110 次（v0 版本）：

| 指标 | 值 |
|---|---|
| 成功单 | **100** |
| 名额满 | 10 |
| 超卖 | **0** |
| 守恒 | ✅ 100 |

**这一组排除了三种错误归因**：代码逻辑没错、种子数据没问题、压测工具没造假。
v0 在 1 并发下完全正确，唯一变量就是并发本身。

### 4.3 v1-version-cas 三轮明细（`MAX_ATTEMPTS=30`）

| 轮次 | 成功单 | 其它失败 | avg | P95 | P99 | `version` | 成功单 |
|---|---|---|---|---|---|---|---|
| 1 | **100** | 7 | 523 ms | 1.23 s | 1.24 s | 100 | 100 |
| 2 | **100** | 39 | 409 ms | 1.08 s | 1.09 s | 100 | 100 |
| 3 | **100** | 0 | 490 ms | 1.12 s | 1.12 s | 100 | 100 |

`version` 每轮都恰好等于成功单数（100），说明 CAS 的每次成功都真实推进了一次版本号，
不存在"CAS 返回 1 但其实没改数据"的情况。

**`biz_other` 的零星残留（7 / 39 / 0）是真实存在的尾部损耗**，不是 bug：
300 个请求挤在 30 次重试窗口里，极少数没排上。想彻底归零只能继续加大重试次数，
代价是 P99 继续往上顶（见 §5.3）。

## 5. 三个反直觉的发现

### 5.1 加锁之后反而更快了

| 版本 | P95 | 说明 |
|---|---|---|
| v0（无保护） | 572 ms | 300 个请求全部走完完整流程 |
| v1-optimistic | **339 ms** | 200 个请求在第一条 UPDATE 就被挡回 |

v0 要卖 300 单，v1 只卖 100 单。**失败的 200 个请求在扣库存那一步就 409 返回了，
根本没走到查重和 `INSERT`**——干的活少了 2/3，当然更快。

这不是"加了锁所以更快"，而是**"正确的系统工作量更小"**。
拿 v1 的 339 ms 去和 v0 的 572 ms 比"性能提升"，是错的比法。

真正可比的对照是 §5.2 里同为空转的 CAS：同一份工作量下，乐观锁 339 ms，
悲观锁 397 ms，CAS 1.1 s。

### 5.2 版本号 CAS 在 REPEATABLE-READ 下会"假重试"

这是本阶段最重要的一次踩坑，值得完整记录。

**现象**：CAS 版本 300 并发只成功 18 单，282 个返回「系统繁忙，请重试」，账目守恒、
日志零异常。把重试次数从 3 提到 30 后变成 97 单（100 VU）/ 100 单（300 VU）。

**第一层原因（已修）：重试和事务的边界没对齐。**

最初的写法是**一个事务里重试 3 次**：

```java
@Transactional                        // ← 事务开始，MySQL 此刻为它拍了快照
public SeckillResponse seckill(...) {
    for (int i = 0; i < 3; i++) {
        CourseStock s = selectByCourseId(courseId);   // 每次都读同一个快照
        if (casDecrement(courseId, s.getVersion()) == 1) break;
    }
}
```

两个真实会话对照（实测，非推测）：

| 时刻 | 会话 A | 会话 B | A 读到 |
|---|---|---|---|
| 1 | `SELECT stock, version` | | `100, 0` |
| 2 | | `UPDATE SET version=1` | |
| 3 | **同一事务内**再 `SELECT` | | **`100, 0`** ❌ 旧值 |
| 4 | 改成 `SELECT ... FOR UPDATE`（当前读） | | `99, 1` ✅ |

REPEATABLE-READ 保证**同一事务内多次读看到一致的数据**，所以第 2、3 次重试拿到的
`version` 永远是 0，`casDecrement(courseId, 0)` 每次都失败——**三次重试等于用同一个
过期答案交三次卷**。

**对照实验证明业务逻辑本身是对的**：把隔离级别临时切成 `READ-COMMITTED`（每次读拿
最新已提交版本），同一份代码、同样 300 VU 立刻变成 100 单 / 0 超卖 / 缺口 0。

**修法**：外层循环无事务，每次重试开一个新事务（`TransactionTemplate`）：

```java
public SeckillResponse seckill(Long courseId) {          // ← 去掉 @Transactional
    for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
        SeckillResponse r = transactionTemplate.execute(st -> tryOnce(courseId, studentId));
        if (r != null) return r;                          // 抢到了
        sleepQuietly(RETRY_BACKOFF_MS);                   // 5~9ms 随机退避
    }
    throw new BusinessException(ResultCode.CONFLICT, "系统繁忙，请重试");
}
```

内层 `tryOnce` 的返回约定：**只有「版本冲突」返回 `null` 让外层重试**；
「名额已满」「已选过」必须原样抛异常，否则 200 个注定失败的请求会各跑 30 次，
数据库白挨 6000 次查询。

> ⚠️ 外层 `@Transactional` 一定要删。不删的话 `transactionTemplate` 会加入外层事务
> （默认 `PROPAGATION_REQUIRED`），还是同一个快照，**改完症状一模一样**。

**第二层原因（设计层面）：每一"波"只产生一个赢家。**

修好事务边界后，100 并发仍然只出 11 单。机理：

```
100 个请求同时读到 version=0
  → CAS 只有一个能成功（其余 99 个版本号已过期）
  → 99 个重试，又几乎同时读到 version=1
  → 又只有一个成功
  → …
```

**每一波只出一个赢家。** 3 次重试 ≈ 最多几单，实测 11 单靠的是 5~9 ms 随机退避
把线程稍微错开了。这解释了为什么 READ-COMMITTED 下能出 100 单——RC 每次重试都能
读到别人刚提交的新版本，等价于"每次重试都是新的一波"。但它只是**掩盖**了问题。

### 5.3 重试次数与成功率的实测关系

| 并发 | 重试次数 | 成功单 | 其它失败 | avg | P95 |
|---|---|---|---|---|---|
| 100 | 3 | **11** | 89 | 65 ms | 82 ms |
| 100 | 30 | **97** | 3 | 222 ms | 573 ms |
| 300 | 30 | **100** | 0~39 | 409~523 ms | 1.08~1.23 s |

单调关系成立，**证明"重试次数"这个变量确实在起作用**，也证明 CAS 逻辑本身没错。

代价同样清楚：重试 30 次时 P95 从 82 ms 涨到 1.1 s 以上。这就是任务书 §6.3 预测的
**重试风暴**——300 并发抢 100 个名额，200 个注定失败的请求每失败一次都要重来。

`MAX_ATTEMPTS = 30` 是为跑通验证设的值，不是"作者原本就这么写"。
真实系统不会靠调大重试次数解决这个问题，而是在前面加限流或 Redis 预扣（v2 要做的事）。

## 6. v1 修复的两个 bug 复盘

### 6.1 悲观锁重复扣减（每个成功请求扣 2 个名额）

**现象**：单次抢课返回 200、订单 1 条，但 `stock=98 sold=2`。
300 VU 时 `biz_success=50`——100 个名额只卖出 50 个。

**根因**：`selectForUpdate` 之后既调了 `absoluteUpdate` 又调了 `tryDecrement`：

```java
CourseStock s = courseStockMapper.selectForUpdate(courseId);   // 扣第 1 次
courseStockMapper.absoluteUpdate(courseId, s.getStock() - 1);
courseStockMapper.tryDecrement(courseId);                       // 扣第 2 次 ← 多余
```

**为什么极难发现**：无异常、无 ERROR 日志、HTTP 全 200/409、`stock + sold = 100`
完美守恒。只有把「成功单数」和「capacity」对比才暴露出来：

```
stock+sold=100 ✅ 守恒    但     success_orders=50 ≠ capacity=100 ❌
```

**结论：守恒证明不了正确性。** 守恒只说明没凭空多出/丢失库存，
不等于每个名额都被用上了。判定必须同时看 `success_orders` vs `capacity`。

### 6.2 `casDecrement` 的 SQL 被复位语句覆盖

```java
// 错：把 loadtest/reset.ps1 里的语句粘进了 mapper
@Update("UPDATE seckill.course_stock SET stock = capacity, sold = 0, version = 0 WHERE course_id = $CourseId;")
```

两个错误叠加：`$CourseId` 是 PowerShell 变量（MyBatis 要 `#{courseId}`），
且整条语句根本不该是复位语句。表现为每次抢课 500，日志：

```
java.sql.SQLSyntaxErrorException: Unknown column '$CourseId' in 'where clause'
### The error may involve com.example.seckill.mapper.CourseStockMapper.casDecrement-Inline
```

正确版本：

```java
@Update("UPDATE course_stock SET stock = stock - 1, sold = sold + 1, version = version + 1 " +
        "WHERE course_id = #{courseId} AND version = #{version} AND stock > 0")
int casDecrement(@Param("courseId") Long courseId, @Param("version") Integer version);
```

### 6.3 另外两处编译错误

| 报错 | 原因 |
|---|---|
| `找不到符号: transactionTemplate` | 声明了使用但没声明字段，也没 import `TransactionTemplate` |
| `不兼容的类型: long 无法转换为 java.time.Duration` | `import static org.apache.commons.lang3.ThreadUtils.sleepQuietly;` 抢走了同名调用，该方法签名为 `(Duration)` |

第二处特别隐蔽：**commons-lang3 里有一个同名的 `sleepQuietly(Duration)`**，
静态导入会让自己的 `sleepQuietly(long)` 悄无声息地失效。

## 7. 三个版本的正确性验证（不只跑压测）

### 7.1 幂等：同一学生 10 个并发（`v1-version-cas`）

| 结果 | 数量 |
|---|---|
| `200 操作成功` | **1** |
| `409 你已选过该课程` | **9** |

数据：`stock=99 sold=1 version=1`，订单 **1** 条。

这条验证的是**事务回滚**：9 个失败请求扣掉的库存必须自动还回来。
如果没有 `@Transactional`，这里会变成 `stock=90`（扣 10 次）。

### 7.2 单次抢课（`v1-version-cas`）

```
抢课      → 200  {"orderNo":"179454573070300017893","status":1}
重复抢    → 409  "你已选过该课程"
数据库    → stock=99 sold=1 version=1 守恒=100
订单      → 1 条
```

`version=1` 是 CAS 特有的额外校验：另两个实现没有这个字段可看。

## 8. 结论

### 8.1 四个版本对比

| 维度 | v0 | v1-optimistic | v1-pessimistic | v1-version-cas |
|---|---|---|---|---|
| 零超卖 | ❌ +200 | ✅ | ✅ | ✅ |
| 名额用满 100 | ❌ 只是超卖 | ✅ 100 | ✅ 100 | ✅ 100 |
| 守恒 | ❌ | ✅ | ✅ | ✅ |
| P95 | 572 ms | **339 ms** | 397 ms | 1.1 s |
| 代码行数 | 115 | **112** | 118 | **140** |
| 需要重试 | — | 否 | 否 | **是（30 次）** |
| 需要事务 | 否 | 是（回滚） | **是（必须）** | 是（每次尝试） |
| 额外字段 | — | 无 | 无 | `version` |

### 8.2 选型建议

**本项目的默认选择：`v1-optimistic`（条件更新）。**

理由按权重排：

1. **代码最短（112 行）**，比 v0 还少 3 行——因为它只是把"读出来改再写回"换成了一条
   带条件的 SQL，没有引入循环、锁、版本号
2. **P95 最低（339 ms）**
3. **不需要重试**，没有重试风暴
4. **对业务侵入最小**：`WHERE stock > 0` 这个条件本身就是"库存足够"这个业务规则

**什么时候该用悲观锁**：临界区里有**多条**需要原子性的写操作时。本场景只有一条
UPDATE，用 `FOR UPDATE` 是拿串行化成本换一个不需要的保证。

**什么时候该用版本号 CAS**：更新的**新值依赖读到的旧值**（比如"库存 > 100 就打八折"），
条件更新表达不了这种逻辑。本场景不需要，所以 CAS 在这里是**过度设计**——
代价是代码 +28 行、P95 ×3.3、必须调重试次数。

**这一版真正的收获不是"选出最快的"，而是看清了三种手段各自的成本结构。**

### 8.3 面试可以直接讲的三句话

1. **「乐观锁的重试边界必须和事务边界对齐。」** 事务内重试会读到冻结的快照，
   重试拿到的是过期版本号。这不是 MySQL 的 bug，是 MVCC 的设计要求。
2. **「账目守恒不等于正确。」** 悲观锁那版 `stock+sold=100` 完美守恒，却只服务了
   50 个人。必须同时看「成功单数 vs 容量」。
3. **「乐观锁在高竞争下会退化成重试风暴。」** 300 并发抢 100 名额，200 个注定失败
   的请求各重试 30 次。所以真实系统里乐观锁前面通常还有一层限流或 Redis 预扣。

## 9. 已知局限

1. **压测时可用内存仅 0.31 GB**（总 15.61 GB）。上表里 CAS 三轮之间的波动
   （409 / 523 / 490 ms）可能有内存换页的影响。绝对值仅供参考，
   **四版之间的相对关系是可用的**（同一台机器、同一时段、同样场景）。
2. **单机、单实例**。没有测多实例部署下的表现——这也是为什么本阶段不考虑分布式锁。
3. **每版只跑了 1~3 轮**，没有做统计学意义上的重复实验（比如每版 10 轮取中位数）。
4. **`biz_other` 的残留未完全归零**（CAS 有 7 / 39 / 0）。它的存在是真实的，
   没有通过"多跑几轮挑个好数字"的方式掩盖。
5. **未测长稳压测**（比如 10 分钟持续 300 并发）。本轮都是 300 个请求的一次性突发。

判定 SQL（`verify.ps1` 内部就是这两条）：

```sql
-- 守恒与库存
SELECT stock, sold, version, capacity, stock + sold AS total
FROM seckill.course_stock WHERE course_id = 88;

-- 成功单数 vs 容量（这一条才是真正的判定）
SELECT COUNT(*) AS success_orders FROM seckill.seckill_order
WHERE course_id = 88 AND status = 1;
```

**四条判据**：

| # | 条件 | 含义 |
|---|---|---|
| 1 | `success_orders <= capacity` | 没超卖 |
| 2 | `stock + sold = capacity` | 账目守恒 |
| 3 | `success_orders = capacity` | **名额被用满**（这一条最容易被忽略） |
| 4 | `version = success_orders`（仅 CAS） | 版本推进次数对得上 |

## 11. 下一步：v2-redis-lua

这一阶段留下的问题，正好是 v2 的靶子：

| 本阶段的局限 | v2 怎么解决 |
|---|---|
| 大量请求打到 MySQL 才被拒（300 个请求 → 300 次 UPDATE） | Redis 预扣，内存里先挡掉 200 个 |
| CAS 靠重试，退化成重试风暴 | Lua 脚本原子扣减，一次成功或一次失败，**不需要重试** |
| P95 1.1 s 的尾部延迟 | Redis 操作在微秒级 |

v2 的验收标准（写进下一份任务书时细化）：

- 300 并发下 P95 **低于 v1-optimistic 的 339 ms**
- 依然 100 单、0 超卖、守恒
- 出现"Redis 扣了但 MySQL 没扣"的不一致时，有补偿机制并**能被验证到**
