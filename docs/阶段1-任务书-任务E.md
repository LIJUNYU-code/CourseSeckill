## 0. 为什么先写测试，再补 Swagger

一句话：**测试验证逻辑对不对，Swagger 只是给人看的说明书。**
先确认逻辑正确，说明书才有意义；反过来，一个描述得再漂亮的接口文档，如果背后的代码是错的，它只是把错误传播得更规范。

更实际的理由：你反复说过目标是「能拿得出手的项目」。**有测试的项目和没测试的项目，在面试官眼里是两个物种**——前者说明你懂"改完还要验证没改坏"，后者说明你只会写能跑的一次性代码。

## 2. 要测什么：`CourseServiceImpl` 的三个分支

看你现在的方法，它有**三条互斥的执行路径**：

```java
public CourseDetailResponse getCourseDetail(Long courseId) {
    Course course = courseMapper.selectById(courseId);
    if (course == null) {
        throw new BusinessException(ResultCode.NOT_FOUND, "课程不存在");   // ← 分支 A
    }
    CourseStock courseStock = courseStockMapper.selectOne(...);
    if (courseStock == null) {
        log.warn(...);
        courseStock = CourseStock.builder().courseId(courseId)
                .capacity(0).stock(0).sold(0).build();                    // ← 分支 B
    }
    return CourseDetailResponse.builder()...build();                      // ← 分支 C
}
```

**分支覆盖率 = 测试质量。** 三个分支 → 三个测试用例。这是最朴素的「一个分支一个用例」原则，也是最有性价比的做法：

| 用例 | 输入 | 期望 | 覆盖分支 |
|---|---|---|---|
| `getCourseDetail_notFound_throws404` | 课程不存在 | 抛 `BusinessException`，`getCode()==404` | A |
| `getCourseDetail_stockMissing_returnsZeroStock` | 课程存在，库存行缺失 | 返回对象 `capacity=0` / `stock=0` / `sold=0`，且课程信息正常 | B |
| `getCourseDetail_success_assemblesAllFields` | 两张表都正常 | 9 个字段全部正确映射 | C |

**为什么不用真数据库？** 三个理由：
1. **快**：Mockito 打桩，单测跑完 ~100ms，不用启动 Spring、不连 MySQL；
2. **稳**：不依赖"数据库里恰好有课程 1"这种外部状态，随时能跑；
3. **能测到异常路径**：真库里很难造出"课程存在但库存缺失"的数据——而这恰恰是你写的防御性代码，必须验证它真的生效。

这叫**单元测试**（只测这一个类的逻辑，把外部依赖换成假的）。等阶段 4 有了真实并发场景，再写**集成测试**（连真库真 Redis）——两者不是替代关系。

## 4. 断言怎么写（教你方法，不直接给答案）

### 4.1 分支 A：验证"抛了正确的异常"

```java
assertThatThrownBy(() -> courseService.getCourseDetail(99999L))
        .isInstanceOf(BusinessException.class)
        .satisfies(e -> assertThat(((BusinessException) e).getCode())
                .isEqualTo(ResultCode.NOT_FOUND))
        .hasMessage("课程不存在");
```

**三个断言各管一件事**：
- `isInstanceOf` —— 抛的是不是对的异常类型（不是 NullPointerException 之类的意外）；
- `satisfies(...)` —— 异常里的 code 对不对（这是 `GlobalExceptionHandler` 拿来翻译 HTTP 状态的依据，错了接口就返回错误的 HTTP 码）；
- `hasMessage` —— 提示语对不对。

**为什么要断言 code 而不只断言异常类型？** 因为 `BusinessException` 是通用的，404 和 409 都用它。只断言 `isInstanceOf` 的话，即使代码把 404 写成了 409，测试照样绿——**测试就失去意义了**。

### 4.2 分支 B：验证"不抛异常 + 降级数据正确"

```java
CourseDetailResponse result = courseService.getCourseDetail(1L);

// 库存缺失时全部降级为 0
assertThat(result.getCapacity()).isZero();
assertThat(result.getStock()).isZero();
assertThat(result.getSold()).isZero();

// 但课程本体信息不能受影响
assertThat(result.getCourseId()).isEqualTo(1L);
assertThat(result.getCourseName()).isEqualTo("课程1");
assertThat(result.getTeacher()).isEqualTo("教师1");
```

**这里最容易漏的一点**：很多人只测了"没抛异常"，没测降级后的数据。但你这个分支的价值恰恰在于**返回可用的降级数据**（全 0），如果实现里写成 `capacity(null).stock(null)`，测试只断言"没抛异常"就会漏掉，前端拿到 `null` 一样会崩。

`assertThat(...).isZero()` 是 AssertJ 的方法，比 `isEqualTo(0)` 更好：它明确表达"我期望这个数是零"，而且当实际值是 `null` 时报错信息更清楚（`isEqualTo(0)` 遇到 `Integer` 为 null 时会报一个含糊的失败）。

### 4.3 分支 C：验证"9 个字段全对"

```java
CourseDetailResponse result = courseService.getCourseDetail(7L);

assertThat(result.getCourseId()).isEqualTo(7L);
assertThat(result.getCourseName()).isEqualTo("课程7");
assertThat(result.getTeacher()).isEqualTo("教师7");
assertThat(result.getCredit()).isEqualByComparingTo("3.5");   // ← BigDecimal 要用这个
assertThat(result.getStartTime()).isEqualTo(LocalDateTime.of(2026, 11, 5, 16, 50, 28));
assertThat(result.getEndTime()).isEqualTo(LocalDateTime.of(2027, 11, 6, 16, 50, 28));
assertThat(result.getCapacity()).isEqualTo(100);
assertThat(result.getStock()).isEqualTo(63);
assertThat(result.getSold()).isEqualTo(37);

// 守恒规则：剩余 + 已售 = 总名额（文档 §2 R3）
assertThat(result.getStock() + result.getSold()).isEqualTo(result.getCapacity());
```

**两个坑，现在说清楚**：

1. **`BigDecimal` 不要用 `isEqualTo`**。`new BigDecimal("3.5")` 和 `new BigDecimal("3.50")` 用 `equals()` 比较是**不相等**的（`equals` 会比较 scale），而 `compareTo` 忽略 scale。所以断言小数永远用 `isEqualByComparingTo("3.5")`。这是个极常见的坑——你的 `credit` 字段是 `decimal(3,1)`，从数据库读出来就是 `2.5` / `3.0` / `3.5`，恰好不会踩到，但以后算平均分、乘法时就一定会撞上。

2. **`assertThat(result.getStock() + result.getSold())`** 这里 `getStock()` 返回 `Integer`，相加会自动拆箱成 `int`，如果任一为 `null` 会抛 NPE。在分支 C 里不会（我们打桩返回了非 null），但要知道这个写法有前提。

### 4.4 关于 `when(...)` 的匹配

分支 B 和 C 里用的是 `when(courseStockMapper.selectOne(any()))`——`any()` 匹配任何参数。

**为什么不用 `when(courseStockMapper.selectOne(具体的 wrapper))`？** 因为 `LambdaQueryWrapper` 没有重写 `equals`，两次 `new` 出来的对象永远不相等，`when` 就永远匹配不上，会返回默认值 `null`。**这是 Mockito 测试 lambda wrapper 时的标准做法：用 `any()`。**

严谨一点可以用 `any(LambdaQueryWrapper.class)` 或 `ArgumentMatchers.<LambdaQueryWrapper<CourseStock>>any()`，消除泛型警告。不过 `any()` 能跑通，不强制。

## 5. 🔴 一个必踩的坑：`can not find lambda cache`

**如果你不写 `@BeforeAll initTableInfo()`，三个测试里分支 B 和 C 会全部失败**，报：

```
com.baomidou.mybatisplus.core.exceptions.MybatisPlusException:
  can not find lambda cache for this entity [com.example.seckill.entity.CourseStock]
```

**为什么**：`LambdaQueryWrapper.eq(CourseStock::getCourseId, ...)` 要在执行时把 `getCourseId()` 这个方法引用翻译成数据库列名 `course_id`。翻译依赖 MyBatis-Plus 内部的 `TableInfo` —— 一个**全 JVM 共享的静态缓存**，正常由 Spring 启动时扫描实体填充。

纯 Mockito 单测没有 Spring 上下文 → 缓存是空的 → 翻译失败 → 抛异常。

**为什么这个坑在项目一被反复踩**：因为它有**执行顺序依赖**。如果同一个 JVM 里先跑了 `@SpringBootTest`（会启动 Spring、填好缓存），后面的单测就"搭便车"通过了；单独跑这个测试类就挂。在 CI 上 surefire 的执行顺序不同 → **本地绿、CI 红**。项目一那次排查了很久，根因就是这个。

所以：**`@BeforeAll` 显式注册，永远不依赖执行顺序。** 这段代码看着像模板，但它是用血换来的。

## 7. 🔬 反向验证（这一步最重要，别跳过）

测试写完第一次就全绿，**先别高兴**——可能是断言写松了（比如啥都没断言）。用这个方法验证测试真有牙齿：

**步骤一**：临时把 `CourseServiceImpl` 里分支 A 的 `ResultCode.NOT_FOUND` 改成 `ResultCode.CONFLICT`。
**步骤二**：跑测试，**分支 A 必须失败**。
**步骤三**：改回来，重跑，全绿。

如果改错了代码测试还是绿的，说明你的断言根本没有检查到这个点——**这种测试比没有测试更危险**，因为它给你虚假的安全感。

同理可以再验证一次分支 B：把 `.capacity(0)` 改成 `.capacity(999)`，测试必须失败。

**这个「改坏代码 → 看测试是否变红 → 改回来」的手法叫变异测试（mutation testing）的心智模型**，是最便宜的测试质量检查。以后每写一批测试，至少抽一个点做一次。

## 8. Swagger 补全（20 分钟）

### 8.1 `CourseController`：`@Tag` 移到类上，改名

你现在的 `@Tag` 挂在方法上（第 24 行）。改成挂在类上——理由：以后 `CourseController` 会加新建/删除接口，它们应该自动归到同一分组，而不是各自带一个 `@Tag`。

```java
@RestController
@RequestMapping("/api/course")
@AllArgsConstructor
@Tag(name = "课程管理", description = "课程详情与剩余名额")
public class CourseController {

    private CourseService courseService;

    @GetMapping("/{courseId}")
    @Operation(summary = "查询课程详情", description = "返回课程基本信息与库存；课程不存在返回 404")
    public Result<CourseDetailResponse> getCourseDetail(@PathVariable Long courseId) {
        return Result.success(courseService.getCourseDetail(courseId));
    }
}
```

注意 `@Tag` 的 name 从「课程查询」改成「**课程管理**」——因为这个 Controller 未来会容纳写操作，名字宽一点才不用改。

### 8.2 `AuthController`：加 `@Tag` + `@SecurityRequirements`

现在它什么 Swagger 注解都没有（我实测确认）。补上：

```java
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.security.SecurityRequirements;
import io.swagger.v3.oas.annotations.tags.Tag;

@RestController
@RequestMapping("/api/auth")
@AllArgsConstructor
@Tag(name = "账号认证", description = "登录与令牌签发")
public class AuthController {

    private final AuthService authService;

    @PostMapping("/login")
    @Operation(summary = "登录", description = "支持管理员（sys_user）与学生（student）两类账号；成功后返回 JWT 令牌")
    @SecurityRequirements          // ← 关键：告诉 Swagger 这个接口不需要 token
    public Result<LoginResponseDTO> login(@Valid @RequestBody LoginRequestDTO loginRequestDTO) {
        return Result.success(authService.login(loginRequestDTO));
    }
}
```

**`@SecurityRequirements` 为什么重要**：如果你的项目在 `OpenApiConfig` 里配了全局的 `bearerAuth`（你现在还没配，阶段 3 会配），Swagger UI 会把所有接口都标成"需要认证"。加了 `@SecurityRequirements`（空注解）就是显式豁免，Swagger 会在这个接口上显示一把"开着的锁"。**不加的后果**：你在 Swagger UI 里点登录接口，它要求你先填 token——但登录接口本身就是为了拿 token，逻辑死锁。

### 8.3 `LoginRequestDTO`：加 `@Schema`

```java
@Schema(description = "登录请求")
public class LoginRequestDTO {

    @NotBlank(message = "账号不能为空")
    @Schema(description = "账号：管理员填用户名（如 admin），学生填学号（如 S000000001）",
            example = "S000000001", requiredMode = Schema.RequiredMode.REQUIRED)
    private String account;

    @NotBlank(message = "密码不能为空")
    @Schema(description = "密码", example = "Abc12345", requiredMode = Schema.RequiredMode.REQUIRED)
    private String password;
}
```

**顺便修一个真实缺陷**：你现在的 `@NotNull` + `@NotBlank` 都**没有 message**，校验失败时前端只能看到默认提示。而且 `@NotBlank` 本身就蕴含 `@NotNull`（一个空字符串也算"not null"），两个叠着写是冗余的。改成只留 `@NotBlank(message = "...")`。

**注意 `password` 原来的 `@NotNull` 也要换成 `@NotBlank`**——只有 `@NotNull` 的话，传 `"password": ""`（空字符串）能通过校验，然后走到 BCrypt 比对失败返回 401，用户会以为是密码错了，其实是根本没填。这种"错误提示与真实原因不符"是最影响体验的 bug 类型。

### 8.4 `LoginResponseDTO`：补全字段说明

```java
@Data
@AllArgsConstructor
@NoArgsConstructor
@Builder
@Schema(description = "登录响应")
public class LoginResponseDTO {

    @Schema(description = "JWT 令牌，后续请求放在请求头 Authorization: Bearer <token>",
            example = "eyJhbGciOiJIUzI1NiJ9...")
    private String token;

    @Schema(description = "登录用户名/学号", example = "S000000001")
    private String username;

    @Schema(description = "角色 ADMIN / STUDENT，仅用于前端界面显示，无安全作用",
            allowableValues = {"ADMIN", "STUDENT"})
    private String role;

    @Schema(description = "真实姓名", example = "学生1")
    private String realName;
}
```

`allowableValues` 会让 Swagger UI 把这个字段渲染成下拉枚举，比纯文字说明更清楚。
