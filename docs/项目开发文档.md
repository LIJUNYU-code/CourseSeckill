## 1. 项目定位

### 1.1 一句话定位

> **一个完整可演示的选课系统，核心是一条可量化的性能优化主线：从"会超卖、低并发"，一步步演进到"不超卖、高并发"，每个版本都有实测数据。**

### 1.2 为什么做这个项目（与项目一的关系）

项目一（ClassHub）已经证明：**能独立完成一个完整系统**（需求分析 → 数据库设计 → 后端 → 前端 → 测试 → CI → 部署）。

但它答不上面试中最关键的那个问题：**"你这个项目最难的地方在哪？怎么发现的？怎么解决的？解决前后差多少？"**

原因很直接：项目一从未遇到真正的困难。数据量小（几千行）、没有并发（单人点页面）、没有性能瓶颈（响应都在 50ms 内）。它能跑，但"能跑"是及格线。

所以项目二的目标不是"再做一遍"，而是**制造困难、解决困难、量化困难**。

| | 项目一 ClassHub | 项目二 CourseSeckill |
|---|---|---|
| 一句话 | 教学管理平台，10 个模块全流程 | 选课秒杀引擎，并发从 0 到万级 |
| 规模 | 大而全（45 个接口、9 个页面） | 小而深（6 个接口、1 个页面） |
| 证明什么 | 能独立交付完整系统 | 能解决真实性能问题 |
| 面试时长 | 能讲 5 分钟 | 能讲 20 分钟 |
| 短板 | 无技术深度 | 业务广度窄 |
| 互补关系 | 广度 | 深度 |

**两个合起来才是完整画像**：只有前者是"会写增删改查"，只有后者是"没做过完整系统"。

### 1.3 四条不可违背的原则

这四条比任何技术选型都重要，它们决定项目会不会退化成"又一个教程复刻"。

| # | 原则 | 具体含义 | 违反的后果 |
|---|---|---|---|
| **P1** | **先复现问题，再解决问题** | 每个优化版本之前，必须先有一个能跑出问题的版本 | 直接抄"标准答案"，学不到任何东西，面试一追问就露馅 |
| **P2** | **不压测不下结论** | 任何"更快了/更稳了"的说法，必须有前后对比数据 | 面试官问"快多少"，答不出具体数字 |
| **P3** | **一次只改一个变量** | 版本之间只允许一处差异，其余全部不变 | 数字变化说不清是谁的功劳，等于白测 |
| **P4** | **功能做小，深度做透** | 全部业务 6 个接口，不新增任何功能 | 摊子铺大，最后哪块都不深 |

⚠️ **P4 是最反直觉的一条**。项目一是"做全"，这个项目是"做小"。因为要练的不是"能不能写出来"，而是"能不能扛住"。任何"要不要再加个 XX 功能"的念头，一律以 P4 驳回。

### 1.4 成功标准（验收定义）

项目做完后，必须能拿出下面这些东西。**缺少任何一项都算未完成。**

| # | 验收项 | 判定方式 |
|---|---|---|
| A1 | 有 5 个可切换的版本，每个版本 git tag 可检出 | `git tag` 能看到 v0~v4，每个都能 `git checkout` 后独立跑起来 |
| A2 | 每个版本都有实测数据 | `docs/压测报告.md` 里有 v0~v4 的 QPS/P95/错误率/超卖数对比表，**数字是实测的** |
| A3 | v0 能稳定复现超卖 | 压测 1000 请求打 100 库存，最后售出数 > 100，现象可复现 |
| A4 | v4 在高并发下零超卖 | 同上条件下售出数 == 100，且 `stock` 与 `sold` 守恒 |
| A5 | 有一键启动 | 克隆仓库后 `docker compose up -d` + 一条命令即可跑起全栈 |
| A6 | 有一个能点操作的页面 | 浏览器里能点"抢课"按钮，看到剩余名额实时变化 |
| A7 | 有自动化测试 | 核心业务逻辑（库存扣减、幂等、退课）有单测，CI 通过 |
| A8 | 分库分表有数据支撑的结论 | 有 2000 万行实测数据，明确回答"需不需要分表"及理由 |
| A9 | 能讲 20 分钟 | 准备 5 个可深挖的技术问题及回答（见 §9.10） |

### 1.5 明确不做（负面清单）

| 不做 | 理由 |
|---|---|
| ❌ 微服务拆分 | 单机都压不出瓶颈，拆成微服务只是把问题变复杂。等能说清"为什么单体扛不住"再谈 |
| ❌ 分库分表做主线 | 见 §8.1：分表解决"数据量大"，本项目核心是"并发高"，两个问题不同，顺序不能反 |
| ❌ 班级/成绩/考勤/请假 | 项目一的领域，重复无收益 |
| ❌ 移动端 / 多语言 / 复杂前端 | 前端只做一个页面，用途是"看得见"，不是"好看" |
| ❌ 第三方登录（OAuth2） | 与并发主题无关，纯耗时 |
| ❌ 分布式事务框架（Seata） | 阶段 4 用"最终一致性 + 补偿"手工实现，比引框架更能理解原理 |
| ❌ 为了用而用（ES / Kafka / Neo4j / K8s） | 面试官一问"为什么用这个"答不出来，就是减分项 |
| ❌ 优惠券/积分/物流等泛业务 | 违反 P4 |

## 2. 业务设计

### 2.1 场景描述

> 学校每学期开放选课，500 门课，每门课 100 个名额。选课在整点开放，**1 万名学生在同一秒涌入**。热门课程在 3 秒内被抢光。

**为什么这个场景天然适合练并发**：

1. **有硬约束**：名额 100 就是 100，多卖一个就是生产事故（超卖）
2. **有热点**：所有请求打在同一行数据上（`course_stock` 的某一行），这不是"分散压力"，是"极致争抢"
3. **有幂等需求**：同一个人重复点按钮，不能扣两次名额
4. **有异步空间**：抢课结果不必同步返回，可以"先受理、后处理"
5. **有降级需求**：热门课瞬间被抢光后，大量请求要快速失败（不能拖垮系统）

### 2.2 角色

| 角色 | 权限 | 说明 |
|---|---|---|
| STUDENT | 登录、抢课、退课、查自己的选课 | 主要压测对象 |
| ADMIN | 登录、查任意课程/订单、重置库存（测试用） | 少量使用，主要用于验证数据一致性 |

⚠️ **角色设计刻意简化**：只有两级，不引入"教师/院系/专业"等维度。理由见 P4。

### 2.3 业务规则（必须精确实现）

| # | 规则 | 违反的表现 |
|---|---|---|
| R1 | 课程剩余名额 > 0 才能抢课成功 | 超卖 |
| R2 | 同一学生同一课程只能有一条**有效**记录（status ∈ {0,1}） | 重复扣名额、同一人占两个名额 |
| R3 | 抢课成功后 `stock` 减 1、`sold` 加 1，且 `stock + sold == capacity` 永远成立 | 数据不守恒 |
| R4 | 退课只对 status=1（已成功）的记录生效，退课后 `stock` 加 1、`sold` 减 1，记录 status 改为 3 | 退课退不掉 / 退了没还名额 |
| R5 | 退课后允许重新抢同一门课 | 用户被永久锁死 |
| R6 | 同一学生并发点击 10 次，只允许 1 次成功（其余返回"已选过"） | 一人占多个名额 |
| R7 | 课程未开放（`course.status != 1`）或已过结束时间时拒绝 | 抢了不该抢的课 |
| R8 | 抢课结果必须是"成功 / 已满 / 已选过 / 未开放 / 处理中"五者之一，不能有第六种 | 前端无法处理未知状态 |

### 2.4 状态机

**订单状态 `seckill_order.status`**

```
                    ┌──────────────────────────────────────┐
                    │                                      │
                    ▼                                      │
  [创建] ──► 0 待处理 ──成功──► 1 已成功 ──退课──► 3 已退课 ──重新抢──┘
                 │
                 └──失败──► 2 已失败（fail_reason 记录原因）
```

| 状态 | 含义 | 何时出现 |
|---|---|---|
| 0 待处理 | 请求已受理，正在异步处理 | **只有 v3（MQ 异步）才会出现**。v0~v2 是同步的，不会停在 0 |
| 1 已成功 | 扣减成功，占用了名额 | 主流状态 |
| 2 已失败 | 处理失败（库存不足/系统异常） | v3 异步场景下的最终失败 |
| 3 已退课 | 学生主动退课，名额已归还 | 退课后 |

⚠️ **关键设计点：退课后不是删除记录，而是将 status 改为 3。**
原因：`uk_student_course(student_id, course_id)` 唯一索引会阻止重新 INSERT。所以"重新抢课"必须走 **UPDATE status 3→1**，而不是 INSERT。这是本项目第一个容易被忽略的坑，见 §5.1 的陷阱表。

**课程状态 `course.status`**

| 值 | 含义 |
|---|---|
| 0 | 未开放（还没到抢课时间） |
| 1 | 开放中（可抢） |
| 2 | 已结束 |

```json

  "code": 200,
  "message": "success",
  "data": { }

```

**统一错误码语义**

| HTTP | code | 含义 | 典型场景 |
|---|---|---|---|
| 200 | 200 | 成功 | — |
| 400 | 400 | 参数错误 | courseId 不是数字、页码非法 |
| 401 | 401 | 未认证/令牌无效 | 没带 token、token 过期 |
| 403 | 403 | 无权限 | 学生访问管理员接口 |
| 404 | 404 | 资源不存在 | 课程不存在、订单不存在 |
| 409 | 409 | 状态冲突 | **已选过**、已满、已退课再退 |
| 429 | 429 | 触发限流 | 阶段 5 之后的限流方案 |

### 2.6 接口详细定义

#### 2.6.1 POST `/api/auth/login`

**请求**

```json
{ "account": "S000000001", "password": "<你的密码>" }
```

**成功响应 200**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "role": "STUDENT",
    "username": "S10000001",
    "studentId": 10000001
  }
}
```

**失败**

| 场景 | HTTP | message |
|---|---|---|
| 用户名或密码错误 | 401 | `用户名或密码错误`（**不区分是哪个错**，防止撞库探测） |
| 账号被禁用 | 401 | `账号已被禁用` |

⚠️ 为什么统一提示"用户名或密码错误"：如果分开提示"用户不存在"/"密码错误"，攻击者可以批量探测哪些账号存在。这是安全细节，项目一已经用过同样处理。

#### 2.6.2 GET `/api/course/{courseId}`

**成功响应 200**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "courseId": 88,
    "courseNo": "CS000000088",
    "name": "高等数学（上）",
    "teacher": "王老师",
    "capacity": 100,
    "stock": 37,
    "sold": 63,
    "status": 1,
    "startTime": "2026-11-10T10:00:00",
    "myOrderStatus": 1
  }
}
```

**字段说明**

| 字段 | 来源 | 说明 |
|---|---|---|
| `stock` / `sold` | v0~v1 查 `course_stock` 表；**v2 起查 Redis** | 这是缓存一致性的观察点 |
| `myOrderStatus` | 查当前登录学生该课的订单 | `null` = 没选过；0/1/2/3 = 对应状态 |

⚠️ **`myOrderStatus` 容易被漏掉**。前端要靠它决定按钮显示"抢课"还是"退课"。没有这个字段，前端只能再去请求一次订单列表。

#### 2.6.3 POST `/api/seckill/{courseId}`

**请求**：无 body（学生身份从 JWT 取，**绝不从请求体传 studentId**）

⚠️ 为什么强调这点：如果 studentId 从请求体传，学生 A 就能改成学生 B 的 ID 帮别人抢课（越权漏洞）。

**同步模式成功响应（v0~v2）200**

```json
{ "code": 200, "message": "抢课成功", "data": { "orderNo": "20261106100001123456", "status": 1 } }
```

**异步模式响应（v3+）200**

```json
{ "code": 200, "message": "抢课请求已受理，请稍后查询", "data": { "orderNo": "20261106100001123456", "status": 0 } }
```

**失败清单**

| 场景 | HTTP | message | 触发规则 |
|---|---|---|---|
| 课程不存在 | 404 | `课程不存在` | — |
| 课程未开放 | 409 | `课程尚未开放选课` | R7 |
| 名额已满 | 409 | `该课程名额已满` | R1 |
| 已选过 | 409 | `你已选过该课程` | R2 |
| 重复点击（并发） | 409 | `你已选过该课程` | R6 |

**成功响应 200**

## 3. 数据库设计

### 3.1 表清单（6 张，不再增加）

| 表 | 用途 | 预估行数 | 写频率 | 读频率 |
|---|---|---|---|---|
| `student` | 学生基础数据（造数据用） | 10 万 | 0（静态） | 低 |
| `course` | 课程与总名额 | 500 | 0 | 中 |
| `course_stock` | **库存（核心热点）** | 500 | **极高** | 极高 |
| `seckill_order` | 选课记录（**最终会到千万级**） | 1000 万（压测造） | 高 | 中 |
| `sys_user` | 登录账号 | 10 万 | 0 | 低 |
| `mq_consume_log` | MQ 消费幂等去重 | 与订单同量级 | 高 | 高（按主键查） |

**为什么库存要单独建表**（关键设计决策）：

如果把 `stock` 放在 `course` 表里，那一行的 `name`、`teacher`、`start_time` 等"读多写不写"的字段会和"每秒被改上千次"的 `stock` 挤在同一行。InnoDB 改一行要加行锁，虽然锁的是行不是列，但：

1. 同一行的并发更新会互相排队（这是我们要的）
2. 但**任何读该行的查询也会被牵扯到锁等待**（这是我们不想要的——查课程名不该因为库存争抢而阻塞）

拆开后，`course` 表承担"读"，`course_stock` 表承担"写争抢"，互不干扰。这是"读写分离"思想在单表级别的最小应用。

### 3.2 DDL

```sql
-- ============================================
-- CourseSeckill 初始化脚本
-- 数据库: seckill
-- 字符集: utf8mb4（支持 emoji，避免中文乱码）
-- ============================================

CREATE DATABASE IF NOT EXISTS seckill
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;

USE seckill;

-- --------------------------------------------
-- 1. 学生表（造数据用，不参与登录）
-- --------------------------------------------
CREATE TABLE IF NOT EXISTS student (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  student_no  CHAR(10)        NOT NULL                COMMENT '学号，如 S10000001',
  name        VARCHAR(50)     NOT NULL                COMMENT '姓名',
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_student_no (student_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生基础数据';

-- --------------------------------------------
```

### 3.3 索引设计理由

| 索引 | 服务于哪个查询 | 为什么这样建 | 不建的后果 |
|---|---|---|---|
| `uk_student_no` | 登录时按学号查 | 唯一约束 + 查询加速 | 同学号重复数据 |
| `uk_course_no` | 课程编号唯一 | 唯一约束 | 编号重复 |
| `idx_status_start` | 查"当前开放的课程" | 联合索引，等值(status) + 范围(start_time) 可走索引 | 全表扫 |

| `idx_student_status` | 我的选课列表 | 复合索引，分页友好 | 全表扫 |
| `uk_msg_id` | MQ 消费去重 | 唯一约束，`INSERT` 冲突即已消费 | 消息重复处理 |

### 3.4 数据量规划

| 场景 | student | course | course_stock | seckill_order |
|---|---|---|---|---|
| 功能自测 | 10 | 3 | 3 | < 100 |
| 常规压测 | 10,000 | 500 | 500 | 10 万 |
| 极限压测 | 10,000 | 500 | 500 | 100 万 |
| 分表实验 | — | — | — | **2,000 万** |

**为什么学生只要 1 万而不是 10 万**：压测并发是"同时有多少个用户"，不是"总共有多少用户"。1 万学生足够模拟 1000~5000 并发（每个用户重复请求），造 10 万反而拖慢造数据速度。

### 3.5 造数据方案

**目标**：一条命令生成全部测试数据，可重复执行（幂等），耗时 < 5 分钟。

| 数据 | 生成方式 | 备注 |
|---|---|---|
| 500 门课程 | SQL 循环 / 存储过程 | 课程名用 "课程001"~"课程500"，capacity 统一 100 |
| 500 条库存 | `INSERT ... SELECT FROM course` | stock=capacity, sold=0 |
| 10,000 学生 | 存储过程批量插入 | 学号 `S10000001` ~ `S10010000` |
| 10,000 登录账号 | 同上，密码统一 BCrypt 哈希 | **同一个哈希复用**（BCrypt 每次结果不同，但验证都通过；复用可把造数据从 10 分钟降到 10 秒） |
| 2000 万订单（阶段 8 专用） | 分批 `INSERT`，每批 10 万 | 单独脚本，不放进常规初始化 |

⚠️ **造数据的一个坑**：`INSERT` 2000 万行不能用一条 SQL，会撑爆 redo log 和内存。必须**分批提交**（每批 10 万行），并且关闭自动提交、用事务包住每一批。这个脚本大概要跑 10~30 分钟，是阶段 8 的时间成本之一。

### 4.3 新增部分与选型理由

#### 4.3.1 Redis：用途与项目一完全不同

| 项目一怎么用 | 这个项目怎么用 |
|---|---|
| Token 黑名单（存个 key 判断存在） | **库存主存 + Lua 原子扣减**（真正的并发控制） |
| 用量：几十个 key | 用量：500 个库存 key + 1 万个用户选课集合 |

**关键技术点：库存扣减必须用 Lua 脚本。**

原因：Redis 单条命令是原子的，但"读库存 → 判断够不够 → 减法"是三步。如果用 Java 代码分三次调用：

```java
// ❌ 错误写法：三步之间可能有其他请求插进来
Integer stock = redis.get("stock:88");   // 读到 100
if (stock > 0) {
    redis.decr("stock:88");              // 如果这中间 100 个请求都读到 100，就全都会减
}
```

**结果：100 个并发请求全部通过判断，库存从 100 减到 0 甚至负数。**

正确做法是把三步写进一个 Lua 脚本，Redis 保证脚本整体原子执行：

```lua
-- ✅ 正确写法：整个脚本原子执行
local stock = redis.call('GET', KEYS[1])
if not stock then return -2 end          -- 库存不存在
if tonumber(stock) <= 0 then return -1 end -- 已满
redis.call('DECR', KEYS[1])
return tonumber(stock) - 1                -- 返回剩余
```

**已在本机 Memurai 8.2.10 实测通过**（EVAL 与 EVALSHA 均正常）。

## 5. 版本演进设计（项目核心）

### 5.1 五版本总览

| 版本 | 名称 | 核心机制 | 预期 QPS | 预期超卖 | 学到什么 |
|---|---|---|---|---|---|
| **v0** | baseline | 直接查库 + 改库存 | 低（几百） | **会超卖** | 什么是竞态条件 |
| **v1** | db-lock | 数据库乐观锁 / 悲观锁 | 更低 | 零 | 锁能保正确性，但代价是性能 |
| **v2** | redis-lua | Redis 预减 + Lua 原子 | **高**（数千） | 零 | 缓存为什么快、原子性为什么重要 |
| **v3** | mq-async | MQ 异步落库 + 幂等 | **更高** | 零 | 削峰、幂等、最终一致性 |
| **v4** | optimize | 压测调优（定位瓶颈） | 最高 | 零 | 性能优化方法论 |
| v5（可选） | sharding | 分库分表实验 | — | 零 | 分片的收益与代价 |

🔴 **硬约束：必须按 v0 → v1 → v2 → v3 → v4 顺序做。** 不允许先做 v2 再回头补 v0。理由见 P1：没有 v0 的超卖现象作为对照，后面所有优化都失去了"优化了什么"的参照系。

### 5.2 v0-baseline：写出会超卖的版本

**实现方式**（朴素到底，不加任何保护）

```java
// v0 伪代码
public void seckill(Long courseId, Long studentId) {
    // 1. 查库存
    Integer stock = stockMapper.selectStock(courseId);   // SELECT stock FROM course_stock WHERE course_id=?
    if (stock == null || stock <= 0) {
        throw new BusinessException(409, "该课程名额已满");
    }
    // 2. 查是否已选
    Order exist = orderMapper.selectByStudentAndCourse(studentId, courseId);
    if (exist != null && exist.getStatus() == 1) {
        throw new BusinessException(409, "你已选过该课程");
    }
    // 3. 扣库存
    stockMapper.decrStock(courseId);                      // UPDATE course_stock SET stock=stock-1 WHERE course_id=?
    // 4. 写订单
    orderMapper.insert(...);
}
```

**预期现象（必须亲眼看到）**

| 指标 | 预期值 | 怎么观察 |
|---|---|---|
| 售出数量 | **> 100**（比如 137） | 压测后 `SELECT COUNT(*) FROM seckill_order WHERE course_id=88 AND status=1` |
| 库存 | **负数**（比如 -37） | `SELECT stock FROM course_stock WHERE course_id=88` |
| 守恒检查 | `stock + sold != capacity` | 触发 §3.2 的 `CHECK (stock >= 0)` 会报错，说明数据已坏 |

**根因（要在文档里写清楚，不是为了"复现一个 bug"）**

`SELECT` 和 `UPDATE` 是两个独立操作，中间有窗口期。100 个并发请求几乎同时执行 `SELECT`，**都读到 stock=1**，于是都认为"还有名额"，都执行 `UPDATE`。

**面试话术准备**："这不是代码写错了，是我的写法在并发下语义不成立。'先查后改'在单线程下正确，在多线程下是错的——这叫竞态条件（race condition）。"

**验收标准**

- [ ] 压测能稳定复现超卖（连跑 3 次，3 次都超卖）
- [ ] 能准确说出超卖数量与并发数的关系（并发越高，超卖越多）
- [ ] `docs/压测报告.md` 记录 v0 的数字

### 5.3 v1-db-lock：用数据库解决

**两个方案都要实现，分别压测**

#### 方案 A：乐观锁

```sql
-- 不改表结构，用 stock > 0 作为条件
UPDATE course_stock
SET stock = stock - 1, sold = sold + 1
WHERE course_id = ? AND stock > 0;
```

```java
int affected = stockMapper.decrWithCheck(courseId);
if (affected == 0) {
    throw new BusinessException(409, "该课程名额已满");
}
```

**原理**：把"判断"和"修改"合并成一条 SQL。InnoDB 执行 `UPDATE` 时会加行锁，两个并发请求会串行执行，第二个执行时 `stock` 已是 0，`affected=0`。

**或者用 version 字段**（更通用，适用于"判断条件不是库存"的场景）：

```sql
UPDATE course_stock
SET stock = stock - 1, version = version + 1
WHERE course_id = ? AND version = ?;
```

关键在于**检查 `affected rows`**，而不是"觉得它应该成功了"。

#### 方案 B：悲观锁

```sql
SELECT stock FROM course_stock WHERE course_id = ? FOR UPDATE;
```

**原理**：`FOR UPDATE` 直接在读取时加排他锁，其他事务必须等。**问题**：锁持有时间长（从 `SELECT` 到事务提交），并发一高就排队，QPS 会掉得比乐观锁更狠。

**预期现象**

| 指标 | 乐观锁 | 悲观锁 |
|---|---|---|
| 超卖 | **0** ✅ | **0** ✅ |
| QPS | 比 v0 明显下降 | 比乐观锁更低 |
| P95 延迟 | 上升 | 上升更多 |
| 现象 | `affected=0` 的请求变多 | 大量请求卡在锁等待 |

**学到什么**

这是项目里第一次遇到"正确性和性能的权衡"。

- v0 快但不正确
- v1 正确但慢

**面试话术**："加了锁之后超卖消失了，但 QPS 从 X 掉到 Y。这不是 bug，是代价——锁的本质是把并发变成串行。所以我继续往下做，目标是既正确又快。"

**验收标准**

- [ ] 两个方案都压测过，有对比数据
- [ ] 能解释"为什么乐观锁通常比悲观锁快"（锁持有时间短：乐观锁在 `UPDATE` 语句执行时加锁，悲观锁从 `SELECT` 就加锁）
- [ ] 能回答"什么场景该用悲观锁"（冲突概率高、重试代价大时，乐观锁的重试会浪费更多资源）

### 5.4 v2-redis-lua：引入 Redis

**这是整个项目的技术核心。**

**实现步骤**

1. **库存预热**：应用启动或手动触发时，把 `course_stock` 的 `stock` 写入 Redis
   ```
   SET stock:88 100
   SET stock:89 100
   ...
   ```
2. **抢课流程改为先走 Redis**
   ```java
   Long remain = redisTemplate.execute(SECKILL_SCRIPT, keys, courseId);
   if (remain == -1) throw new BusinessException(409, "该课程名额已满");
   if (remain == -2) throw new BusinessException(404, "课程不存在");
   // 扣减成功，继续落库
   ```
3. **Lua 脚本**（必须整体原子）
   ```lua
   local stock = redis.call('GET', KEYS[1])
   if not stock then return -2 end
   if tonumber(stock) <= 0 then return -1 end
   redis.call('DECR', KEYS[1])
   return tonumber(stock) - 1
   ```

**预期现象**

| 指标 | 变化 |
|---|---|
| QPS | **大幅上升**（请求不再打数据库） |
| 超卖 | 0 |
| 数据库 CPU | 明显下降 |
| **新问题** | **Redis 扣了但数据库没写成功，怎么办？** |

**新问题的三种场景（这是 v2 最有价值的部分）**

| 场景 | 后果 | 处理 |
|---|---|---|
| Redis 扣减成功 → 写数据库时宕机 | 名额被"吃掉"了，但没人选上（少卖） | 补偿任务：定期对比 Redis 与 DB 的库存差，修正 |
| Redis 扣减成功 → 数据库写失败（如唯一索引冲突） | 名额被吃掉，但订单没建 | 回滚 Redis（`INCR`），或进失败重试队列 |
| Redis 重启丢数据（未开 AOF） | 库存状态丢失 | 开启 AOF，或从数据库重建 |

⚠️ **本机 Memurai 的 `appendonly` 当前是 `no`**。压测场景没问题（丢了重新预热），但要写进文档：生产必须开 AOF。

**学到什么**

- Redis 为什么快（内存 + 单线程无锁 + 无 SQL 解析）
- 为什么"原子"必须用一个整体（Lua），而不是"几条命令靠得近"
- **缓存与数据库不一致是常态，不是异常**——必须设计补偿机制

**验收标准**

- [ ] QPS 相比 v1 有数量级提升（至少 3 倍）
- [ ] 零超卖
- [ ] 能画出"Redis + DB 双写"的时序图，标出 3 个可能不一致的点
- [ ] 实现至少一种补偿机制（定时对账或失败回滚）

### 5.5 v3-mq-async：MQ 异步落库

**核心思路：Redis 扣减成功后，不直接写数据库，而是发消息，让消费者慢慢写。**

**架构变化**

```
v2:  请求 → Redis 扣减 → 同步写 DB → 返回
v3:  请求 → Redis 扣减 → 发 MQ 消息 → 立即返回"处理中"
                              ↓
                       消费者 → 写 DB → 更新订单状态
```

**预期现象**

| 指标 | 变化 |
|---|---|
| 接口响应时间 | **大幅下降**（不等数据库） |
| QPS | 上升 |
| 数据库压力 | **被摊平**（瞬时高峰变成持续低峰） |
| **新问题** | **消息堆积**——如果消费者太慢，队列越堆越长 |

**必须解决的三个经典问题**

#### 问题 1：消息丢了怎么办

| 丢失点 | 原因 | 处理 |
|---|---|---|
| 生产者发出前宕机 | Redis 已扣，消息没发出 | 本地消息表 / 事务消息 |
| MQ 收到但没持久化 | RabbitMQ 默认不持久化 | 声明 `durable=true` + `delivery_mode=2` |
| 消费者取到但处理前宕机 | 消息已 ack 但业务没做 | **手动 ack**，处理成功才 ack |

🔴 **必须用手动 ack**（`acknowledge-mode: manual`）。自动 ack 会在"取到消息就删"的语义下丢消息。

#### 问题 2：消息重复了怎么办（幂等）

**为什么一定重复**：网络超时、ack 丢失、消费者处理完但 ack 前宕机——MQ 的语义是"至少一次"（at-least-once），不是"恰好一次"。

**实现方式（用 `mq_consume_log` 表）**

```java
// 伪代码
@Transactional
public void consume(SeckillMessage msg) {
    // 1. 用 msg_id 做唯一约束插入，冲突说明已消费
    try {
        consumeLogMapper.insert(msg.getMsgId());
    } catch (DuplicateKeyException e) {
        log.info("消息 {} 已消费，跳过", msg.getMsgId());
        return;   // 幂等：直接返回成功
    }
    // 2. 正常处理业务
    stockMapper.decrStock(msg.getCourseId());
    orderMapper.updateStatus(msg.getOrderNo(), 1);
}
```

⚠️ **关键点：去重表的 INSERT 和业务操作必须在同一个事务里。** 否则可能出现"去重记录插了但业务失败"，导致消息被永久丢弃。

#### 问题 3：消费失败了怎么办

| 情况 | 处理 |
|---|---|
| 可重试的失败（数据库超时） | 重试 N 次，间隔递增 |
| 不可重试的失败（库存不足、参数错误） | 直接进死信队列，记录 `fail_reason` |
| 重试耗尽 | 进死信队列，人工/定时任务处理 |

**RabbitMQ 配置**：`x-dead-letter-exchange` 指向死信交换机。

**学到什么**

- MQ 的三种投递语义（至多一次 / 至少一次 / 恰好一次）——**"恰好一次"是不存在的**，只能靠幂等模拟
- 削峰的原理：不是"处理更快"，而是"把峰值摊到更长时间"
- 最终一致性：接口返回"处理中"时，数据还没落库，但保证最终会一致

**验收标准**

- [ ] 接口响应时间相比 v2 明显下降
- [ ] 队列在压测期间能看到堆积（这是正常现象，要看它是否最终被消费完）
- [ ] 故意重复投递同一条消息，业务只执行一次（幂等生效）
- [ ] 故意让消费者抛异常，消息进死信队列而不丢失
- [ ] 能回答"消息为什么一定重复"（不是"可能"，是"一定"）

### 5.6 v4-optimize：压测调优

**这一步没有固定代码，只有方法论：先测量，再优化，一次只改一个变量。**

**调优顺序（按瓶颈转移规律）**

| 轮次 | 观察到的现象 | 可能瓶颈 | 动作 |
|---|---|---|---|
| 1 | QPS 上不去，DB 连接等待 | 连接池太小 | 调大 `maximum-pool-size` |
| 2 | 连接池加大后 QPS 略升，但 GC 频繁 | JVM 内存不足 | 调 `-Xmx`，换 G1/ZGC |
| 3 | GC 好了，Redis 命令耗时上升 | Redis 单线程打满 | 加 Pipeline / 拆分 key / 用本地缓存 |
| 4 | 都好了，但 P99 有毛刺 | 网络/线程池/日志 | 关同步日志、调 Tomcat 线程数 |
| 5 | 系统稳定，但错误率上升 | 触发限流/超时 | 确认是保护机制正常工作 |

🔴 **必须遵守：一次只改一个参数，改完重压。** 同时改三个参数，QPS 涨了也不知道是谁的功劳（违反 P3）。

**预期现象：瓶颈会"跑"**

```
修好 DB  → 瓶颈跑到连接池
修好连接池 → 瓶颈跑到 GC
修好 GC   → 瓶颈跑到 Redis 网络
修好 Redis → 瓶颈跑到 CPU
```

**这个"瓶颈转移"现象本身就是最好的面试素材**——它证明你不是在背答案，而是在真的调优。

**验收标准**

- [ ] 有一张"调优前后对比表"，每行只改一个参数
- [ ] 能说出每一轮"为什么判断是这个瓶颈"（依据是什么监控指标）
- [ ] 找到系统真实的压测上限（QPS 拐点），并说明超限后的表现

### 5.8 版本演进的陷阱清单

这些是开发中**一定会遇到**的问题，提前写下来，遇到了不会慌。

| # | 陷阱 | 出现在 | 正确做法 |
|---|---|---|---|

## 6. 压测方案

### 6.1 压测指标定义

**所有对比必须以这些指标为准，不允许只报"感觉快了"。**

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **QPS** | 每秒成功处理请求数 | 吞吐能力的核心指标。注意是"成功"，不是"总请求" |
| **P50 / P95 / P99 延迟** | 50%/95%/99% 的请求在多少毫秒内完成 | **平均值会骗人**。100 个请求里 99 个 10ms、1 个 5000ms，平均 60ms 看着不错，但那 1 个用户疯了 |
| **错误率** | 非 2xx 请求占比 | 高 QPS 配上高错误率毫无意义 |
| **超卖数** | `sold - capacity`（正数即超卖） | 正确性指标，**比 QPS 更重要** |
| **数据守恒** | `stock + sold == capacity` | 一次校验胜过一万次猜测 |
| **CPU / 内存占用** | 被测机与被测 JVM 的资源曲线 | 判断瓶颈在哪 |

⚠️ **为什么必须看 P99 而不只看平均**：面试官常问"你怎么衡量性能"。只答"平均 50ms"会被追问"那最慢的呢"。能主动说"我看 P99，因为平均值掩盖长尾"是加分项。

### 6.2 压测场景设计

#### 场景 A：单课程极限抢购（核心场景）

```
500 个虚拟用户 → 同时抢 100 个名额的课程 88 → 持续 30 秒
```

**关注**：超卖、QPS、P99、错误率分布。

#### 场景 B：多课程分散抢购（更真实）

```
1000 个虚拟用户 → 随机抢 50 门课（每门 100 名额）→ 持续 60 秒
```

**关注**：整体吞吐、是否出现热点倾斜。

#### 场景 C：读写混合（模拟真实使用）

```
70% 抢课 + 30% 查课程详情 → 持续 60 秒
```

**关注**：读写互相影响。**这是 v2 引入 Redis 后最有价值的场景**——如果课程详情还没走缓存，会被库存争抢拖慢。

#### 场景 D：重复点击（验证幂等）

```
100 个用户 × 每个点 10 次同一门课 → 共 1000 请求
```

**关注**：成功数必须恰好等于用户数（100），不能是 110。

### 6.4 压测环境约束（对应你选的方案 B）

**目标**：模拟资源受限的真实环境，而不是"无限资源下的漂亮数字"。

| 组件 | 限制 | 配置方式 | 理由 |
|---|---|---|---|
| Redis（Memurai） | `memory=4GB` 上限已设 | `.wslconfig`（WSL 内存） | 防止 WSL 无节制吃内存 |
| RabbitMQ 容器 | **512 MB / 0.5 CPU** | `docker run --memory 512m --cpus 0.5` | 已生效 |
| 后端 JVM | `-Xmx512m -Xms512m` | 启动参数 | 固定堆大小，让 GC 行为稳定可复现 |
| MySQL | 不限制 | — | 让数据库"自然"表现，观察它何时成为瓶颈 |
| WSL | `memory=4GB, processors=8` | `.wslconfig` | 留出 CPU 给 k6 |

**为什么后端要固定 `-Xmx512m`**：JVM 默认堆会按物理内存的 1/4 设置，不同机器不同时刻不一样。固定后，v2 和 v3 的 GC 行为才可比——**这是"一次只改一个变量"原则在环境上的体现**。

### 7.3 🔴 关键设计：如何在一个仓库里容纳 5 个版本

**这是本项目最重要的工程决策，决定了"版本对比"能否成立。**

**方案对比**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 每个版本一个分支 | `git checkout v0` 切换代码 | 干净 | 无法同时对比；合并冲突；**测试时切来切去很痛苦** |
| B. 每个版本一个 tag，主干只保留最新 | 打 tag 存档 | 简单 | 同上 |
| **C. 策略模式 + 配置切换** ⭐ | 同一份代码里有 5 个 Service 实现，通过配置选一个 | **同一次启动就能对比**；改配置即可；面试演示极方便 | 代码里有"死代码"（v0 在 v4 时不用了） |
| D. 独立项目 5 份 | 完全隔离 | 最干净 | 5 份代码要同步维护，工作量爆炸 |

**选定方案 C，理由：**

1. **压测对比可以"热切换"**：改 `application.yml` 的 `seckill.strategy=v0` 重启即可，不用 git 切分支（切分支后 target 目录、依赖都可能要重编，很慢）
2. **面试演示时可以说**："我保留了 5 套实现，你可以现场切换看效果"——**这比分 5 个仓库更有说服力**
3. **代码 diff 清晰**：`git diff` 看不出"v2 相比 v1 加了什么"，但在同一文件树里，`SeckillServiceImplV1.java` vs `V2.java` 一眼看到差异

**实现方式**

```java
public interface SeckillService {
    SeckillResult seckill(Long courseId, Long studentId);
    void cancel(Long courseId, Long studentId);
}

@Service
@ConditionalOnProperty(name = "seckill.strategy", havingValue = "v0", matchIfMissing = true)
public class SeckillServiceImplV0 implements SeckillService { ... }

@Service
@ConditionalOnProperty(name = "seckill.strategy", havingValue = "v1")
public class SeckillServiceImplV1 implements SeckillService { ... }
// ... v2 / v3 / v4
```

```yaml
# application.yml
seckill:
  strategy: v0   # 改这里切换版本
```

**同时也要打 git tag**（两者不冲突）：

```bash
git tag -a v0-baseline -m "v0: 朴素实现，会超卖"
git tag -a v1-db-lock  -m "v1: 数据库锁，零超卖但慢"
git tag -a v2-redis-lua -m "v2: Redis Lua 原子扣减"
git tag -a v3-mq-async  -m "v3: MQ 异步落库 + 幂等"
git tag -a v4-optimize  -m "v4: 压测调优完成"
```

⚠️ **tag 和策略切换要一起用**：tag 用于"回看某一版完整代码"（含当时的测试、文档、配置），策略切换用于"快速对比性能"。

## 8. 分库分表专项

### 8.1 先回答一个问题：这个项目真的需要分库分表吗

**结论先行：大概率不需要。**

**为什么必须写在最前面**：分库分表是简历上最容易被问倒的技术。面试官问"为什么分"，如果答"因为数据量大"就会被追问"多大数据量？测过吗？不分会怎样？"——答不上来就暴露了"照着教程做的"。

**分库分表解决的是两个不同的问题**

| 问题 | 表现 | 解法 |
|---|---|---|
| **并发高**（本项目核心） | QPS 上不去、行锁争抢 | 缓存、异步、限流、读写分离 |
| **数据量大**（分表要解决的问题） | 单表查询变慢、DDL 卡住、备份慢 | 分库分表 |

🔴 **这是两个不同的问题。** 本项目 v0~v4 要解决的是第一个。用分表去解决并发问题 = 用错工具。

**量化判断标准**（本项目实测数据填进这张表）

| 表 | 行数阈值 | 依据 |
|---|---|---|
| 单表 < 500 万行 | 不需要分表 | B+ 树 3 层，索引查询 3 次 IO，通常在 10ms 内 |
| 单表 500 万 ~ 2000 万 | 视情况 | 要看实际查询耗时和索引命中 |
| 单表 > 2000 万 | 考虑分表 | 索引可能到 4 层，DDL/备份开始痛苦 |

⚠️ **这个数字不是铁律**。真正的判断依据是：**在真实数据量下，核心查询的 P99 是多少、是否还能走索引。** §8.3 会给出实测方法。

### 8.2 如果要分，怎么分：方案设计

**分片键选择（最重要的决策）**

| 候选 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **student_id** ⭐ | "查我的选课"天然聚合到一个分片 | "按课程查名单"要扫全部分片 | **选定** |
| course_id | "按课程查名单"高效 | "我的选课"要扫全部分片；热门课数据倾斜 | 不选 |
| order_no | 分布均匀 | 业务查询几乎都用不上它 | 不选（它只适合做路由，不适合做分片键） |

**为什么选 student_id**：

看 6 个接口的访问模式：

| 接口 | SQL 特征 | 分片键 = student_id 时的表现 |
|---|---|---|
| `POST /seckill/{courseId}` | `INSERT` + 按 student+course 查重 | ✅ 单分片 |
| `GET /order/my` | `WHERE student_id = ?` | ✅ **单分片，最快** |
| `GET /order/{orderNo}` | `WHERE order_no = ?` | ⚠️ 需全分片扫（或建全局索引） |
| 按课程查名单（管理端） | `WHERE course_id = ?` | ⚠️ 需全分片扫 |

**80% 的流量是学生查自己的选课**，所以按 student_id 分片，让最常见的查询最快。

**分片算法**

```
shard = student_id % 4   （先做 4 个分片，不要一上来 16 个）
```

⚠️ **为什么是 4 不是 16**：分片数一旦定下，后期改动要迁移数据（这是分库分表最大的坑之一）。4 个分片足够演示效果，且数据量可控。

### 8.3 ShardingSphere-JDBC 配置示例

**pom.xml**

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc</artifactId>
    <version>5.5.2</version>
</dependency>
```

**application-sharding.yml**

```yaml
spring:
  datasource:
    # 用 ShardingSphere 的数据源替代原生 Hikari
    driver-class-name: org.apache.shardingsphere.driver.ShardingSphereDriver
    url: jdbc:shardingsphere:classpath:sharding.yaml

sharding:
  rules:
    - !SHARDING
      tables:
        seckill_order:
          actualDataNodes: ds_0.seckill_order_${0..3}
          tableStrategy:
            standard:
              shardingColumn: student_id
              shardingAlgorithmName: order_inline
          # 关键：分片键是 student_id，但主键是自增 id
          keyGenerateStrategy:
            column: id
            keyGeneratorName: snowflake
      shardingAlgorithms:
        order_inline:
          type: INLINE
          props:
            algorithm-expression: seckill_order_${student_id % 4}
      keyGenerators:
        snowflake:
          type: SNOWFLAKE
```

⚠️ **注意：ShardingSphere 5.x 的配置格式在 5.4 之后有变动**（`rules:` 改为 `- !SHARDING` 形式）。如果版本不对会报配置解析错误。**以官方文档对应版本为准，不要抄网上的旧配置。**

### 8.4 分库分表的三个真实代价（必踩）

#### 代价 1：唯一索引失效 → 重复选课

**这是最致命的。**

原来靠 `uk_student_course(student_id, course_id)` 防重复。分表后，这个唯一索引**只在单个分片内唯一**。假设 4 个分片，同一学生同一课程的数据落在**同一个分片**（因为都按 student_id 分），所以理论上不会重复……

**但如果分片键选错就会出问题**：如果按 `course_id` 分片，同一学生选同一课程也落同分片，也没问题。**真正出问题的是"跨分片唯一性"**，比如"订单号全局唯一"——这个必须靠雪花 ID 在应用层保证，不能靠数据库。

⚠️ **实践结论**：按 student_id 分片时，`uk_student_course` 仍然有效（因为两个字段相同 student_id 必在同分片）。但**必须验证**，不能假设。验证方法：插入同一 student+course 两次，看是否报 DuplicateKey。

#### 代价 2：非分片键查询变成全分片扫描

`GET /order/{orderNo}` 按 `order_no` 查，但分片键是 `student_id` → ShardingSphere 会**并发查 4 个分片再归并**。

| 查询 | 单表耗时 | 分表耗时（4 分片） |
|---|---|---|
| 按 student_id 查 | 8 ms | **8 ms**（单分片） |
| 按 order_no 查 | 8 ms | **25 ms**（4 分片并发 + 归并） |
| 按 course_id 查名单 + 分页 | 15 ms | **60 ms+**（4 分片 + 内存归并 + 分页在内存做） |

⚠️ **分页是最痛的地方**：`LIMIT 10 OFFSET 1000` 在分表后要改写为每个分片 `LIMIT 10 OFFSET 0`（取前 1010 条）再归并排序取 10 条。**偏移量越大越慢**。这是"深分页问题"，分表会放大它。

**解法（阶段 8 可选）**：
- 用 `order_no` 或 `id` 做游标分页（`WHERE id > lastId LIMIT 10`）代替 `OFFSET`
- 或建"订单号 → 分片"的映射表（Redis / 小表）

#### 代价 3：改分片数要迁移数据

如果 4 个分片不够要扩到 8 个，`student_id % 4` 变成 `% 8`，**几乎所有数据的落点都变了**，需要全量迁移。

**业界解法**：一致性哈希 / 预分片（一开始就分 32 个逻辑分片，映射到 4 个物理库，扩容时挪逻辑分片）。**本项目不实现，只作为面试知识储备。**

### 8.5 分库分表实验的验收标准

**注意：这一阶段的目标是"得出有数据支撑的结论"，不是"用上 ShardingSphere"。**

| # | 任务 | 产出 |
|---|---|---|
| 1 | 造 2000 万行订单数据 | 实测造数据耗时 |
| 2 | 在单表上测：按 student_id 查、按 order_no 查、按 course_id + 分页查 | 三种查询在 100 万/1000 万/2000 万行下的耗时表 |
| 3 | 用 `EXPLAIN` 确认是否走索引、扫描行数 | 每档数据的执行计划 |
| 4 | 配置 ShardingSphere 分 4 表 | 配置文件 |
| 5 | 重测同样的三种查询 | 分表后的耗时表 |
| 6 | **写结论** | "需要分表"或"不需要，因为……" |

**预期结论（待实测验证，不要提前写死）**

| 场景 | 单表（2000 万） | 4 分表 |
|---|---|---|
| 按 student_id 查（走索引） | 可能在 10–30 ms | 相近或略快 |
| 按 order_no 查（走唯一索引） | 可能在 10–30 ms | 可能更慢（全分片） |
| 按 course_id + 深分页 | 可能 100 ms+ | 可能 200 ms+（归并代价） |

⚠️ **很可能得出的结论是"这个项目不需要分表"**。这个结论**完全不丢人**，反而是最值钱的——因为你用实测数据回答了"什么情况下才需要"。面试时说"我压测过 2000 万行，按分片键查仍在 30ms 内，所以没必要分表"比"我用了 ShardingSphere"强得多。

### 8.6 分库分表的四条纪律

| # | 纪律 | 原因 |
|---|---|---|
| 1 | **不为了简历分表** | 面试官会追问细节，答不上来是减分 |
| 2 | **分表前必须先证明单表不够用** | 违反 P2（不压测不下结论） |
| 3 | **分片键一旦确定不改** | 改一次全量迁移 |
| 4 | **分表后必须重跑全部业务测试** | 唯一索引、分页、事务边界都可能变 |

### 9.10 面试问答准备（A9 验收项）

**必须能流畅回答的问题**

| # | 问题 | 回答要点 |
|---|---|---|
| 1 | 你这个项目解决什么问题？ | 选课场景的并发控制。从会超卖演进到零超卖且高吞吐，5 个版本都有实测数据 |
| 2 | 超卖是怎么产生的？ | 竞态条件：`SELECT` 和 `UPDATE` 之间的窗口期，100 个请求都读到 stock=1 |
| 3 | 为什么用 Lua 而不是普通 Redis 命令？ | 三步操作需要原子性，单条命令原子但组合不原子 |
| 4 | Redis 扣减成功但数据库失败怎么办？ | 三种补偿：Redis 回滚、失败重试队列、定时对账。我实现了对账任务 |
| 5 | 为什么要用 MQ？ | 削峰：把瞬时高峰摊平到更长时间，接口不用等数据库 |
| 6 | MQ 消息重复怎么办？ | 用 `msg_id` 唯一约束做幂等，去重表和业务操作必须同一事务 |
| 7 | 你说的 QPS 提升，瓶颈转移到哪了？ | 按实际调优记录回答（DB 连接池 → GC → Redis 网络 → CPU） |
| 8 | 分库分表做了吗？ | 做了实验，实测 2000 万行下按分片键查仍在 XX ms，结论是……（照实说） |
| 9 | 如果要做分布式锁，你怎么做？ | `SET key value NX PX 30000` + Lua 释放（校验 value）+ 续期（看门狗） |
| 10 | 这个项目最大的难点？ | **不要答技术名词**，答"最难的是让数字可信——压测环境、一次只改一个变量、每次重置数据" |

⚠️ **第 10 题是最容易被问倒的**。答"难在 Redis 分布式锁"会显得很假（那是照着教程做的）。答"难在保证测试本身可信"才是真正做过的人才会说的话。

## 10. 风险清单

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | **内存不足导致压测数据失真** | 高 | 致命 | 压测前关 PyCharm 等（§6.5），precheck 脚本拦截 |
| R2 | 压不出瓶颈（本机配置太好） | 中 | 数据平淡 | 用资源限制（容器限 0.5 CPU、JVM 限 512MB）人为制造瓶颈 |
| R3 | 阶段 6 调优找不到瓶颈 | 中 | 卡住 | 按要求降低资源限制，逼出瓶颈；或明确记录"未触及上限" |
| R4 | ShardingSphere 版本配置格式不兼容 | 中 | 阶段 8 卡住 | 阶段 8 是可选的，先查官方文档对应版本 |
| R5 | 2000 万造数据耗时过长 | 中 | 拖慢进度 | 分批提交；接受 10–30 分钟；可降到 1000 万 |
