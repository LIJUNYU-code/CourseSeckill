## 4. 压测方法

### 4.1 为什么要先把登录拆出去

`setup()` 里一次性登录 N 个学生，把 token 传给各 VU。

如果让每个 VU 在压测循环里登录，测出来的 P95 会被 BCrypt 的 ~60 ms 吃掉——那是**登录接口**的成本，不是**抢课接口**的成本。混在一起，后面 v1 改动了抢课逻辑却看到 P95 大幅波动，会误判。

### 4.2 为什么 VU 数必须大于 capacity

100 个学生抢 100 个名额，**即使库存判断完全失效，最多也只能成功 100 单**——超卖根本压不出来。

所以设计是：**300 个不同学生抢 100 个名额**。这样「成功单数 > 100」才是超卖的硬证据。

### 4.3 为什么用 `per-vu-iterations`

```js
executor: 'per-vu-iterations', vus: 300, iterations: 1
```

每个 VU 只发 1 次请求，且 300 个 VU 几乎同时启动。目的是让 300 个请求**挤在同一个时间窗口内**，最大化「读库存 → 写库存」之间的重叠。如果用 `constant-vus` 跑 30 秒，请求会被摊平，竞态反而难复现。

### 4.4 判定口径

超卖不能靠 k6 的 `http_req_failed` 判断——那只是 HTTP 状态码统计。真正的判定要查库：

| 判据 | 含义 |
|---|---|
| `success_orders > capacity` | **超卖**，成功单数超过了名额 |
| `stock + sold != capacity` | **账不平**，说明有更新丢失 |
| `stock < 0` | 本表有 CHECK 约束，正常不会出现（v0 的失败方式是「订单多」而非「库存负」） |
| 同一学生 `status=1` 的记录 > 1 | 唯一索引失效 |

### 5.2 关键发现：`stock` 只掉了 4，而不是掉到 0

第 2~4 轮卖出 300 单，但 `stock` 从 100 只降到 **96**。

这不是 bug，这**恰恰是丢失更新的直接证据**：

```
假设 8 个线程同时读到 stock = 100
  线程 A: 算 99 → 写回 99   ✅ 生效
  线程 B: 算 99 → 写回 99   ❌ 覆盖（值一样，看不出来）
  线程 C: 算 99 → 写回 99   ❌ 覆盖
  ... 其余 5 个线程同理
结果：stock 只减了 1，但 8 个学生都拿到了订单
```

而 `sold = sold + 1` 是**数据库端原子累加**，300 次请求就老实加 300。

**一个减得慢、一个加得准，两者的和必然越跑越偏**——这就是 `conservation_gap = −296` 的来源。

> 这条比「超卖了多少单」更有教学价值：它说明超卖的**机制**是丢更新，不是「判断写错了」。

### 5.3 串行对照为什么必须做

同一个接口、同一份代码、同一批 110 个学生，只是**不并发**（1 个 VU 挨个请求）：

```
成功 = 100    名额已满 = 10    其它 = 0
stock = 0     sold = 100     gap = 0
```

**完全正确**。

这一轮排除了三种可能的错误归因：

1. 不是「代码逻辑写错了」—— 单线程下 100 个名额卖 100 份，第 101 个正确拒绝；
2. 不是「种子数据有问题」—— 同样的数据串行就对；
3. 不是「压测工具造假」—— 同样的 k6 脚本，只改了 VU 数。

**剩下的唯一变量就是并发**。这是「先复现问题，再解决问题」原则的落地：我们证明了问题是并发引起的，而不是猜的。

### 5.4 超卖随并发单调增长

| 并发 | 超卖 | 超卖率 |
|---|---|---|
| 1（串行） | 0 | 0% |
| 110 | +10 | 10% |
| 300 | +200 | **200%** |

这条曲线的意义：**并发越高，丢更新越严重**。110 并发时只是「偶尔两个人同时读到同一个值」，300 并发时几乎所有人都在同一个时间窗口里撞车，库存判断完全失效。

反过来说，如果 v1 修好了，这条曲线应该变成一条**水平线**：并发从 1 涨到 300，超卖始终是 0。

### 5.5 第 1 轮的 51 个失败请求（已排除干扰）

第 1 轮（首次 300 并发）有 51 个请求 `biz_other`：

```
dial tcp 127.0.0.1:8080: connectex: No connection could be made
because the target machine actively refused it.
```

原因：Hikari 连接池在应用启动后是懒加载的，第一个请求才建连接。300 个请求同时到达时，51 个在连接池初始化完成前就被拒了。

**这是冷启动噪声，不是 v0 的缺陷。** 第 2 轮起预热过，`biz_other = 0`，`http_req_failed = 0.00%`。

后续版本压测前，**先发 1 个请求预热连接池**，否则第一轮数据不可用。

## 6. 机制拆解

v0 的 `SeckillServiceImpl.seckill()` 关键三段：

```java
// ① 普通读，不加锁
CourseStock stock = courseStockMapper.selectByCourseId(courseId);

// ② 在 Java 里判断
if (stock.getStock() <= 0) throw new BusinessException(ResultCode.CONFLICT, "该课程名额已满");

// ③ 把 Java 里算好的绝对值写回去
courseStockMapper.absoluteUpdate(courseId, stock.getStock() - 1);
```

对应的 SQL：

```sql
UPDATE course_stock SET stock = #{newStock}, sold = sold + 1 WHERE course_id = #{courseId}
```

**问题出在第 ③ 步的 `stock = #{newStock}`**：写的是「我以为库存应该是多少」，而不是「在现有基础上减一」。

两个请求并发时：

| 时刻 | 请求 A | 请求 B | 实际 `stock` |
|---|---|---|---|
| T1 | 读到 1 | — | 1 |
| T2 | — | 读到 1 | 1 |
| T3 | 判断 1 > 0，放行 | — | 1 |
| T4 | — | 判断 1 > 0，放行 | 1 |
| T5 | 写 `stock = 0` | — | 0 |
| T6 | — | 写 `stock = 0` | 0 |
| 结果 | **拿到订单** | **拿到订单** | **0** |

**1 个名额卖给了 2 个人，而库存显示 0——账面上根本看不出超卖。**

这就是为什么判定必须查 `seckill_order` 表数订单，不能看 `stock`。

### 为什么第 ① 步没有 `@Transactional` 是「故意的」

任务书 §5.3 明确要求 v0 **不加事务**。原因：

- 加了事务，`UPDATE` 失败时会把订单一起回滚，「订单多出来」的现场就被抹掉了；
- v0 的语义是「每一步单独看都成功，整体是错的」——这正是超卖类 bug 最难查的地方。

**这是教学设计，不是疏忽。** v1 修复时也不靠加事务解决，靠的是让 `UPDATE` 自己带条件：

```sql
-- v1 的写法（本阶段不实现）
UPDATE course_stock SET stock = stock - 1, sold = sold + 1
WHERE course_id = ? AND stock > 0
-- 然后检查 affected rows；返回 0 就说明抢完了
```

## 7. 结论

| 结论 | 证据 |
|---|---|
| v0 **会超卖**，且极度容易复现 | 4 轮并发压测全部超卖；110 并发就超卖 10 单 |
| 超卖**随并发单调放大** | 1 并发 → 0；110 并发 → +10（10%）；300 并发 → +200（200%） |
| 超卖**不是代码写错**，是竞态 | 串行 110 个学生 → 精确卖出 100、拒绝 10、账目 gap = 0 |
| 真正的机制是**丢失更新** | `stock` 只降 4 却卖出 300 单；`sold` 累加准确（原子 +1） |
| 库存账面**无法反映超卖** | 卖出 300 单后 `stock` 仍显示 96 |
| 数据库 `CHECK (stock >= 0)` **不防超卖** | 它只保证库存不为负，不保证「订单数 ≤ 名额」 |

**这一版故意保留的缺陷，就是 v1 要修的东西。** v1 的验收标准是：同样的 300 VU、同样的课程，`success_orders = 100`、`conservation_gap = 0`。

## 8. 已知局限（不要过度解读这些数字）

1. **这不是生产级压测**。单机同时跑 MySQL、应用和 k6，三者抢同一份 CPU 和内存。生产环境是分开部署的。报告里的 P95 = 572 ms 反映的是「单机三合一」的成本，不能当作接口性能指标对外引用。
2. **没有测长稳压测**。本次是 300 VU 打一发就结束（约 18 秒）。持续 10 分钟的高压下，连接池耗尽、GC 抖动、慢 SQL 累积等长尾问题都没有暴露。
3. **单机 MySQL 没有调优**。`innodb_buffer_pool_size`、`max_connections` 都是默认值。v4 调优阶段才会碰这些。
4. **只测了「单课极限」场景**。任务书 §6.3 的 B（多课分散）、C（读写混合）、D（重复点击）三个场景尚未跑。
5. **超卖数不是「精确值」**。300 个学生全部成功（`biz_success = 300`），说明这一轮的库存判断**完全失效**，而不是「偶尔漏一两个」。不同机器、不同时刻跑出来的具体数字会变，但「超卖严重」这个结论稳定可重复。

## 11. 本轮踩到的三个坑（写脚本时值得记住）

### 11.1 `.ps1` 文件恰恰需要 UTF-8 BOM

前面反复强调「Java / 中文文件不要用 PowerShell `Set-Content`，会写 BOM 导致编译失败」。但 **`.ps1` 文件是反例**：

```
注: PowerShell 5.1 默认按 ANSI(GBK) 读取 .ps1 文件。
若文件是无 BOM 的 UTF-8，中文注释会被解码成乱码，
进而把注释里的引号/括号吃掉 → ParserError:
  表达式或语句中包含意外的标记"鎵句笉鍒?$cfgPath"
```

修法是给 `.ps1` 加 BOM：

```powershell
$txt = [System.IO.File]::ReadAllText($f, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($f, $txt, (New-Object System.Text.UTF8Encoding($true)))
```

**判据**：`ReadAllBytes` 前 3 字节是 `239,187,191`（EF BB BF）。
`.java`、`.js`、`.yaml` 要 `239,187,191` **不存在**；`.ps1` 要**存在**。同一条「不要 BOM」的规则，对不同扩展名结论相反。

### 11.2 mysql 的密码怎么传（试错了两轮）

| 方式 | 结果 |
|---|---|
| `-p$pw` 命令行参数 | 能用，但 mysql 往 **stderr** 打 `[Warning] Using a password on the command line interface can be insecure`。PowerShell 5.1 把原生程序 stderr 当成 `NativeCommandError`，配合 `$ErrorActionPreference='Stop'` **直接中断脚本**，exit=1 |
| `MYSQL_PWD` 环境变量 | **本机这个 mysql 客户端不认**，报 `ERROR 1045 (28000): Access denied for user 'root'@'localhost'` |
| 临时 option file | ✅ 正解 |

```powershell
$cnf = Join-Path $env:TEMP ("seckill-mysql-" + [guid]::NewGuid().ToString('N') + ".cnf")
[System.IO.File]::WriteAllText($cnf, "[client]`r`nuser=root`r`npassword=$pw`r`n", ...)
& $mysql "--defaults-extra-file=$cnf" -e $sql
# finally 里 Remove-Item $cnf
```

密码既不进命令行、也不打 warning，还能让脚本干净地 `exit=0`。

### 11.3 `source` 读 SQL 文件要用正斜杠

Windows 路径 `D:\software\...\x.sql` 里的反斜杠会被 mysql 客户端当成转义符吃掉。要先 `-replace '\\','/'`。
