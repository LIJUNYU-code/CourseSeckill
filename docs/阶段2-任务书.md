## 0. 这一阶段为什么反直觉

绝大多数教程教你"避免 bug"。这一阶段要求你**主动制造一个 bug**，并且要能稳定复现它。

理由（原则 P1：先复现问题再解决）：

- 没有 v0 的超卖，v1 加锁就变成"抄一段 `FOR UPDATE`"，你不知道它在解决什么。
- 没有 v0 的数字（比如 149 人抢到 100 个名额），v1 的"零超卖"就没有对照物，说"优化了"是空话。
- 面试官问"你做过性能优化吗"，说"我加了 Redis"是背课文；说"我的基线在 300 并发下超卖 49 个名额，QPS 420，P99 1.8 秒"才是做过。

所以本阶段的验收标准是：**压测跑完，`seckill_order` 里成功订单数 > 100。**

## 4. 🔴 本阶段最核心的一节：v0 到底该怎么写才会超卖

### 4.1 三种写法，只有一种会超卖

假设 `stock = 1`，两个线程 A、B 同时抢。

**写法一：`UPDATE ... SET stock = stock - 1`（无条件）**

```java
stockMapper.decr(courseId);   // UPDATE course_stock SET stock = stock - 1 WHERE course_id = ?
```

这条 UPDATE 本身是**原子的**，数据库会给行加排他锁，A 执行完 stock=0，B 执行完 stock=-1。
→ 但 `ck_stock_non_negative` 会让 B 直接报 `ERROR 3819`，整个请求 500。
→ **在你这张表上，这种写法写不出负库存，只能写出 500。**

**写法二：在 Java 里算好绝对值，再写回去（🔴 本阶段就用这个）**

```java
CourseStock cs = stockMapper.selectByCourseId(courseId);   // 普通 SELECT，不加锁
if (cs.getStock() <= 0) throw new BusinessException(409, "该课程名额已满");
int newStock = cs.getStock() - 1;                           // 在内存里减
stockMapper.absoluteUpdate(courseId, newStock);             // UPDATE ... SET stock = #{newStock}, sold = sold + 1
```

A 和 B 都读到 `stock=1`，都算出 `newStock=0`，**都写 0**。
→ 两次写入都成功（写 0 不违反 CHECK），但库存只减了 1 次，**却卖出了 2 个名额**。
→ 这叫**丢失更新（lost update）**，是本阶段要复现的核心。

**写法三：`SELECT ... FOR UPDATE` / 乐观锁 / Lua**

这是 v1、v2 要做的事，**本阶段一律不准用**。用了就没有基线了。

### 4.2 为什么推荐写法二而不是"把 CHECK 删掉看负库存"

| | 写v0-A：保留 CHECK + 绝对值写回 | 写v0-B：DROP CHECK + 无条件 `stock-1` |
|---|---|---|
| 要改表结构 | 不用 | 要（且 v1 前必须加回来，容易忘） |
| 超卖证据 | 成功订单数 > capacity | 成功订单数 > capacity **且** stock < 0 |
| 数据是否还能自愈 | 是（reset 即可） | 是 |
| 额外收获 | 能看到 `stock + sold ≠ capacity` 两个指标同时崩 | 只有负库存一个视觉冲击 |
| 风险 | 无 | 忘了加回 CHECK，v1 之后的数据全脏 |

**结论：用写法二。** 你会同时看到两个独立证据：
- `success_orders = 149 > capacity = 100`（超卖）
- `stock + sold = 93 + 149 = 242 ≠ 100`（守恒被破坏）

`stock` 不会是负数 —— **不是你没复现成功，是数据库的 CHECK 在兜底**。这一点必须在压测报告里写清楚，否则 v1 之后你会以为"加了锁所以库存不变负了"，其实一直是 CHECK 挡着。

### 4.3 `CourseStockMapper` 需要的两个方法

```java
package com.example.seckill.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.example.seckill.entity.CourseStock;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;
import org.apache.ibatis.annotations.Update;

@Mapper
public interface CourseStockMapper extends BaseMapper<CourseStock> {

    /** 普通读：不加锁。v0 的竞态就发生在这条 SELECT 与下面那条 UPDATE 之间 */
    @Select("SELECT * FROM course_stock WHERE course_id = #{courseId}")
    CourseStock selectByCourseId(@Param("courseId") Long courseId);

    /**
     * 🔴 v0 的"犯罪现场"：把 Java 里算好的绝对值写回去。
     * 它自己没错，错在调用它之前没有锁、没有版本校验。
     */
    @Update("UPDATE course_stock SET stock = #{newStock}, sold = sold + 1 WHERE course_id = #{courseId}")
    int absoluteUpdate(@Param("courseId") Long courseId, @Param("newStock") int newStock);
}
```

`SeckillOrderMapper` 不需要自定义方法，`BaseMapper` 的 `selectOne/insert/updateById` 够用。

### 5.2 订单号生成

`order_no` 是 `varchar(40)` + 唯一索引。本阶段不要引入雪花算法（阶段 8 才需要），用：

```java
private String generateOrderNo(Long studentId) {
    return System.currentTimeMillis() + String.format("%04d", studentId % 10000)
            + String.format("%04d", ThreadLocalRandom.current().nextInt(10000));
}
```

长度 13+4+4 = 21 位，唯一性够用。**为什么带 studentId**：压测时如果撞唯一键，你能一眼看出是"同一学生重复点击"还是"纯随机碰撞"。

### 5.3 `SeckillServiceImpl` 骨架（v0，故意不加保护）

```java
@Service
@AllArgsConstructor
@Slf4j
@ConditionalOnProperty(name = "seckill.strategy", havingValue = "v0-baseline", matchIfMissing = true)
public class SeckillServiceImpl implements SeckillService {

    private final CourseMapper courseMapper;
    private final CourseStockMapper courseStockMapper;
    private final SeckillOrderMapper orderMapper;

    @Override
    public SeckillResponse seckill(Long courseId, Long studentId) {
        // 1. 课程存在性
        Course course = courseMapper.selectById(courseId);
        if (course == null) throw new BusinessException(ResultCode.NOT_FOUND, "课程不存在");

        // 2. 时间窗口（R7 的替代实现，因为 course 表没有 status 列）
        LocalDateTime now = LocalDateTime.now();
        if (now.isBefore(course.getStartTime()) || now.isAfter(course.getEndTime())) {
            throw new BusinessException(ResultCode.CONFLICT, "课程尚未开放选课");
        }

        // 3. 读库存（普通读，不加锁）—— 竞态窗口从这里开始
        CourseStock stock = courseStockMapper.selectByCourseId(courseId);
        if (stock == null) throw new BusinessException(ResultCode.NOT_FOUND, "课程不存在");
        if (stock.getStock() <= 0) throw new BusinessException(ResultCode.CONFLICT, "该课程名额已满");

        // 4. 查重（R2 / R6）
        SeckillOrder exist = orderMapper.selectOne(new LambdaQueryWrapper<SeckillOrder>()
                .eq(SeckillOrder::getStudentId, studentId)
                .eq(SeckillOrder::getCourseId, courseId)
                .in(SeckillOrder::getStatus, 0, 1));
        if (exist != null) throw new BusinessException(ResultCode.CONFLICT, "你已选过该课程");

        // 5. 绝对值写回 —— 丢失更新的发生点
        courseStockMapper.absoluteUpdate(courseId, stock.getStock() - 1);

        // 6. 落订单
        SeckillOrder order = SeckillOrder.builder()
                .orderNo(generateOrderNo(studentId))
                .studentId(studentId).courseId(courseId)
                .status(SeckillOrder.STATUS_SUCCESS).build();
        orderMapper.insert(order);   // uk_student_course 是最后一道防线，并发重复点击会在这里撞键

        return new SeckillResponse(order.getOrderNo(), order.getStatus());
    }
}
```

🔴 **两个必须做的选择**（否则复现不出来）：

1. **方法上不加 `@Transactional`。**
   加了事务反而可能因为 UPDATE 失败（CHECK）而回滚掉订单，"订单多出来"就被掩盖了。
   v0 的语义就是"每一步都成功，但整体是错的"。

2. **第 5 步和第 6 步之间可以插入一个"竞态窗口放大器"**（见 §6），否则本机并发不够时复现不稳定。

⚠️ 归还名额时如果要加 `CHECK (stock + sold <= capacity)` 类似的判断，注意本表**没有**这个约束，`stock` 加多了不会报错，只会数据变脏。

### 5.5 分页（偏差 4 的修复）

新建 `config/MybatisPlusConfig.java`：

```java
@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));

```

**不加这个，`orderMapper.selectPage(...)` 会把整表拉进内存。** 现在 `seckill_order` 是 0 条，压测后变成几百条看不出问题；等阶段 8 造 2000 万行，一次 `/api/order/my` 就能把你内存打爆。

### 5.6 唯一键冲突处理（偏差 5 的修复）

`GlobalExceptionHandler` 补一个：

```java
@ExceptionHandler(org.springframework.dao.DuplicateKeyException.class)
public ResponseEntity<Result<Void>> handleDuplicateKey(DuplicateKeyException e) {
    log.warn("唯一键冲突: {}", e.getMostSpecificCause().getMessage());

            .body(Result.error(ResultCode.CONFLICT, "操作冲突，请勿重复提交"));
}
```

不加这条，压测里并发重复点击会全部变成 500，k6 的 5xx 指标就没法看了。

## 6. 🔬 竞态窗口放大器（本机内存不够时的救命手段）

### 6.1 为什么需要它

本机总内存 15.6 GB，但实测可用常在 3~5 GB。300~500 并发时 JVM 和 MySQL 都在抢内存，**你未必能稳定复现超卖**。
"跑 3 次只超卖 1 次"是没用的 —— 无法证明因果关系。

### 6.2 做法

在 `application.yaml` 的 `seckill:` 下加一个配置：

```yaml
seckill:
  strategy: v0-baseline
  queue-timeout-ms: 3000
  # 🔬 竞态窗口放大器：单位毫秒。>0 时在第 3 步 SELECT 与第 5 步 UPDATE 之间 sleep。
  # 正常压测保持 0；复现不稳定时临时改成 20~50。
  # 它不是作弊 —— 它是把"1 微秒的窗口"放大成"20 毫秒的窗口"，
  # 让 10 个并发就能稳定复现 500 并发才会出现的现象。这叫"可控复现"。
  window-delay-ms: 0
```

```java
@Value("${seckill.window-delay-ms:0}")
private long windowDelayMs;

// 在第 4 步之后、第 5 步之前：
if (windowDelayMs > 0) {
    try { Thread.sleep(windowDelayMs); } catch (InterruptedException ignored) { Thread.currentThread().interrupt(); }
}
```

### 6.3 怎么用

| 场景 | 配置 | 期望 |
|---|---|---|
| 正式压测（记录进报告） | `window-delay-ms: 0`，300 VU | 超卖但数字随机，取决于真实调度 |
| 验证"我确实有竞态" | `window-delay-ms: 30`，10 VU × 10 次 | **稳定**超卖，且每次结果高度相似 |
| 给 v1 做对照 | 同样 `30` + 10 VU | v1 必须变 0 超卖 |

⚠️ 报告里必须写明用了哪个值。用放大窗口得出来的 QPS **不能**当作性能数据（sleep 会拉低 QPS），只能用来证明"正确性缺陷存在"。

```javascript
import http from 'k6/http';
import { check } from 'k6';
import { BASE_URL, STUDENT_PREFIX, STUDENT_START, PASSWORD } from './config.js';

/** 生成 S000000001 这种 10 位学号 */
export function studentNo(index) {
  return STUDENT_PREFIX + String(STUDENT_START + index).padStart(6, '0');
}

/** 登录并返回 token；失败返回 null（不要 throw，让 setup 能统计失败数） */
export function login(account) {
  const res = http.post(
    `${BASE_URL}/api/auth/login`,
    JSON.stringify({ account, password: PASSWORD }),
    { headers: { 'Content-Type': 'application/json' } }
  );
  if (res.status !== 200) return null;
  return res.json('data.token');
}

export function loginStudent(index) {
  const account = studentNo(index);
  const token = login(account);
  if (token) check(token, { 'token 非空': (t) => t.length > 20 });
  return { account, token };
}
```

### 7.3 `loadtest/seckill-single.js`（场景 A）

```javascript
import http from 'k6/http';
import { check } from 'k6';
import { Counter } from 'k6/metrics';
import { BASE_URL, COURSE_ID } from './config.js';
import { loginStudent } from './lib/auth.js';

// 业务结果分桶：这是"能说清发生了什么"的关键，比总 QPS 有用得多
const success   = new Counter('biz_success');
const soldOut   = new Counter('biz_sold_out');
const duplicate = new Counter('biz_duplicate');
const other     = new Counter('biz_other');

// 关键：在 setup 里预登录，避免把 BCrypt 的 60ms 算进压测耗时
export function setup() {
  const users = [];
  for (let i = 0; i < Number(__ENV.VUS || 300); i++) {
    const u = loginStudent(i);
    if (u.token) users.push(u);
  }
  if (users.length === 0) throw new Error('没有任何学生登录成功，先检查后端是否在跑');
  console.log(`setup 完成：${users.length} 个学生 token`);
  return { users };
}

export const options = {
  scenarios: {
    rush: {
      executor: 'shared-iterations',   // 总请求数固定，便于对比
      vus: Number(__ENV.VUS || 300),
      iterations: Number(__ENV.ITERATIONS || 300),
      maxDuration: '120s',
    },
  },
  // 注意：409 在本场景里是【预期业务拒绝】，不是错误。
  // 所以 threshold 只卡 5xx 与延迟，不卡 http_req_failed。
  thresholds: {
    'http_req_duration': ['p(95)<3000'],
    'http_req_failed{expected_response:true}': ['rate<0.05'],
  },
};

export default function (data) {
  const me = data.users[(__VU - 1) % data.users.length];
  const res = http.post(`${BASE_URL}/api/seckill/${COURSE_ID}`, null, {
    headers: { Authorization: `Bearer ${me.token}` },
  });

  const code = res.json('code');
  if (res.status === 200) success.add(1);
  else if (code === 409) {
    const msg = res.json('message') || '';
    if (msg.includes('名额已满')) soldOut.add(1);
    else if (msg.includes('已选过')) duplicate.add(1);
    else other.add(1);
  } else other.add(1);

  check(res, {
    '响应是 200 或 409': (r) => r.status === 200 || r.status === 409,
    '没有 5xx': (r) => r.status < 500,
  });
}

export function teardown(data) {
  console.log(`可用 token 数：${data.users.length}`);
}
```

### 7.4 🔴 k6 的一个致命陷阱（本项目最危险的一条）

**k6 的 `http_req_failed` 把 HTTP 状态码 >= 400 全部算作失败。**
本场景 300 个请求抢 100 个名额，正常就有 ~200 个 409。如果你把 threshold 写成 `http_req_failed: ['rate<0.05']`，k6 会判定失败并返回非零退出码 —— 但你的代码其实完全正常。

**更危险的反向情况**：v0 的超卖如果因为某个异常被 `Exception` 兜底成 **HTTP 500**，`http_req_failed` 会显示"失败率高"，但如果你只看 `biz_success` 计数器，会以为"只成功了 100 个，没超卖"。所以**最终判据必须以数据库为准**，不能只看 k6 输出。

### 8.2 🔴 判定 SQL（修正了文档里 capacity 查错表的问题）

```sql
SELECT
  cs.capacity,
  cs.stock,
  cs.sold,
  (SELECT COUNT(*) FROM seckill.seckill_order o
     WHERE o.course_id = cs.course_id AND o.status = 1) AS success_orders,
  cs.stock + cs.sold - cs.capacity                          AS conservation_gap,
  (SELECT COUNT(*) FROM seckill.seckill_order o
     WHERE o.course_id = cs.course_id AND o.status = 1) - cs.capacity AS oversold_by
FROM seckill.course_stock cs
WHERE cs.course_id = 88;
```

### 8.3 四条判据（满足第 1 条即算复现成功）

| # | 判据 | 期望（v0） | 含义 |
|---|---|---|---|
| **1** | `success_orders > capacity` | 例如 149 > 100 | **超卖**：卖出名额多于总名额 |
| 2 | `stock + sold != capacity` | 例如 93+149=242 ≠ 100 | **丢失更新**：库存被覆盖写，`sold` 却累加了 |
| 3 | `stock` < 0 | **不会出现** | 被 `ck_stock_non_negative` 挡住，属正常，不是失败 |
| 4 | 同一学生有 2 条 status=1 | **不会出现** | `uk_student_course` 挡住，说明唯一索引生效 |

⚠️ 判据 3、4 的"不会出现"是**好消息**，要写进报告。它们证明"数据库的兜底约束在工作，问题出在应用层的读-改-写"。v1 要修的是应用层，不是数据库约束。

### 8.4 稳定性要求

**连跑 3 次，3 次都要 `success_orders > 100`。** 如果只有 1~2 次超卖：
- 先把 `window-delay-ms` 调到 20~30（§6），这是可控复现
- 再把 VU 从 300 提到 500
- 报告里如实写"用放大器复现"，不要假装是原始并发下的数据

## 附：与《项目开发文档》§5.2 的差异说明

文档 §5.2 的 v0 伪代码写的是 `stockMapper.decrStock(courseId)`（即 `stock = stock - 1`），并预期"库存变负数"。
实测发现这条路径在 MySQL 8.0.45 + `CHECK (stock >= 0)` 下会直接 `ERROR 3819`，无法产生负库存，只能产生 500。

本任务书因此把 v0 改为"Java 内计算 + 绝对值写回"，超卖证据从"负库存"改为"成功订单数 > capacity 且 stock+sold ≠ capacity"。
**这一改动已同步记录到压测报告的 v0 章节，后续 v1 对照时都以"成功订单数"为唯一口径，不再看库存正负。**
