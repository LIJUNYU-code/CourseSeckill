## 0. 先说清楚：多实例到底会坏在哪

单实例时很多"看起来没问题"的写法，在多实例下会变成真 bug。我逐个查了当前代码，
按**严重程度**排出来：

| # | 位置 | 单实例为什么没事 | 多实例会怎样 | 严重度 |
|---|---|---|---|---|
| ① | `SeckillOrderConsumer.java:59-63` 幂等闸 | 同一条消息不会被两个线程同时处理 | 两个实例同时拿到同一 msgId，`insert` 一个成功一个撞唯一索引 → **但两个都进了事务**，撞索引的那个抛 `DuplicateKeyException` → 转成 `DuplicateMessageException` → ack。**看起来是对的** | ⚠️ 见下面详解 |
| ② | `PendingOrderSweeper.java` 每分钟扫 | 只有一个实例在扫 | 两个实例同时扫到同一批 PENDING → 都调 `updateStatusAndFailReason`（CAS，只有一个成功）→ **但 Redis 归还没有 CAS 保护**，见下 | 🔴 会多还 |
| ③ | `StockReconciler.java` 每 5 分钟对账 | 只有一轮在跑 | 两个实例同时发现同一门课偏高 → 都调 `preheat` → 结果一样（都是写 MySQL 的 stock），**幂等** | ✅ 无害 |
| ④ | `SeckillServiceImplV3MqAsync.java:99` 订单号生成 | 单进程内 `currentTimeMillis + 随机数` 够用 | 两个实例同一毫秒 + 同 studentId + 同随机数 → `uk_order_no` 撞 → `DuplicateKeyException` 直接 500 | 🟡 概率低但真实 |
| ⑤ | 日志 | 一个进程，所有行都是它 | 三份日志混在一起，出问题不知道是谁干的 | 🟡 排查成本 |
| ⑥ | `mq_consume_log` 表 | 见 ① | **表会无限增长**，且"处理中"状态的行永远没人清理 | 🟡 |

下面逐条拆。

## 1. ① 幂等闸：看起来对，但有个洞

### 1.1 当前实现

`src/main/java/com/example/seckill/infra/mq/SeckillOrderConsumer.java:52-88`：

```java
private void handle(SeckillMessage message) {
    transactionTemplate.executeWithoutResult(status -> {
        // ① 幂等闸
        MqConsumeLog consumeLog = MqConsumeLog.builder()
                .msgId(message.msgId())
                .status(0)
                .build();
        try {
            mqConsumeLogMapper.insert(consumeLog);      // 靠 uk_msg_id 唯一索引挡重复
        } catch (DuplicateKeyException e) {
            throw new DuplicateMessageException("重复消息");   // 跳出事务
        }
        // ② 扣库存 ...
```

### 1.2 为什么单实例下没问题、多实例下"看起来"也没问题

两个实例同时收到同一 msgId：

```
实例 A: BEGIN → INSERT msg_id=X → 拿到行锁 → 继续扣库存 → COMMIT
实例 B: BEGIN → INSERT msg_id=X → 等锁（InnoDB 唯一索引会阻塞等待）
                              → A 提交后 B 拿到 1062 → catch → 抛 DuplicateMessageException → ROLLBACK → ack
```

**结论：这条其实是对的**，InnoDB 的唯一索引 + 行锁天然解决了跨实例并发。
`DuplicateKeyException` 会从 `insert` 抛出，被 catch 后转成 `DuplicateMessageException`，
`onMessage` 里正常 ack。

### 1.3 但有一个真问题：`mq_consume_log` 会无限长

- 每条消息一行，**永不清理**。
- `status=0`（处理中）的行如果消费进程在事务提交前崩了，会永久留在表里。
  下次同 msgId 重投时 `insert` 撞唯一索引 → 被当成"重复消息"直接 ack →
  **这条订单永远停在 PENDING**（清扫会兜底，但那是 5 分钟后）。

**这不是多实例特有的问题，是"幂等表没有生命周期"的问题。** 多实例只是让它更容易暴露
（重投概率变高）。

### 1.4 要做什么

**A. 给 `mq_consume_log` 加时间索引 + 定期归档**（低优先级，但必须做）

```sql
-- sql/V12__mq_consume_log_index.sql
ALTER TABLE mq_consume_log ADD KEY idx_create_time (create_time);
```

清理策略二选一（推荐后者）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 删除 | `DELETE FROM mq_consume_log WHERE create_time < NOW() - INTERVAL 7 DAY LIMIT 1000` | 简单 | 删了就没法追溯 |
| **归档** | 先 `INSERT INTO mq_consume_log_archive SELECT ...` 再删 | 可追溯 | 多一张表 |

**顺带修一个文档错误**：`README.md` 的已知局限第 7 条写「超时清扫的扫描是单表的 `idx_status_start`」，
但 `seckill_order` 上**根本没有这个索引**（实测只有 `PRIMARY(id)`、`uk_order_no`、
`uk_student_course`、`idx_course_status(course_id,status)`、`idx_student_status(student_id,status)`）。
当前 `selectStalePending` 的 SQL 是：

```sql
SELECT * FROM seckill_order WHERE status = 0 AND create_time < #{deadline} ORDER BY id LIMIT #{limit}
```

没有任何索引覆盖 `(status, create_time)`，MySQL 只能按主键顺序扫、逐行过滤 `status=0`。
实测 `EXPLAIN`（当前表为空，所以 `rows=1`，但执行路径已经说明问题）：

```
type: index
possible_keys: NULL      ← 没有任何索引可用
key: PRIMARY             ← 退化成按主键全表顺序扫
Extra: Using where       ← 逐行过滤
```

数据量小的时候是毫秒级（因为 `LIMIT 200` 让它很快凑够 200 条），但 `status=0` 的行很少时
会扫过大量历史订单。**建议在 V12 里一起加**：

```sql
ALTER TABLE seckill_order ADD KEY idx_status_create (status, create_time);
```

> 加之前先 `EXPLAIN` 看一眼现在的执行计划，加之后再 `EXPLAIN` 对比，期望变成
> `type: range`、`key: idx_status_create`、`Extra: Using index condition`。
> 如果 `type` 已经是 `range` 或 `index`，说明 MySQL 选了别的路，加索引不一定有用——
> 但 `(status, create_time)` 对这条查询是很自然的组合，值得加。

**B. `status=0` 的僵尸行处理**（这个更重要）

现在的逻辑：`insert` 成功但事务回滚了（比如扣库存那步抛异常）→ 事务回滚会把 `insert` 一起撤销，
所以**不会留僵尸行**。这是对的。

但如果进程在 `COMMIT` 之后、`basicAck` 之前崩溃 → 消息会被 broker 重投 →
`insert` 撞唯一索引 → 当成重复 ack → **订单永远 PENDING**。

**修法**：`mq_consume_log` 的 `status` 改成有意义的终态，重复消息进来时**检查旧行状态**：

```java
try {
    mqConsumeLogMapper.insert(consumeLog);
} catch (DuplicateKeyException e) {
    // 不是无脑当重复：看看上次到底处理成功没有
    MqConsumeLog old = mqConsumeLogMapper.selectOne(
            new LambdaQueryWrapper<MqConsumeLog>().eq(MqConsumeLog::getMsgId, message.msgId()));
    if (old != null && old.getStatus() == 0) {
        // 上次卡在"处理中"，说明当时事务回滚了或进程崩了 → 这次要重新处理
        // 但直接重试会撞主键，所以先把它改成失败态再走正常流程
        int claimed = mqConsumeLogMapper.updateStatusIfPending(old.getId(), 3);  // 3 = 放弃旧记录
        if (claimed == 0) {
            throw new DuplicateMessageException("重复消息");  // 别人抢先了
        }
        mqConsumeLogMapper.insert(MqConsumeLog.builder()
                .msgId(message.msgId() + ":retry:" + System.currentTimeMillis())
                .status(0).build());
    } else {
        throw new DuplicateMessageException("重复消息");
    }
}
```

> ⚠️ **这一步要想清楚再写**：上面的方案引入了"同一订单可能有两条 consume_log"的复杂性。
> 更简单的做法是**接受它**——反正 `PendingOrderSweeper` 5 分钟后会兜底。
> 如果你选简单做法，就只做 A（加索引 + 归档），不做 B。
>
> **我的建议：先只做 A，B 留作"如果真遇到再做"。** 理由：B 会让幂等逻辑变复杂，
> 而它要解决的问题（进程在 COMMIT 和 ACK 之间崩溃）概率极低，且已经有兜底。

## 2. ② 超时清扫：Redis 归还没有 CAS 保护 🔴

### 2.1 当前实现

`src/main/java/com/example/seckill/infra/schedule/PendingOrderSweeper.java`：

```java
public int sweepOnce(LocalDateTime now) {
    LocalDateTime deadline = now.minusMinutes(pendingTimeoutMinutes);
    List<SeckillOrder> stale = seckillOrderMapper.selectStalePending(deadline, batchSize);
    int swept = 0;
    for (SeckillOrder order : stale) {
        int affected = seckillOrderMapper.updateStatusAndFailReason(
                order.getOrderNo(), SeckillOrder.STATUS_FAILED, "处理超时");
        if (affected == 0) {
            continue;                                    // 抢输了，跳过
        }
        stockCacheService.incrementIfPresent(order.getCourseId());   // ← 这里
        swept++;
    }
    return swept;
}
```

### 2.2 多实例会怎样

两个实例的定时器同时触发（默认都是 `initialDelay=30s` + `fixedDelay=60s`，
**启动时间相近就会一直同步**）：

```
实例 A: selectStalePending → 拿到订单 X
实例 B: selectStalePending → 也拿到订单 X

实例 A: updateStatusAndFailReason(X) → affected=1（赢了）→ incrementIfPresent → Redis +1
实例 B: updateStatusAndFailReason(X) → affected=0（输了）→ continue  ← 这里是对的！
```

**看起来没问题**：`affected == 0` 就 `continue`，不会多还。

**但有一个真实的窗口**：`updateStatusAndFailReason` 的 SQL 是

```sql
UPDATE seckill_order SET status=#{newStatus}, fail_reason=#{failReason}
WHERE order_no=#{orderNo} AND status=0
```

两个实例的 `UPDATE` 会**串行**（行锁），第一个拿到 affected=1，第二个拿到 affected=0。
**这个是安全的**。

### 2.3 那到底哪里会坏？

**坏在"同一订单被两个不同的机制同时处理"**：清扫和消费者。

```
T1  实例 A 的清扫：发现订单 X 超时 → UPDATE ... WHERE status=0 → affected=1 → Redis +1
T2  消费者（实例 B）：处理订单 X 的消息 → 幂等闸过 → tryDecrement（MySQL -1）
                    → updateStatusByOrderNo（WHERE status=0）→ affected=0
                    → returnStock（MySQL +1）→ 正常 ack
```

结果：Redis +1（清扫）且 MySQL 净变化 0（-1 再 +1）→ **Redis 偏高 1**。
对账会在 5 分钟内修回来，**但在这 5 分钟里 Redis 多了一个名额**。

**这也不是多实例特有的**——单实例下清扫和消费者也会撞。所以这个 bug **现在就存在**，
只是概率低（要求订单刚好在 5 分钟边界上）。

### 2.4 要做什么

**A. 把清扫的扫描条件改得更保守**（推荐，改动最小）

现在是 `create_time < now - 5min`。改成 `create_time < now - 5min AND update_time = create_time`
（即"从创建到现在没被任何人动过"）：

```sql
SELECT * FROM seckill_order
WHERE status = 0
  AND create_time < #{deadline}
  AND update_time = create_time      -- ← 新增：没被消费者碰过
ORDER BY id
LIMIT #{limit}
```

理由：消费者处理订单时会 `UPDATE ... status=1`，`update_time` 会因为
`ON UPDATE CURRENT_TIMESTAMP` 自动变。所以 `update_time = create_time` 意味着
"这条订单从插进去到现在没人动过"，正是清扫该处理的。

**B. 加分布式锁避免多个实例同时扫**（可选，见 §4）

如果做了 A，多实例同时扫也不会互相干扰（CAS 已经挡住了），
所以 B 不是必需的。**别为了"用上分布式锁"而加锁。**

## 3. ③ 库存对账：其实是安全的

两个实例同时发现课程 88 偏高（Redis 105、DB 100）→ 都调 `preheat(88)` →
`preheat` 是 `SET seckill:stock:88 = <MySQL 的 stock>`，**写的是同一个值，幂等**。

**唯一的小浪费**是两倍日志、两倍 `SELECT`。如果在意，可以加个 `SETNX` 让同一轮只有一个实例干活：

```java
// StockReconciler.java 的 reconcile() 开头
String lockKey = "seckill:lock:reconcile";
Boolean got = stringRedisTemplate.opsForValue()
        .setIfAbsent(lockKey, instanceId, Duration.ofSeconds(60));
if (!Boolean.TRUE.equals(got)) {
    return;   // 别的实例正在跑，这轮跳过
}
try {
    // ... 原来的逻辑
} finally {
    stringRedisTemplate.delete(lockKey);   // ⚠️ 见 §4.2 的坑
}
```

**我的建议：不做。** 对账是幂等的，加锁只省一点日志，却引入"锁没释放导致对账永久停摆"的新风险。

## 4. ④ 订单号生成：概率低但真实

### 4.1 当前实现

`src/main/java/com/example/seckill/service/impl/SeckillServiceImplV3MqAsync.java:41-44`：

```java
private String generateOrderNo(Long studentId) {
    return System.currentTimeMillis() + String.format("%04d", studentId % 10000)
            + String.format("%04d", ThreadLocalRandom.current().nextInt(10000));
}
```

格式：`13 位毫秒 + 4 位学号尾 + 4 位随机` = 21 位。

### 4.2 碰撞概率

同一毫秒内，同一个学生（学号尾相同）要撞上同一个随机数：
`1/10000`。如果同一毫秒内有 N 个请求来自同一学号尾的学生，
碰撞概率约 `N²/2/10000`。**实际几乎不可能**。

但**多实例不改变这个概率**（随机数空间一样）。所以这条其实**不是多实例问题**。

### 4.3 真正该改的

`uk_order_no` 撞了会抛 `DuplicateKeyException`，而 `GlobalExceptionHandler` 有专门的 handler
返回 **409**。前端会看到"订单号重复"，用户一脸问号。

**更好的做法**：撞了就重试一次（换随机数），而不是把 409 抛给用户。

```java
private String generateOrderNo(Long studentId) {
    // 21 位：13 毫秒 + 4 学号尾 + 4 随机
    return System.currentTimeMillis()
            + String.format("%04d", studentId % 10000)
            + String.format("%04d", ThreadLocalRandom.current().nextInt(10000));
}

// 插入时重试
for (int i = 0; i < 3; i++) {
    try {
        seckillOrderMapper.insert(order);
        break;
    } catch (DuplicateKeyException e) {
        if (i == 2) throw e;                       // 三次都撞，认了
        order.setOrderNo(generateOrderNo(studentId));   // 换个号再来
    }
}
```

**但注意**：`uk_student_course(student_id, course_id)` 也会抛 `DuplicateKeyException`，
那种情况**不该重试**（说明真的重复选了）。要区分是哪个索引撞的：

```java
String msg = e.getMessage();   // "Duplicate entry 'xxx' for key 'seckill_order.uk_order_no'"
if (msg != null && msg.contains("uk_order_no")) {
    // 换号重试
} else {
    throw new BusinessException(ResultCode.CONFLICT, "你已选过该课程");
}
```

> ⚠️ 靠解析异常消息判断索引名是**脆弱的**（MySQL 版本变了消息格式可能变）。
> 更稳的做法是**先查后插**，但那样又有竞态。折中：只在 `uk_order_no` 撞时重试，
> 其它 `DuplicateKeyException` 一律当"重复选课"。这已经够用了。

**我的建议：做这个。** 它跟多实例无关，但确实是当前代码的一个真实缺陷
（`uk_order_no` 撞了会给用户返回一个莫名其妙的 409）。

## 5. ⑤ 日志：多实例下分不清谁是谁

### 5.1 现状

`src/main/resources/application.yaml` 的日志格式是 Spring Boot 默认：

```
2026-11-27T09:36:41.220+08:00  INFO 3628 --- [seckill-course] [main] c.e.s.SeckillApplication : Started ...
```

`3628` 是 PID，`[seckill-course]` 是应用名。**三个实例的 PID 不同，所以日志本身能区分**，
但你需要知道"哪个 PID 对应哪个容器"。

### 5.2 要做什么

**A. 给日志加实例标识**（推荐，5 分钟的事）

`application.yaml` 里加：

```yaml
logging:
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [${HOSTNAME:local}:${PID:-}] [%thread] %logger{36} - %msg%n"
```

或者更简单，用环境变量：

```yaml
logging:
  pattern:
    console: "%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [${INSTANCE_ID:local}] [%thread] %logger{36} - %msg%n"
```

compose 里给每个容器设不同的 `INSTANCE_ID`：

```yaml
# docker-compose.yml 的 app 服务
environment:
  INSTANCE_ID: ${HOSTNAME}     # Docker 会自动设 HOSTNAME 为容器 ID 前 12 位
```

**B. 关键日志加上 `courseId`/`orderNo`/`msgId`**（现在的日志已经大部分有了，检查一遍即可）

## 6. ⑥ 多实例部署本身：compose 怎么改

### 6.1 现在的 compose 是单实例的

```yaml
app:
  build: .
  container_name: seckill-app      # ← 这个写死了，不能 scale
  ports:
    - "8080:8080"                  # ← 端口写死了，第二个实例起不来
```

### 6.2 改法（实际采用的方案）

> 下面这版是**实施时定下来的**，与初稿不同：初稿建议直接把主文件的
> `ports` 改成 `"8080-8082:8080"`，实测发现单副本时 Docker **不保证**分配
> 区间里的第一个端口——只起 1 个副本被分到 `8082`，`localhost:8080` 直接打不开，
> 而且没有任何报错提示。所以最终把多实例配置隔离到一个独立的覆盖文件。

**主文件 `docker-compose.yml` 保持单实例**（`container_name` 删掉、端口仍是 `8080:8080`）：

```yaml
app:
  build: .
  # container_name 删掉：scale 时 Docker 会自动加序号后缀（seckill-course-app-1/-2/-3）
  ports:
    - "8080:8080"
```

**新增 `docker-compose.scale.yml`** 只放多实例才需要的东西：

```yaml
services:
  app:
    ports: !override
      - "8080-8082:8080"
    environment:
      SECKILL_RECONCILE_ENABLE: "false"
      SECKILL_PENDING_SWEEP_INITIAL_DELAY_MS: "5000"
      SECKILL_PENDING_SWEEP_INTERVAL_MS: "5000"
```

然后：

```bash
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=3
docker compose -f docker-compose.yml -f docker-compose.scale.yml ps
# 恢复单实例
docker compose -f docker-compose.yml -f docker-compose.scale.yml down
docker compose up -d
```

**四个必须知道的坑（都实测踩过）**：

| 坑 | 现象 | 原因与解法 |
|---|---|---|
| `container_name` 与 `--scale` 冲突 | `Conflict. The container name "/seckill-app" is already in use` | 删掉 `container_name`，让 Docker 自动编号 |
| 合并多文件时 `ports` 是**追加**不是替换 | `["8080:8080", "8080-8082:8080"]` 两条并存，第二个副本 `Bind for 0.0.0.0:8080 failed: port is already allocated` | 覆盖文件里写 `ports: !override` |
| 宿主机环境变量传不进容器 | 设了 `$env:SECKILL_PENDING_SWEEP_INITIAL_DELAY_MS=5000`，清扫一次都没跑、日志 0 行 | compose **只传 `environment:` 里声明过的变量**，必须写进覆盖文件 |
| `INSTANCE_ID: ${INSTANCE_ID:-}` 注入空串 | 三副本日志前缀全是 `[] []` | 变量不存在时注入的是**空字符串**，而 Spring 的 `${INSTANCE_ID:${HOSTNAME:local}}` 只在"变量缺失"时用默认值。默认不注入该变量，只在需要手工命名时取消注释 |

### 6.3 要不要加 Nginx？

如果只是验证"多实例下不重复扣库存"，**不需要 Nginx**——直接用 `8080/8081/8082` 分别压即可：

```bash
# 三个实例同时压同一门课
k6 run -e BASE_URL=http://localhost:8080 loadtest/seckill-single.js &
k6 run -e BASE_URL=http://localhost:8081 loadtest/seckill-single.js &
k6 run -e BASE_URL=http://localhost:8082 loadtest/seckill-single.js &
```

**加 Nginx 的价值**是验证"负载均衡后会话/幂等仍然正确"，但本项目是 STATELESS + JWT，
不存在会话粘性问题，所以 Nginx 是**可选**的。

> **实测**：验收时用的是单个 k6 脚本轮流打三个端口（`loadtest/_multi.js`，
> 300 VU 按 VU 序号取模分发），比开三个 k6 进程更好控总量，也能在一个报告里
> 看到全局的 `biz_queued` / `biz_rejected` 计数。

## 8. 验收标准

> **本节已于 2026-11-27 实际执行完毕，结论见每小节末尾的「实测」行。**
> 命令按当时环境写；如果你在另一台机器复现，注意 `docker compose` 需要叠加
> `-f docker-compose.scale.yml`（原因见 8.0）。

### 8.0 先看这一节：多实例必须用 scale 覆盖文件

主文件 `docker-compose.yml` 里 `app` 的端口是单个 `8080:8080`，**不能**直接
`docker compose up -d --scale app=3` —— 三个副本会抢同一个宿主机端口，报：

```
Bind for 0.0.0.0:8080 failed: port is already allocated
```

正确做法：

```bash
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=3
docker compose -f docker-compose.yml -f docker-compose.scale.yml ps
```

`docker-compose.scale.yml` 做了三件事：

| 配置 | 值 | 为什么 |
|---|---|---|
| `ports` | `!override` + `8080-8082:8080` | 主文件是单端口，必须**覆盖**而不是追加。compose 合并列表默认是追加，不写 `!override` 会变成两条并存 |
| `SECKILL_RECONCILE_ENABLE` | `false` | 对账会 `preheat` 覆盖 Redis，验收期间改 Redis 会让读数不可信 |
| `SECKILL_PENDING_SWEEP_*` | `5000` / `5000` | 让清扫 5 秒就触发，不用等默认的 30 秒 + 60 秒 |

> 为什么主文件不直接写端口区间：只起 **1 个**副本时，Docker 不保证分配区间里的
> 第一个端口。实测被分到 `8082`，于是 `localhost:8080` 直接打不开，而且**没有任何
> 报错提示**。所以单实例场景留在主文件，多实例隔离到 scale 文件。

### 8.1 三实例抢同一门课，零超卖

```bash
# 1. 复位
docker compose exec mysql mysql -uroot -p"$DB_ROOT_PASSWORD" -e "
  TRUNCATE seckill.seckill_order;
  TRUNCATE seckill.mq_consume_log;
  UPDATE seckill.course_stock SET capacity=100, stock=100, sold=0, version=0;"

# 2. 起三个实例（注意 -f 叠加）
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=3

# 3. 预热课程 88（打任意一个实例）
curl -X POST -H "Authorization: Bearer $ADMIN_TOKEN" http://localhost:8080/api/admin/cache/stock/88

# 4. 三个 k6 同时压
for p in 8080 8081 8082; do
  k6 run -e BASE_URL=http://localhost:$p loadtest/seckill-single.js &
done
wait

# 5. 查账
docker compose exec mysql mysql -uroot -p"$DB_ROOT_PASSWORD" -e "
  SELECT COUNT(*) AS orders, SUM(status=1) AS success FROM seckill.seckill_order;
  SELECT capacity, stock, sold, capacity=stock+sold AS conserved FROM seckill.course_stock WHERE course_id=88;"
```

**必须满足**：

| 指标 | 期望值 | 不满足说明什么 |
|---|---|---|
| `orders` | **100**（不是 300） | 幂等闸失效了 |
| `success` | **100** | 有订单没被消费 |
| `stock` | **0** | 有库存没扣 |
| `sold` | **100** | 有订单没记库存 |
| `capacity = stock + sold` | **true** | 账目不平，严重 bug |
| Redis `seckill:stock:88` | **0** | Redis 与 MySQL 不一致 |

> **实测（300 VU 轮流打三个实例）**：`biz_queued=100` / `biz_rejected=200`、
> `checks 100%`、P95 1.34s。查库 `orders=100 success=100 pending=0 failed=0`、
> `course_stock` 88 → `capacity=100 stock=0 sold=100`、`consume_log=100`、
> `distinct_students=100`、Redis `seckill:stock:88=0`。
> 注意 `biz_rejected=200` 里既有"抢完了"也有"已选过"，两者都是 409，不影响结论。

### 8.2 同一学生并发双击，只成功一单

```bash
# 同一个 token 并发发 10 次
for i in $(seq 1 10); do
  curl -s -X POST -H "Authorization: Bearer $STUDENT_TOKEN" \
    http://localhost:8080/api/seckill/88 &
done
wait
```

**期望**：1 个 200、9 个 409「你已选过该课程」或「操作过于频繁」，订单表只有 1 条。

> **实测**：`HTTP 200=1 / 409=9`，消息分布 `操作成功=1 / 你已选过该课程=9`；
> 库 `orders=1 success=1`、课程 77 → `stock=99 sold=1`、Redis `99`。
> **Redis 没有因为并发双击多扣**，说明阶段 9 修的 CAS 检查（`if (claimed == 0) throw`）生效。

### 8.3 三实例同时清扫，不多还 Redis

```sql
-- 造 3 条超时订单（不同课程，避免 CAS 互相干扰）
-- ⚠️ create_time 和 update_time 必须都设成 10 分钟前：
--    扫描条件是 update_time = create_time，只改 create_time 会被判成"消费者碰过"而跳过。
INSERT INTO seckill.seckill_order(order_no, student_id, course_id, status, create_time, update_time)
VALUES ('SWEEP_M1', 9001, 81, 0, NOW() - INTERVAL 10 MINUTE, NOW() - INTERVAL 10 MINUTE),
       ('SWEEP_M2', 9002, 82, 0, NOW() - INTERVAL 10 MINUTE, NOW() - INTERVAL 10 MINUTE),
       ('SWEEP_M3', 9003, 83, 0, NOW() - INTERVAL 10 MINUTE, NOW() - INTERVAL 10 MINUTE);
```

把三个实例的 `pending-sweep-initial-delay-ms` 都设成 `5000`（`docker-compose.scale.yml`
已经设好，同时触发），等 30 秒后查：

```sql
SELECT order_no, status, fail_reason FROM seckill.seckill_order WHERE order_no LIKE 'SWEEP_M%';
-- 三条都应该是 status=2, fail_reason='处理超时'

SELECT course_id, stock, sold FROM seckill.course_stock WHERE course_id IN (81,82,83);
-- stock 必须还是 100（MySQL 库存从头到尾没被扣过，清扫只还 Redis）
```

**再查 Redis**：

```bash
for c in 81 82 83; do docker compose exec redis redis-cli GET "seckill:stock:$c"; done
```

**期望**：三个都是 `100`（清扫各还 1 次，没有重复还）。

> **实测**：Redis 先各设 99，12 秒后 → `91=100 92=100 93=100`（**不是 102**）；
> 三条订单全变 `status=2 fail_reason=处理超时`；
> `course_stock` 91/92/93 全部 `capacity=100 stock=100 sold=0`，**MySQL 一行都没动**。
> 清扫日志只出现在一个实例上（其余两个 CAS 抢占失败直接 continue），证明
> 「条件更新抢占 + 只还 Redis」两条设计都对。

### 8.4 日志能分清实例

```bash
docker compose logs app | grep "订单超时未处理" | head -5
```

**期望**：能看到 `[<不同容器名>]` 前缀，知道哪条是谁打的。

> **实测**：三副本日志前缀分别是 `[ad556f47839d]` / `[bb3b8f6c3f1f]` / `[cf7df740859d]`
> （容器 ID 前 12 位，由 `HOSTNAME` 提供）。
> ⚠️ 这里有个坑：`docker-compose.yml` 里**不要**写 `INSTANCE_ID: ${INSTANCE_ID:-}`。
> 变量不存在时它会注入**空字符串**，而 Spring 的 `${INSTANCE_ID:${HOSTNAME:local}}`
> 只在"变量缺失"时用默认值、"变量存在但为空"时直接取空串 —— 日志会变成 `[] []`。
> 现在的写法是默认不注入该变量，只在需要手工命名时取消注释。

## 9. 明确不做

| 不做 | 理由 |
|---|---|
| 引入 Redis 分布式锁做清扫互斥 | 清扫已经有 CAS（`WHERE status=0`），加锁只省日志，却引入"锁没释放导致永久停摆"的新风险 |
| 给对账加锁 | 对账是幂等的（`preheat` 写同一个值），加锁纯属浪费 |
| 引入 ZooKeeper / etcd 做选主 | 本项目只有一个定时任务，用不上 |
| 把 `mq_consume_log` 换成 Redis 存幂等键 | Redis 可能丢数据（虽然有 AOF），MySQL 唯一索引更可靠；且现在这张表还能当审计日志 |
| 用 Snowflake 替换当前订单号 | 当前 21 位格式已经够用，Snowflake 需要额外的 workerId 分配机制（多实例下这本身是个新问题） |
| 做服务注册发现 | 只有 3 个实例且用固定端口，用不上 |
| 给 `mq_consume_log` 实现自动归档 | 只写了索引和两套归档方案（§1.4-A），没有落地定时清理。理由：归档策略取决于业务保留期（合规要求多久？），不是技术问题；而且本项目当前表只有几百行，提前做等于凭空增加一个会出错的定时任务 |
| 用 Nginx 做负载均衡 | STATELESS + JWT，不存在会话粘性；验证"多实例正确性"不需要它。真要上生产再说 |
| 让死信队列自动重放 | `mq_dead_letter` 是证据表不是重试队列。自动重放会引出"重放时库存早没了"的新问题，超出本阶段范围（见 README 已知局限第 8 条） |

## 10. 做完能得到什么

**四个能讲的点**：

1. **"幂等闸为什么靠数据库唯一索引而不是 Redis"** —— Redis 可能丢（AOF everysec 会丢最多 1 秒），
   MySQL 唯一索引是持久的。多实例下这个选择的优势才显现出来。

2. **"CAS 返回值必须检查"** —— 这是阶段 7 那个 bug 的延续。多实例下 CAS 从"防御并发双击"
   变成"防御跨进程并发"，同一行代码价值翻倍。

3. **"为什么对账不需要分布式锁"** —— 因为 `preheat` 是幂等写。
   **能证明"不需要锁"比"会用锁"更难，也更值钱。**

4. **"清扫条件里 `update_time = create_time` 的含义"** —— 它不是随便加的，
   而是"这条订单从创建到现在没人碰过"的判据。这种"用一个字段表达一个业务状态"的设计，
   面试官会追问。
