### 1.1 缺陷代码

`src/main/java/com/example/seckill/infra/cache/impl/StockCacheServiceImpl.java:50-62`：

`src/main/java/com/example/seckill/service/impl/SeckillServiceImplV3MqAsync.java:137-148`：

冷启动 + 并发涌入 = 所有请求同时拿到 `-1`。

### 1.4 缺陷后果（已实测，不是推断）

阶段 10 压测的四组数据（1200/1200/1600/1200 RPS × 15s，900 学生，课程 88 `capacity=100`）：

| 组 | 本轮预热行数 | 预热时间窗 | 受理数 | 超额 | 失败订单 |
|---|---|---|---|---|---|
| 无限流 | **200** | **3 ms** | **100** | 0 | 0 |
| 限流 2000/1500 | **115** | **20 ms** | **299** | +199 | 199 |
| 限流 300/300 | **50** | **102 ms** | **364** | +264 | 200 |
| 限流 2000/1500 + 预预热 | **0** | — | **100** | 0 | 0 |

> ⚠️ **这张表是开工前的数据，其中的 299 / 364 不可稳定复现**（见文首「完成情况回填」）。
> 后来的四组重跑里，预热 200 次挤在 2 ms 内 → 受理精确 100；预热 79 次摊在 56 ms 内 → 受理 300。
> **表格保留原样，是因为它记录了当时看到的现象；但不要拿 299 当验收基准，判据请用 §6.3。**

**关键认知：决定后果的不是预热次数，是预热的时间离散度。**

- 所有 `SET` 挤在 3 ms 内完成、之后才开始 `DECRBY` → 无害（200 次预热，一次都没多卖）
- `SET` 被摊开、和 `DECRBY` 交错 → 已扣到 40 的库存被 `SET 100` 重置回满额 → 名额复活
  （50 次预热，多卖 264 个）

而**把请求摊开的正是限流**。这是加限流时完全没预料到的副作用。

> 这也解释了为什么这个缺陷能潜伏这么久：不加限流时它几乎不发作。
> 换句话说，**它一直存在，只是需要一个「改变请求时间分布」的东西才能显形。**

### 1.5 为什么它没造成超卖（这点要想清楚，别改错方向）

v3 的库存权威在 MySQL，不在 Redis：

- Redis 门禁只负责「挡掉明显没戏的请求」，减少无效流量
- 真正的扣减在 `SeckillOrderConsumer` 的事务里：`UPDATE course_stock SET stock=stock-1 WHERE stock > 0`
- 条件更新 affected=0 → 订单标 FAILED，不还 Redis

所以门禁被击穿只会多产生 FAILED 订单，不会超卖。
**代价是体验：199 个学生收到 200「排队中」，最后订单变失败，比当场告诉他「名额已满」更糟。**

**推论：这次修的是「无效请求太多」，不是「会超卖」。** 修完之后仍然不超卖，
但受理数应该精确等于 capacity。

## 2. 为什么 `SETNX` 就够（先把道理讲通再动手）

### 2.1 为什么 `SETNX` 不会写进一个过期的值

这是最容易想歪的地方。直觉上会担心：「线程 A 读到 stock=100 准备写，这期间别人扣了 20，
A 再写 100 不就又把库存写多了？」

不会。因为 **`-1` 只在 key 不存在时返回，而 key 不存在期间 `DECRBY` 一个都成功不了**
（Lua 脚本第一句就是 `if not current then return -1 end`）。

所以「读 MySQL → 写 Redis」这个窗口里，**不可能有别的线程扣过库存**。
第一个抢到 `SETNX` 的线程，写进去的值必然是当时有效的值。

后面的线程 `SETNX` 失败（返回 false），说明别人刚写过了，直接跳过写入，
接着走第二次 `tryDecrement` 正常扣减。**它们不需要知道别人写了多少，Redis 里有值就行。**

### 2.2 为什么不干脆用 Lua 一把做完

更彻底的做法是把「判存在 + 写 + 扣」合成一个脚本：

```lua
-- 可选方案，本次不做
if redis.call('EXISTS', KEYS[1]) == 0 then
    redis.call('SET', KEYS[1], ARGV[1])   -- ARGV[1] = MySQL 读到的 stock
end
return redis.call('DECRBY', KEYS[1], 1)
```

优点是少一次网络往返（现在冷启动路径是 `tryDecrement` → `preheat` → `tryDecrement` 三次）。
缺点是**把数据库读取耦合进了脚本调用**：你得先查 MySQL 才能调脚本，
而大多数请求根本不需要查 MySQL（key 存在）。为了省冷启动那一次的往返，
让所有请求都多带一个可能没用的参数，不划算。

**本次采用 `SETNX` 方案。** 冷启动路径多一次往返是可接受的 —— 它每个课程只会发生一次。

### 2.3 一个必须注意的边界

`preheatIfAbsent` 在库存行不存在时也**不能写 Redis**（保持和 `preheat` 一致）。
此时第二次 `tryDecrement` 仍然返回 `-1`，落到 `left < 0` 分支抛
`INTERNAL_ERROR「库存状态异常」` —— 这是正确行为，属于数据问题，不该伪装成「名额已满」。

## 3. 任务 A：接口 + 实现

### 3.1 接口加方法

`src/main/java/com/example/seckill/infra/cache/StockCacheService.java`，
在 `preheat` 下面加：

```java
/**
 * 仅在 key 不存在时写入。用于抢课冷启动，避免惊群。
 * <p>
 * 与 {@link #preheat(Long)} 的区别：那个是"覆盖"，这个是"补缺"。
 * 对账与管理端要覆盖（收回虚报名额），抢课要补缺（并发时只让一个人写）。
 */
void preheatIfAbsent(Long courseId);
```

顺手把 `preheat` 的 Javadoc 补一句，说明它是**覆盖写**、不要用在抢课路径上。
现有注释写的是「幂等：重复调用以数据库为准。用 SET 不用 SETNX」——
这句话在阶段 4 的语境下是对的（那时还没有冷启动并发的概念），
但现在必须补上「不要用在抢课路径」这个限定，否则下一个人（或者三个月后的你）
看到「用 SET 不用 SETNX」会直接照抄到抢课路径里。

### 3.2 实现

`src/main/java/com/example/seckill/infra/cache/impl/StockCacheServiceImpl.java`，
在 `preheat` 后面加：

```java
@Override
public void preheatIfAbsent(Long courseId) {
    CourseStock stock = courseStockMapper.selectByCourseId(courseId);
    if (stock == null) {
        log.warn("预热跳过：课程库存行不存在 courseId={}", courseId);
        return;
    }
    Boolean written = stringRedisTemplate.opsForValue()
            .setIfAbsent(stockKey(courseId), String.valueOf(stock.getStock()));
    if (Boolean.TRUE.equals(written)) {
        log.info("预热完成（冷启动） courseId={} stock={}", courseId, stock.getStock());
    } else {
        log.debug("预热跳过：已由其它请求写入 courseId={}", courseId);
    }
}
```

**为什么 `Boolean.TRUE.equals(written)` 而不是 `written`**：`setIfAbsent` 返回的是
包装类型 `Boolean`，Redis 连接异常等极端情况下可能返回 `null`，直接拆箱会 NPE。
项目里 `incrementIfPresent` 已经用了同样的写法，保持一致。

**为什么日志用 `debug`**：这条在并发下会打几十次，用 `info` 会把日志淹掉。
而「谁真正写了」这件事，`info` 那一条就够了。

void preheatIfAbsent_usesSetIfAbsent() {

### 🔴 坑：Mockito 严格模式会因「多余的打桩」报错

`@ExtendWith(MockitoExtension.class)` 默认是 `Strictness.STRICT_STUBS`。
如果你在用例 3 里顺手写了 `when(valueOps.setIfAbsent(...))`，但代码提前 return 了没调用它，
测试会以 `UnnecessaryStubbingException` 失败 —— **报错信息看起来像"测试写错了"，
实际是在提示你"这个桩没用上，说明你的假设和代码不符"**。

项目里已有的 `preheat_stockRowMissing_skips` 就是靠"不打桩"来证明提前 return 的，照抄它。

### 6.3 判定标准

| 指标 | 修复前 | 修复后（实测） | 怎么查 |
|---|---|---|---|
| `biz_queued` | **300**（`mutated600`） | **100**（`fixed600b`） | k6 输出 |
| 失败订单（`status=2`） | **200** | **0** | SQL |
| 本轮预热行数 | **79** | **1**（或个位数） | 日志 `预热完成（冷启动）` |
| `stock + sold` | 100 | 100 | SQL |
| Redis 剩余 | 0 | 0 | `get seckill:stock:88` |

> 🔴 **判定时不要只盯 `biz_queued`。** 修复前那一侧的受理数**不保证超过 capacity**——同样的 `SET` 代码，预热 200 次挤在 2 ms 内时受理数精确等于 100。所以正确判据是**两条一起看**：
>
> 1. `本轮预热行数` 必须是 **1**（`SETNX` 生效，其余请求都写不进去）——这一条是确定性的，不受时序影响。
> 2. `biz_queued` 必须 **≤ capacity**。
>
> 只要预热行数是 1，就说明修复生效了；受理数是否恰好 100 取决于别的因素（比如 VU 池够不够）。

SQL：

```sql
SELECT capacity, stock, sold FROM seckill.course_stock WHERE course_id = 88;
SELECT status, COUNT(*) FROM seckill.seckill_order GROUP BY status;
```

### 🔴 6.4 统计日志行数时最容易犯的错（我上次就栽在这）

**必须按字符偏移切出「本轮」区间，否则你数到的是累计值。**

```powershell
# 压测前记一个 mark
$mark = (Read-Shared $logPath).Length

# 压测后只统计新增部分
$all = Read-Shared $logPath
$segment = $all.Substring($mark)
$count = ([regex]::Matches($segment, "预热完成（冷启动）")).Count
```

`Read-Shared` 是自己写的辅助函数（日志被运行中的应用占用，
`[System.IO.File]::ReadAllBytes` 会抛「文件正由另一进程使用」）：

```powershell
function Read-Shared([string]$p) {
    $fs = New-Object System.IO.FileStream($p,'Open','Read','ReadWrite')
    try {
        $sr = New-Object System.IO.StreamReader($fs, [System.Text.Encoding]::UTF8)
        return $sr.ReadToEnd()
    } finally { $fs.Dispose() }
}
```

**注意编码是 UTF-8，不是 GBK。** 应用日志（logback）是 UTF-8，
用 `GetEncoding(936)` 读会得到 `瀹屾垚` 这类乱码，匹配数直接变 0 ——
我上次因此误判「一次预热都没发生」。Maven/surefire 的输出才是 GBK，两者别搞混。

### 6.5 一个诚实的说明

修复后预热行数**不会精确等于 1**。因为：

- `reset-v3.ps1` 之后到压测真正开始之间有几百毫秒，可能已经有零星请求
- `StockReconciler` 每 5 分钟一轮，可能插进来一次覆盖写（压测时应关掉：`--seckill.reconcile-enable=false`）

**判定看 `biz_queued` 是否回到 100，不要死抠预热行数。**

## 10. 做完能得到什么

### 面试可讲的一件事

> 「压测时发现受理数超过了 capacity，最后定位到是缓存预热的惊群。
> 有意思的是它跟并发量不完全相关 —— 预热 200 次的那组一次都没多卖，
> 预热 50 次的那组反而多卖 264 个，因为决定后果的是预热的时间离散度。
> 而把请求摊开、让它显形的，正是我们刚加的限流。
> 修法是 `SET` 换 `SETNX`，但只改抢课路径 —— 对账那条必须保持覆盖写，否则收不回虚报名额。」

这段的价值在于：**它同时包含「怎么发现的」「为什么难发现」「为什么不能一刀切修」**。
比"我加了个限流"有信息量得多。

### 这一阶段补上了什么

| 之前 | 之后 |
|---|---|
| 冷启动受理 300、失败单 200 | 受理 100、失败单 0 |
| `preheat` 语义含糊（注释还写着"用 SET 不用 SETNX"） | 两种语义分开，各自注明用途 |
| 99 条单测 | 103 条 |
| README 已知局限第 11 条「还没修」 | 划掉 |
