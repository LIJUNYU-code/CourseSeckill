## 0. 先说一件我上一条回复说错的事

我在给你列 4 个缺陷时，把 **A8 的游标分页结论**套到了订单列表上：

> 「A8 刚实测出 offset 分页 LIMIT 100000,20 要 280ms，游标分页只要 0.2ms —— 快 1000 倍。你现在有一份报告证明该做游标分页，代码里用的却是 offset。」

**这条不成立。** 我核实了表结构：

```sql
UNIQUE KEY uk_student_course (student_id, course_id)
```

一个学生在同一门课上只能有一条订单，全库 100 门课 → **单个学生的订单数上限是 100 条**。

`queryOrders` 的查询条件是 `.eq(SeckillOrder::getStudentId, currentId)`，所以：

- `LIMIT 0, 10` → 偏移 0
- `LIMIT 90, 10` → 偏移 90（已经是最后一页）
- `LIMIT 100000, 20` → **永远不可能发生**

A8 测的是「一门课有 39.8 万条订单」时的深分页，那是**管理员视角**或**统计视角**的问题。本项目没有管理员订单列表接口，所以这个深分页场景**在现有代码里不存在**。

### 结论修正

| 原判断 | 修正后 |
|---|---|
| ② 订单列表要改游标分页 | ❌ **不需要**，学生最多 100 条，offset 分页偏移量天然有上限 |
| ② 订单列表有 N+1 | ✅ **成立**，这个要修 |

**这正好是一课**：一份实测报告证明「某个模式在某个场景下是灾难」，不等于「你代码里所有类似写法都是灾难」。用之前先问一句：**我的场景真的会走到那个量级吗？**

那 A8 的游标分页建议就白做了吗？不是。它告诉你：

- 如果以后加「管理员看全部订单」「按课程统计报名名单」，那些接口**必须**用游标分页
- 现在不做，是因为现在没有那个接口——**P4 原则：功能做小，深度做透，不提前造**

## 2. 任务 ①：补 405 handler

### 2.1 现象（已实测）

```bash
# /api/seckill/{courseId} 是 POST 接口，故意用 GET 调
curl -X GET http://localhost:8080/api/seckill/88 -H "Authorization: Bearer <token>"
```

返回：

```json
{"code":500,"message":"服务器内部错误，请稍后重试","data":null}
```

日志：

```
GlobalExceptionHandler : 未处理异常 uri=/api/seckill/88 method=GET
org.springframework.web.HttpRequestMethodNotSupportedException: Request method 'GET' is not supported
```

### 2.2 根因

`src/main/java/com/example/seckill/exception/GlobalExceptionHandler.java` 现在有 8 个 handler，**没有 `HttpRequestMethodNotSupportedException`**，于是落进最后的 `Exception.class` 兜底，变成 500。

### 2.3 为什么这值得修（不是吹毛求疵）

把客户端错误报成服务端错误，后果是：

1. **监控假告警**。你按「5xx 比例」配告警，前端某次发错方法就能把值班人半夜叫起来。
2. **排查方向错**。看到 500 第一反应是查服务端日志、查数据库，实际是调用方写错。
3. **错误分类失真**。真正的 500 被淹没在一堆假 500 里。

一句话：**HTTP 状态码是给机器看的，不能糊弄。**

### 2.4 要做的事

**第 1 步**：在 `src/main/java/com/example/seckill/common/ResultCode.java` 的「通用」段落里，`NOT_FOUND = 404` 之后、`CONFLICT = 409` 之前插入：

```java
    /** 405：请求方法不被该接口支持（如用 GET 调 POST 接口）。 */
    public static final int METHOD_NOT_ALLOWED = 405;
```

注意保持现有的 javadoc 注释风格（每个常量上面一行 `/** ... */`）。

**第 2 步**：在 `GlobalExceptionHandler.java` 里加一个 handler。位置建议放在 `handleNotFound` 之后、`handleUnreadable` 之前——按 HTTP 状态码顺序排列，和现有风格一致：

```java
    @ExceptionHandler(org.springframework.web.HttpRequestMethodNotSupportedException.class)
    public ResponseEntity<Result<Void>> handleMethodNotSupported(
            org.springframework.web.HttpRequestMethodNotSupportedException e) {
        return ResponseEntity.status(405)
                .body(Result.error(ResultCode.METHOD_NOT_ALLOWED,
                        "请求方法不支持: " + e.getMethod()));
    }
```

### 2.5 三个容易踩的点

**坑 1：handler 必须比 `DefaultHandlerExceptionResolver` 先跑**

Spring MVC 的异常解析器是一条链，按 order 排序：

| order | 解析器 | 说明 |
|---|---|---|
| 0 | `ExceptionHandlerExceptionResolver` | 我们的 `@RestControllerAdvice` |
| 1 | `ResponseStatusExceptionResolver` | |
| 2 | `DefaultHandlerExceptionResolver` | Spring 内置，把标准异常翻成状态码 |

`@ExceptionHandler` 的 order 是 0，**排在 `DefaultHandlerExceptionResolver` 前面**，所以能抢到。

反证：你之前加 `MethodArgumentTypeMismatchException` handler 之前，日志里出现过
`DefaultHandlerExceptionResolver : Resolved [HttpMessageNotReadableException: ...]`——那就是没人接、被内置解析器兜走的证据。

**坑 2：不要 import `HttpRequestMethodNotSupportedException` 就以为万事大吉**

它的包是 `org.springframework.web.HttpRequestMethodNotSupportedException`（`web` 包，不是 `web.servlet`，也不是 `web.bind.annotation`）。
写错包名会编译失败，但**如果恰好有一个同名类在别的包**，就会变成运行期行为不对。IDE 自动导入时看一眼全路径。

**坑 3：不要顺手把它写成 400**

405 和 400 的区别：400 = 你的请求内容有问题；405 = 路径对了但方法不对。
`GET /api/seckill/88` 的路径完全正确，只是这个资源不接受 GET，所以是 405，并且响应必须带 `Allow` 头（Spring 会自动加，不用你管）。

### 2.6 验收标准

```bash
# ① 方法用错 → 405 + 中文提示
curl -s -o /dev/null -w "%{http_code}" -X GET http://localhost:8080/api/seckill/88 \
  -H "Authorization: Bearer $TOKEN"
# 期望：405

# ② body 是统一 Result 格式
curl -s -X GET http://localhost:8080/api/seckill/88 -H "Authorization: Bearer $TOKEN"
# 期望：{"code":405,"message":"请求方法不支持: GET","data":null}

# ③ 正常 POST 仍然 200（别把对的也拦了）
curl -s -X POST http://localhost:8080/api/seckill/88 -H "Authorization: Bearer $TOKEN"
# 期望：code=200

# ④ 未知路径仍是 404（别被新 handler 抢走）
curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/api/nope -H "Authorization: Bearer $TOKEN"
# 期望：404

# ⑤ 日志里不该再出现「未处理异常 uri=/api/seckill/88 method=GET」
grep "未处理异常" target/run.log
# 期望：无此行
```

## 3. 任务 ④：检查 CAS 返回值（并发正确性）

### 3.1 问题代码

`src/main/java/com/example/seckill/service/impl/SeckillServiceImplV3MqAsync.java:88-91`：

```java
//CANCELLED 或 FAILED 复用旧帐单
orderNo = existing.getOrderNo();
seckillOrderMapper.updateStatusIfMatch(
        existing.getId(), SeckillOrder.STATUS_PENDING, existing.getStatus());
// ↑ 返回值被丢弃
```

### 3.2 为什么这是 bug（必须理解清楚）

`updateStatusIfMatch` 是条件更新（CAS）：

```sql
UPDATE seckill_order SET status = #{newStatus}
WHERE id = #{id} AND status = #{expectStatus}
```

**`affected = 0` 表示「我以为它是 CANCELLED，但其实别人已经改过了」。**

现在的代码不看返回值，直接往下走。场景：

```
学生 S 之前退过课程 88（订单 status=3 已退课）
现在同时点两次「重新抢课」（双击、或前端重试）

线程 A                          线程 B
────────────────────────────────────────────────────────
读订单 → status=3                读订单 → status=3
updateStatusIfMatch(→0)          updateStatusIfMatch(→0)
  实际：3→0 成功，affected=1       实际：状态已是 0，affected=0 ← 被丢弃
Redis 扣减 → 99                  Redis 扣减 → 98
插消息 msgId=A                   插消息 msgId=B
返回 200                         返回 200
```

结果：

- **Redis 扣了 2 个名额**
- MySQL 只有 1 条订单（`uk_student_course` 保证一人一课一条）
- 消费者处理 2 条消息：第 1 条扣 MySQL 库存、改订单成功；第 2 条 `updateStatusByOrderNo` 返回 0 → 归还库存

所以 **MySQL 最终是平的**（扣 1 还 1 = 净 0，但订单成功占 1 个名额 → 净 -1，正确）。
而 **Redis 少了 2 个**，只还回来 0 个（消费者不碰 Redis）→ **Redis 永久偏低 1 个**。

Redis 偏低不会超卖（安全方向），但会导致：

- 明明还有 1 个名额，用户点进去提示「名额已满」
- 对账脚本 `loadtest/reconcile.ps1` 报 `redisStock < dbStock`（偏低态）

### 3.3 为什么说它「隐蔽」

- 不会超卖 → 压测的成功单数、超卖数都正常
- 不会报错 → 日志里没有 ERROR
- 只有**并发双击 + 退课后重选**这个组合才触发
- 表现是「偶尔有人说名额没了但其实还有」，很难复现

**这是本项目唯一会静默产生脏数据的缺陷。**

### 3.4 怎么改

把返回值接住，`affected == 0` 说明输了这场竞争，直接失败退出：

```java
            //CANCELLED 或 FAILED 复用旧帐单
            orderNo = existing.getOrderNo();
            int claimed = seckillOrderMapper.updateStatusIfMatch(
                    existing.getId(), SeckillOrder.STATUS_PENDING, existing.getStatus());
            if (claimed == 0) {
                // 别人抢先把它改成 PENDING 了（并发双击 / 前端重试）。
                // 不能继续：继续就会多发一条消息、多扣一次 Redis。
                throw new BusinessException(ResultCode.CONFLICT, "操作过于频繁，请稍后重试");
            }
```

### 3.5 为什么这样就够了（把三层防线讲清楚）

改完之后，同一场景：

```
线程 A                          线程 B
读订单 → status=3                读订单 → status=3
CAS 3→0 成功（affected=1）       CAS 3→0 失败（affected=0）
Redis 扣减 → 99                  抛 409
发消息                            走 finally：
返回 200                            Redis incrementIfPresent → 100
```

**finally 块自动兜住了 Redis**——因为 `success` 还是 `false`。这是原代码设计得好的地方：所有失败路径都走 `finally` 里的补偿。

三层防线各自负责什么：

| 防线 | 挡住什么 | 挡不住什么 |
|---|---|---|
| Redis Lua 门禁 | 库存耗尽后的无效请求 | 同一学生重复请求（它不知道是谁） |
| 订单 CAS（本次要修的） | 同一学生的并发重复请求 | 不同学生抢同一课（那是正常的） |
| `uk_student_course` 唯一索引 | 数据库层的重复插入 | 它抛异常时 Redis 已经扣过了 |

### 3.6 顺带检查另一处

`SeckillServiceImplV2RedisLua.java:142` 也调了 `updateStatusIfMatch`，但那一行**有** `int affected = ...` 接住并判断了。**不用改。**

用这条命令自查全项目还有没有别的地方丢弃返回值：

```bash
grep -rn "updateStatusIfMatch\|tryDecrement\|returnStock\|updateStatusByOrderNo" \
  src/main/java --include=*.java | grep -v "^.*mapper/"
```

期望：除了 `SeckillServiceImplV3MqAsync.java:90`（本次要改的）之外，其余都在用返回值或本来就无需判断（如 `returnStock` 在 `cancel` 里）。

## 4. 任务 ②：消除订单列表的 N+1

### 4.1 问题代码

`src/main/java/com/example/seckill/service/impl/OrderServiceImpl.java:54-65`：

```java
List<OrderResponse> records = seckillOrderPage.getRecords().stream().map(s ->
{
    Course course = courseMapper.selectById(s.getCourseId());   // ← 每单一次查询
    if (course == null) throw new BusinessException(ResultCode.NOT_FOUND, "课程不存在");
    return OrderResponse.builder()...
}).toList();
```

**1 次分页查询 + N 次课程查询**。默认 `size=10` → 11 次 SQL；前端现在传 `size=50` → **51 次 SQL**。

### 4.2 为什么这值得修（即使 100 条上限）

单次查询都很便宜（`WHERE id=?` 主键命中 0.06ms），但：

1. **每次都要一次网络往返**。本机是 0.1ms，跨机房是 0.5~2ms。50 次 × 1ms = **50ms**，比业务逻辑本身还慢。
2. **每次都要占一个连接**。HikariCP 池 50 个连接，50 次串行查询会反复借还。
3. **N 会随 `size` 线性增长**。前端今天传 50，明天有人传 200 就是 201 次。

这就是 N+1 的经典形态：**单次不慢，次数致命。**

### 4.3 怎么改

用 `selectByIds` 一次查完。**注意 MyBatis-Plus 3.5.17 的 API 变化**：

```java
// ✅ 3.5.17 的正确写法（已用 javap 核实存在）
List<Course> courses = courseMapper.selectByIds(courseIds);

// ❌ 老教程的写法，3.5.17 里是 @Deprecated 的 default 方法
List<Course> courses = courseMapper.selectBatchIds(courseIds);
```

`javap` 核实结果：

```
public abstract java.util.List<T> selectByIds(java.util.Collection<? extends java.io.Serializable>);
public default  java.util.List<T> selectBatchIds(java.util.Collection<? extends java.io.Serializable>);  ← default 转调 selectByIds
```

两个都能用，但 `selectByIds` 是抽象方法（真正的实现），`selectBatchIds` 只是转调。**用前者。**

完整改法：

```java
        List<SeckillOrder> orders = seckillOrderPage.getRecords();

        // 一次性把这一页涉及的课程查出来，用 id → name 的字典代替 N 次查询
        Set<Long> courseIds = orders.stream()
                .map(SeckillOrder::getCourseId)
                .collect(Collectors.toSet());
        Map<Long, String> courseNameMap = courseMapper.selectByIds(courseIds).stream()
                .collect(Collectors.toMap(Course::getId, Course::getCourseName));

        List<OrderResponse> records = orders.stream().map(s -> {
            String courseName = courseNameMap.get(s.getCourseId());
            if (courseName == null) {
                // 🔴 课程被删了，不能像原来那样抛 404：
                //    一门课消失不该让整页订单都打不开（用户会以为自己的选课记录全没了）
                log.warn("订单关联的课程不存在，用占位名代替 orderNo={} courseId={}",
                        s.getOrderNo(), s.getCourseId());
                courseName = "课程已删除";
            }
            return OrderResponse.builder()
                    .orderNo(s.getOrderNo())
                    .courseId(s.getCourseId())
                    .courseName(courseName)
                    .failReason(s.getFailReason())
                    .statusText(getStatusText(s.getStatus()))
                    .status(s.getStatus())
                    .createTime(s.getCreateTime())
                    .updateTime(s.getUpdateTime())
                    .build();
        }).toList();
```

需要新增的 import：

```java
import lombok.extern.slf4j.Slf4j;
import java.util.Map;
import java.util.Set;
import java.util.stream.Collectors;
```

并在类上加 `@Slf4j`。

### 4.4 三个关键决策，你要能解释

**决策 1：为什么课程不存在时改成「课程已删除」而不是继续抛 404？**

原来的 `throw new BusinessException(ResultCode.NOT_FOUND, "课程不存在")` 会让**整页订单**都返回 404。用户打开「我的选课」，看到的是「接口不存在」，他会以为账号出问题了。

正确做法是**降级**：这门课的名字显示为「课程已删除」，其他订单正常显示。**局部数据缺失不应该让整体功能失效。**

**决策 2：`selectByIds` 传空集合会怎样？**

MyBatis-Plus 对空集合会返回空列表，**不生成 SQL**（不会拼出 `WHERE id IN ()` 这种语法错误）。所以理论上不用判空。

但既然上面已经有 `if (seckillOrderPage.getRecords().isEmpty()) return ...` 提前返回，到这里 `orders` 一定非空。**两道保险都在，不用再加判断。**

**决策 3：`Collectors.toMap` 遇到重复 key 会抛异常，要不要防？**

`course` 表主键是 `id`，`selectByIds` 按主键查，**不可能返回重复 id**。所以不需要 `(a, b) -> a` 这种合并函数。

如果哪天有人改成按非唯一列查，就会抛 `IllegalStateException: Duplicate key`——这是**好事**，快速失败比静默覆盖好。

### 4.5 顺手加一个防护：限制 size 上限

`OrderController.java:26` 现在是：

```java
@RequestParam(defaultValue = "10") Integer size
```

没有上限。有人传 `size=100000` 就是一次查 10 万行 + 10 万次……（改完后是 1 次批量查，但仍然返回 10 万条 JSON）。

**要不要加？** 我建议加，但只加一行：

```java
    @PreAuthorize("hasRole('STUDENT')")
    @GetMapping("/my")
    public Result<MyOrderPageResponse> query(@RequestParam(defaultValue = "1") Integer page,
                                             @RequestParam(defaultValue = "10") Integer size) {
        // 单个学生最多 100 条订单，超过这个数的 size 没有意义，
        // 但可以让调用方一次拉 10 万行 JSON 把内存打爆 —— 兜一下
        if (size == null || size < 1) size = 10;
        if (size > 100) size = 100;
        MyOrderPageResponse res = orderService.queryOrders(page, size);
        return Result.success(res);
    }
```

> 用 `if` 而不是 `@Max(100)` 注解，是因为 `@RequestParam` 上的校验注解需要类上加 `@Validated` 才生效，多引入一个机制不如两行 `if` 直白。**这也是取舍，不是唯一正确答案。**

| 1 | 一页 3 单、3 门不同课 | `courseMapper.selectByIds` 被调 **1 次**；`courseMapper.selectById` **零调用** |
| 2 | 一页 3 单、只有 2 门课（重复课程） | 返回 3 条记录，课程名正确（证明字典按 id 命中） |
| 3 | 某门课查不到 | 该条 `courseName = "课程已删除"`，**其余订单正常返回**，不抛异常 |
| 4 | 空列表 | `total=0`、`records` 为空、`selectByIds` **零调用**（提前 return 生效） |
| 5 | 状态文案 | status=0→「待处理」、1→「已成功」、2→「已失败」、3→「已退课」、null→`""` |

用例 1 是核心——它用 `verify(times(1))` **钉死**了 N+1 不会复发。这类断言叫「性能回归测试」：它不测功能，测的是「别退回到 N 次查询」。

## 5. 任务 ③：PENDING 订单超时清扫

### 5.1 问题

全项目**没有任何 `@Scheduled`**（已 grep 确认）。订单创建时 `status=0`（待处理），正常路径由消费者改成 1 或 2。

但存在一条**没有出口**的路径：

```
seckill() 里 insert 订单 status=0
  → messageProducer.send() 成功（confirm ack）
  → 消息进了队列
  → 但消费者没在处理（RabbitMQ 挂了 / @RabbitListener 启动失败 / 队列被误删）
  → 消息躺在队列里
  → 订单永久停在 status=0
```

用户视角：一直显示「待处理」，刷新一百次还是「待处理」。他不知道到底选上没有。

### 5.2 为什么不能只靠现有机制

`SeckillMessageProducer` 的 finally 补偿只覆盖**发送失败**（超时/nack）。一旦 confirm 成功，`success=true`，`finally` 不做任何事——**代码认为「交给 MQ 就完事了」**。

而 MQ 的可靠性只保证「消息不丢」，不保证「一定被消费」。消费者停摆时消息会一直堆着，`queue-timeout-ms` 那个配置**只影响同步等待，不影响订单状态**。

### 5.3 设计

**核心规则：超过 N 分钟仍是 status=0 的订单，标记为 FAILED（原因「处理超时」），并把名额还给 MySQL 和 Redis。**

三个必须想清楚的点：

**点 1：为什么用 CAS 更新，而不是先查再改？**

清扫任务和消费者会**同时**操作同一条订单。如果先 `SELECT` 再 `UPDATE`，中间消费者可能已经把订单改成 SUCCESS 了，你的 `UPDATE` 会把它覆盖成 FAILED——**把成功的单子改失败，这是灾难**。

所以必须用条件更新：

```sql
UPDATE seckill_order SET status = 2, fail_reason = '处理超时'
WHERE order_no = ? AND status = 0
```

`affected = 0` 表示「我慢了一步，消费者已经处理了」→ 跳过，不动库存。

**点 2：归还库存的顺序**

和退课一样：**先 MySQL 提交，再还 Redis**。Redis 归还失败只 log 不抛（Redis 偏低是安全方向）。

**点 3：会不会和消费者双倍归还？**

不会。推演一遍：

| 时序 | MySQL stock | Redis | 说明 |
|---|---|---|---|
| 初始 | 99（已扣） | 99 | 订单 PENDING |
| 清扫 CAS 成功 | 100 | 100 | 标记 FAILED，归还两边 |
| 消费者后到：`tryDecrement` | 99 | 100 | 扣了 |
| 消费者：`updateStatusByOrderNo` 返回 0 | 99 | 100 | 状态已是 2，不是 0 |
| 消费者：`returnStock` | 100 | 100 | 归还 |

**最终 MySQL 100、Redis 100，账平。** 消费者那条分支（`订单状态已更改，跳过`）本来就是为这种情况设计的。

反过来时序（消费者先成功）：清扫的 CAS 返回 0 → 直接跳过，什么都不动。也平。

**文件 2：`src/main/java/com/example/seckill/infra/schedule/PendingOrderSweeper.java`**（新建包 `infra/schedule`）：

```java
package com.example.seckill.infra.schedule;

import com.example.seckill.entity.SeckillOrder;
import com.example.seckill.infra.cache.StockCacheService;
import com.example.seckill.mapper.CourseStockMapper;
import com.example.seckill.mapper.SeckillOrderMapper;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

/**
 * PENDING 订单超时清扫。
 *
 * <p>解决什么问题：订单创建后要等 MQ 消费者把它改成「成功」或「失败」。
 * 如果消费者停摆（RabbitMQ 挂了、@RabbitListener 启动失败、队列被误删），
 * 消息会一直躺在队列里，订单永久停在 status=0，用户看到的是永远「待处理」。
 *
 * <p>这不是 MQ 的 bug —— MQ 只保证「消息不丢」，不保证「一定被消费」。
 * 兜底要靠业务自己：谁创建了中间状态，谁负责给它一个出口。
 */
@Slf4j
@Component
public class PendingOrderSweeper {

    private final SeckillOrderMapper seckillOrderMapper;
    private final CourseStockMapper courseStockMapper;
    private final StockCacheService stockCacheService;
    private final long pendingTimeoutMinutes;
    private final int batchSize;

    /**
     * 用构造器注入 + @Value 而不是 @RequiredArgsConstructor + 字段 @Value。
     *
     * <p>理由：字段注入的 @Value 无法在单测里替换，只能起 Spring 容器测；
     * 构造器参数可以，于是纯 Mockito 测试能直接 new 出来。
     * 这个取舍和项目里其它类（JwtUtil 用字段 @Value）不一致，是刻意的：
     * 这个类要单测，JwtUtil 的配置值不影响逻辑。
     */
    public PendingOrderSweeper(
            SeckillOrderMapper seckillOrderMapper,
            CourseStockMapper courseStockMapper,
            StockCacheService stockCacheService,
            @Value("${seckill.pending-timeout-minutes:5}") long pendingTimeoutMinutes,
            @Value("${seckill.pending-sweep-batch:200}") int batchSize) {
        this.seckillOrderMapper = seckillOrderMapper;
        this.courseStockMapper = courseStockMapper;
        this.stockCacheService = stockCacheService;
        this.pendingTimeoutMinutes = pendingTimeoutMinutes;
        this.batchSize = batchSize;
    }

    /**
     * 定时入口。参数全部走配置，方便压测时调快（改成 1 分钟能立刻看到效果）。
     *
     * <p>initialDelay 给 30 秒：应用刚启动时 MQ 消费者可能还没就绪，
     * 立刻清扫会把本来正常在途的订单误判为超时。
     */
    @Scheduled(
            fixedDelayString = "${seckill.pending-sweep-interval-ms:60000}",
            initialDelayString = "${seckill.pending-sweep-initial-delay-ms:30000}")
    public void sweep() {
        try {
            sweepOnce(LocalDateTime.now());
        } catch (Exception e) {
            // 定时任务里绝不能把异常抛出去：一次失败不该让整个调度停掉
            log.error("PENDING 订单清扫失败", e);
        }
    }

    /**
     * 可单测的实际逻辑（把时间当参数传进来，测试里不用等 5 分钟）。
     *
     * @return 本轮清扫掉的订单数
     */
    public int sweepOnce(LocalDateTime now) {
        LocalDateTime deadline = now.minusMinutes(pendingTimeoutMinutes);
        List<SeckillOrder> stale = seckillOrderMapper.selectStalePending(deadline, batchSize);
        if (stale.isEmpty()) {
            return 0;
        }
        log.info("发现 {} 条超时未处理订单，开始清扫", stale.size());

        int swept = 0;
        for (SeckillOrder order : stale) {
            // 条件更新：只有仍是 status=0 才改。
            // affected=0 说明消费者已经处理了这条单，绝不能覆盖它的结果
            int affected = seckillOrderMapper.updateStatusAndFailReason(
                    order.getOrderNo(), SeckillOrder.STATUS_FAILED, "处理超时");
            if (affected == 0) {
                continue;
            }
            // 先 MySQL（上面的 UPDATE 已提交），再 Redis
            int returned = courseStockMapper.returnStock(order.getCourseId());
            if (returned == 0) {
                log.warn("清扫归还库存失败（可能已归还）orderNo={} courseId={}",
                        order.getOrderNo(), order.getCourseId());
            }
            try {
                stockCacheService.incrementIfPresent(order.getCourseId());
            } catch (Exception e) {
                // Redis 偏低是安全方向，不抛。交给对账脚本 reconcile.ps1 修
                log.error("清扫归还 Redis 失败（Redis 偏低，不会超卖）courseId={}",
                        order.getCourseId(), e);
            }
            swept++;
            log.warn("订单超时未处理，已标记失败 orderNo={} courseId={} studentId={}",
                    order.getOrderNo(), order.getCourseId(), order.getStudentId());
        }
        return swept;
    }
}
```

### 5.5 五个容易踩的点

**坑 1：`@Scheduled` 方法不能有参数、不能有返回值**

必须是 `public void xxx()`。有参数会启动报错。所以逻辑要拆成 `sweep()`（无参入口）+ `sweepOnce(now)`（可测逻辑）。

**坑 2：定时任务里抛异常会怎样？**

Spring 默认会 `log.error` 掉，然后**继续下一轮**（`fixedDelay` 调度器会 catch）。所以不 catch 也能活，但日志会变成一坨原始栈。**主动 catch 能让日志说人话。**

反例：如果用的是 `ScheduledExecutorService` 而不是 Spring 的调度器，未捕获异常会**终止后续所有执行**——这就是为什么很多人写定时任务都要包 try-catch，习惯成自然。

**坑 3：单实例假设**

这个清扫任务在**多实例部署时会重复执行**。但因为用的是 CAS 条件更新，两个实例同时扫到同一条订单，只有一个 `affected=1`，另一个 `affected=0` 跳过——**天然幂等，不会双倍归还**。

这就是为什么**必须用 CAS 而不是先查再改**：不只是为了和消费者竞争，也是为了多实例之间竞争。

如果将来要严格单实例执行，可以加分布式锁（Redisson / Redis SETNX），但那是另一个话题，现在不需要。

**坑 4：`initialDelay` 不能省**

应用刚启动时，`@RabbitListener` 容器还在初始化，队列里可能有一批刚投进来的消息没被消费。如果第一轮清扫立刻跑，会把这些**正常在途**的订单误判成超时。

30 秒 + 5 分钟阈值 = 实际有 5.5 分钟余量。

**坑 5：不要用 `create_time < NOW() - INTERVAL 5 MINUTE` 写在 SQL 里**

看起来更简洁，但：

- 时间来自数据库服务器时钟，应用和数据库时区不一致时会错
- 单测里没法控制时间（你不可能等 5 分钟）

**把时间当参数从 Java 传进去**，测试里传 `LocalDateTime.of(2026, 1, 1, 12, 0)` 就能精确构造场景。这是「可测试性驱动设计」的一个小例子。

## 9. 做完之后你会得到什么

不是「代码更整洁了」，而是四个可以在面试里讲的具体故事：

1. **「你怎么区分客户端错误和服务端错误？」** → 405 那个例子。能说出「假告警淹没真故障」。
2. **「N+1 是什么，你项目里有吗？」** → 51 次 SQL → 3 次。能说出为什么「单次不慢但次数致命」。
3. **「中间状态卡住了怎么办？」** → PENDING 清扫。能说出「MQ 只保证不丢，不保证被消费，兜底要业务自己做」，以及「为什么必须用 CAS」。
4. **「你遇到过最隐蔽的并发 bug？」** → CAS 返回值被丢弃。能说出「不超卖、不报错、只有并发双击+退课后重选才触发、表现是名额凭空消失」。

**第 4 个是本阶段最值钱的**——因为它不是从教程抄的，是你自己代码里的真 bug，而且能讲清楚三层防线各自挡什么。
