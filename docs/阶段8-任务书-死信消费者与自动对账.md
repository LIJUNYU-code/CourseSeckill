# 阶段 8 任务书 —— 死信消费者 + 库存自动对账

> 这份文档只做两件事：补上 `docs/压测报告-v3.md` §9.3 承认的「死信队列没有消费者」，
> 和 §9.1 承认的「confirm 超时窗口会让 Redis 偏高，只能人工跑 `reconcile.ps1` 查」。
>
> 两个任务都不改变任何现有接口的行为，都是**旁路**：一个把死信落库，一个定时比对库存。
> 所以它们可以独立做、独立测、独立回滚 —— 出问题最多是多写一张表、多跑一个定时任务，
> 不会让抢课链路变慢或变错。
>
> 但正因为是旁路，**写错了不会有任何报错**。任务书里标 🔴 的地方都是「错了也看不见」的地方。

### 0.2 对账现在只能手动

`loadtest/reconcile.ps1`（147 行）做的事情，核心就是三行判断：

```powershell
# consistent = redisStock != null && redisStock == dbStock
# redis > db  → 🔴 危险：Redis 偏高，可能超卖
# redis < db  → 🟡 安全：Redis 偏低，浪费名额
# redis = null → 未预热，不算错
```

**现状**：只有人想起来的时候才会跑一次。`docs/压测报告-v3.md` §9.1 写得很清楚：

> confirm 超时（3 秒）后抛异常、订单回滚、但消息可能其实已经到了 broker。
> 这时 Redis 已经扣了 1 却没还（`finally` 里的 `incrementIfPresent` 只在 `success == false` 时执行，
> 而超时抛异常时 `success` 确实还是 false，所以**这种情况其实是还了的** ——
> 真正会偏高的是「消息到了、消费者扣了 MySQL、但 confirm 没回来」，需要靠对账兜底）。

不管具体哪条路径，结论是：**Redis 和 MySQL 会有不一致的窗口，而现在没有自动发现它的机制。**

## 1. 任务 A：死信消费者

### 1.1 它该做什么、不该做什么

先说清楚边界，否则很容易写成一个「帮倒忙」的组件。

| 该做 | 不该做 |
|---|---|
| 把死信**落库**，字段拆开便于 SQL 查 | ❌ 不要尝试重新投递回业务队列（会无限循环） |
| 记录 `x-death` 里的死信原因（rejected / expired / maxlen） | ❌ 不要改订单状态（订单由 `PendingOrderSweeper` 兜底） |
| 落库失败时把**完整 body 打进日志** | ❌ 不要 `basicNack(requeue=true)`（没有 DLX 了，会死循环或丢消息） |

**为什么不该改订单状态**：一条消息进死信，可能是「坏 JSON」（订单号都解析不出来，改不了），
也可能是「技术异常」（数据库连接断了）。后者的订单仍是 `status=0`，
而 `PendingOrderSweeper` 每分钟扫一次超时 PENDING 订单，**它才是改订单状态的那个组件**。
两个组件都去改，就是两个线程抢同一行，还各自 `incrementIfPresent` 一次 → Redis 多还一个名额。

> 一句话：**死信消费者只负责「留证据」，不负责「收拾现场」。**

### 1.2 🔴 为什么必须给死信消费者换一个 `containerFactory`

这是本任务最容易踩的坑，而且踩了会**丢证据**。

如果照抄 `SeckillOrderConsumer` 的写法：

```java
// ❌ 千万别这么写
@RabbitListener(queues = RabbitConfig.DLQ_QUEUE)
public void onMessage(SeckillMessage message, Message raw, Channel channel) { ... }
```

Spring AMQP 会先用 `JacksonJsonMessageConverter` 把 body 转成 `SeckillMessage`。
而死信里躺着的**恰恰就是那条转不过去的坏消息**（阶段 5 自测第 13 项发的
`{"msgId":"dlq-test-bad","orderNo":` 就是不完整 JSON）。转换直接抛
`MessageConversionException` → 监听器异常 → 因为 `default-requeue-rejected: false`，
消息被**丢弃**。你花力气做的死信队列，最后把唯一的证据弄丢了。

#### ⚠️ 但是：只把签名改成 `Message` **并不能**解决问题（实测踩到了）

本节初稿写的是「参数类型用 `org.springframework.amqp.core.Message`，Spring 原样传给你」。
**这条是错的**，实测发现签名改成 `Message` 之后，坏 JSON 依然一行日志都没有、数据库零行、
队列照样被清空 —— 证据还是丢了。

读 Spring AMQP 4.1.1 源码可以确认原因：

| 位置 | 代码 |
|---|---|
| `MessagingMessageListenerAdapter#onMessage`（:183） | **无条件**调 `toMessagingMessage(amqpMessage)` |
| `MessagingMessageListenerAdapter#toMessagingMessage`（:300） | `return (Message<?>) getMessagingMessageConverter().fromMessage(amqpMessage);` |
| `MessagingMessageConverter#fromMessage`（:129） | **无条件**调 `extractPayload(message)` → `payloadConverter.fromMessage(message)` |

也就是说 **payload 转换发生在「推断方法参数类型」之前**，跟你的形参写什么完全无关。
`providedArgumentTypes` 只影响「要不要再转成业务对象」，不影响「会不会先解析一遍」。

#### ✅ 正确做法：给死信监听器单独一个容器工厂

```java
// src/main/java/com/example/seckill/config/RabbitConfig.java
@Bean
SimpleRabbitListenerContainerFactory deadLetterContainerFactory(
        SimpleRabbitListenerContainerFactoryConfigurer configurer,
        ConnectionFactory connectionFactory) {
    SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
    configurer.configure(factory, connectionFactory);   // 先套上 application.yaml 的 manual ack / 并发 / prefetch
    factory.setMessageConverter(new SimpleMessageConverter());  // 再覆盖转换器
    return factory;
}
```

```java
// src/main/java/com/example/seckill/infra/mq/DeadLetterConsumer.java
@RabbitListener(queues = RabbitConfig.DLQ_QUEUE, containerFactory = "deadLetterContainerFactory")
public void onMessage(Message raw, Channel channel) throws IOException { ... }
```

**为什么 `SimpleMessageConverter` 能救**：它的 `fromMessage` 只在
`contentType` 以 `text` 开头时解码成 String、等于 `CONTENT_TYPE_SERIALIZED_OBJECT`
时做 Java 反序列化，**其余情况一律返回原始 `byte[]`，永远不会因为内容不合法抛异常**。
body 自己 `new String(raw.getBody(), StandardCharsets.UTF_8)` 拿，解析失败就存 null，
**body 原样落库**。

> 顺带记住两条：
> 1. `configurer.configure(factory, connectionFactory)` 必须在 `setMessageConverter` **之前**调，
>    否则 manual ack、并发数、prefetch 这些来自 `application.yaml` 的配置会被覆盖掉。
> 2. 教训比结论重要：**「参数类型决定要不要转换」这个说法只对了一半** ——
>    它决定的是「转不转成你的业务类」，不是「要不要解析 payload」。

### 1.3 🔴 为什么落库失败也必须 ack

这是取舍，不是疏忽。

```java
try {
    // 落库
    channel.basicAck(tag, false);
} catch (Exception e) {
    log.error("死信落库失败，原始消息 body={}", body, e);   // ← 证据在这里
    channel.basicAck(tag, false);                          // ← 仍然 ack
}
```

三个选项对比：

| 处理方式 | 后果 |
|---|---|
| `basicAck`（推荐） | 数据库挂了会丢这条死信，但**日志里有完整 body**，能人工补录 |
| `basicNack(requeue=true)` | 数据库挂着 → 每 0.1 秒重投一次 → **CPU 打满 + 日志刷屏**，且永远出不来 |
| `basicNack(requeue=false)` | DLQ 没有自己的 DLX → 消息**直接消失**，日志里也没有 body（因为你没打） |

选 `basicAck` + 打日志，是因为「数据库挂」这件事本身就该由数据库告警来解决，
不该让一个旁路组件把 broker 拖垮。**但前提是日志里必须有完整 body**，否则丢了就真找不回来。

### 1.4 表结构

新建 `sql/V11__mq_dead_letter.sql`（编号接在 `V10__a8_sharding_split.sql` 后面）：

```sql
-- 死信落库表：seckill.order.dlq 里的消息由 DeadLetterConsumer 写进来。
--
-- 为什么不复用 mq_consume_log：
--   那张表是「消费成功/业务失败」的账，有 UNIQUE(msg_id)，一条消息一行；
--   死信是「技术异常/坏消息」的账，同一条消息可能因不同原因死多次，不该有唯一约束。
--   混在一起会让 uk_msg_id 挡住重试记录，也会让幂等闸误判。
CREATE TABLE mq_dead_letter (
    id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    msg_id      VARCHAR(64)           DEFAULT NULL   COMMENT '消息唯一标识（坏 JSON 时为 NULL）',
    order_no    VARCHAR(40)           DEFAULT NULL   COMMENT '订单号（解析不出时为 NULL）',
    student_id  BIGINT                DEFAULT NULL   COMMENT '学生 ID',
    course_id   BIGINT                DEFAULT NULL   COMMENT '课程 ID',
    reason      VARCHAR(50)  NOT NULL                COMMENT '死信原因：rejected/expired/maxlen/unknown',
    body        VARCHAR(1000)         DEFAULT NULL   COMMENT '原始消息体（截断到 1000 字符）',
    create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_create_time (create_time),
    KEY idx_order_no (order_no)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '死信消息（MQ 技术异常的现场）';
```

三个设计点，写之前想清楚：

1. **`msg_id` 没有唯一索引**。同一条消息可能因为「消费者连续三次技术异常」而死三次，
   三次都该留证据。加唯一索引会让第二次 insert 抛 `DuplicateKeyException`，
   然后你的 catch 把它当成「落库失败」，日志里出现一个假的错误。
2. **`body` 用 `VARCHAR(1000)` 而不是 `TEXT`**。死信体一般就是一条 `SeckillMessage`
   的 JSON（约 100 字节），1000 够用；`TEXT` 会把它挤到 off-page 存储，
   查 100 行要多读 100 次页，而这张表的用法是「运维扫最近 100 条」。
   超长就 `body.substring(0, 1000)` 截断。
3. **`reason` 用 `VARCHAR(50)` 存字符串而不是 `TINYINT` 存码**。这张表是给人看的，
   `rejected` 比 `1` 好懂，也不用维护码表。代价是多占 8 字节，无所谓。

### 1.6 消费者

新建 `src/main/java/com/example/seckill/infra/mq/DeadLetterConsumer.java`：

```java
package com.example.seckill.infra.mq;

import com.example.seckill.config.RabbitConfig;
import com.example.seckill.entity.MqDeadLetter;
import com.example.seckill.mapper.MqDeadLetterMapper;
import com.rabbitmq.client.Channel;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.core.Message;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.stereotype.Component;
import tools.jackson.databind.ObjectMapper;

import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.util.List;
import java.util.Map;

/**
 * 死信消费者 —— 只负责留证据，不负责收拾现场。
 *
 * <p>与 {@link SeckillOrderConsumer} 的两个关键差异：
 * <ol>
 *   <li>方法收 {@link Message} 而不是 {@code SeckillMessage}：死信里的 body 恰恰是
 *       转不过去的那种（坏 JSON），走转换器会抛 MessageConversionException，
 *       然后被 default-requeue-rejected=false 丢弃 —— 证据就没了。</li>
 *   <li>任何情况都 ack：落库失败也只打日志，不 requeue。理由见 docs/阶段8-任务书 §1.3。</li>
 * </ol>
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class DeadLetterConsumer {

    private static final int BODY_MAX = 1000;

    private final MqDeadLetterMapper mqDeadLetterMapper;
    private final ObjectMapper objectMapper;

    @RabbitListener(queues = RabbitConfig.DLQ_QUEUE, containerFactory = "deadLetterContainerFactory")
    public void onMessage(Message raw, Channel channel) throws IOException {
        long deliveryTag = raw.getMessageProperties().getDeliveryTag();
        String body = new String(raw.getBody(), StandardCharsets.UTF_8);

        MqDeadLetter record = parse(raw, body);
        log.error("收到死信 reason={} orderNo={} msgId={} body={}",
                record.getReason(), record.getOrderNo(), record.getMsgId(), body);

        try {
            mqDeadLetterMapper.insert(record);
        } catch (Exception e) {
            // 落库失败也要 ack：requeue 会让 broker 每 0.1 秒重投一次，
            // 数据库挂着的时候直接把 CPU 和日志打爆，而且永远出不来。
            // 证据已经在上面那行 log.error 里（含完整 body）。
            log.error("死信落库失败，原始消息 body={}", body, e);
        }
        channel.basicAck(deliveryTag, false);
    }

    /** 解析 body + 读 x-death 头。任何一步失败都降级成 null，绝不抛。 */
    private MqDeadLetter parse(Message raw, String body) {
        MqDeadLetter.MqDeadLetterBuilder b = MqDeadLetter.builder()
                .reason(extractReason(raw))
                .body(body.length() > BODY_MAX ? body.substring(0, BODY_MAX) : body);

        try {
            SeckillMessage m = objectMapper.readValue(body, SeckillMessage.class);
            b.msgId(m.msgId()).orderNo(m.orderNo())
                    .studentId(m.studentId()).courseId(m.courseId());
        } catch (Exception e) {
            // 坏 JSON 是死信的常见形态，不是异常情况，不需要打堆栈。
            log.debug("死信 body 不是合法 SeckillMessage，只存原始内容");
        }
        return b.build();
    }

    /**
     * 从 x-death 头取死信原因。
     *
     * <p>结构是 List&lt;Map&gt;，第一项是最近一次死信：
     * {@code {reason=rejected, queue=seckill.order.queue, count=1, routing-keys=[seckill.order]}}。
     * 没有这个头（比如消息是被直接 publish 到 DLQ 的）就返回 unknown。
     */
    private String extractReason(Message raw) {
        List<Map<String, ?>> xDeath = raw.getMessageProperties().getXDeathHeader();
        if (xDeath == null || xDeath.isEmpty()) {
            return "unknown";
        }
        Object reason = xDeath.get(0).get("reason");
        return reason == null ? "unknown" : String.valueOf(reason);
    }
}
```

几个容易忽略的点：

- `ObjectMapper` 注入的是 **Jackson 3**（`tools.jackson.databind.ObjectMapper`）。
  写成 `com.fasterxml.jackson.databind.ObjectMapper` 能编译通过（`jjwt-jackson` 把它带进了 classpath），
  但**没有对应的 Bean**，启动时报 `No qualifying bean of type ...`。
  这是阶段 1 踩过的坑（`SecurityConfig`），别再踩第二次。
- `objectMapper.readValue(body, SeckillMessage.class)` 对 **record** 也能工作，
  Jackson 3 原生支持 record 的规范构造器反序列化，不需要额外注解。
- `getXDeathHeader()` 是 Spring AMQP 提供的便捷方法（`spring-amqp-4.1.1.jar`，
  `MessageProperties:getXDeathHeader()` 返回 `List<Map<String, ?>>`），
  不要自己去 `getHeaders().get("x-death")` 强转 —— 类型是 `ArrayList<LinkedHashMap>`，
  强转成 `List<Map<String, Object>>` 会有泛型擦除之外的麻烦。

### 1.7 死信体被截断的风险（诚实说明）

`VARCHAR(1000)` + `substring(0, 1000)` 意味着超长 body 只留前 1000 字符。
一条正常 `SeckillMessage` 的 JSON 大约 100~120 字节，够用。
但如果将来消息体变大（比如加了商品快照），这里会静默截断。

**可接受的代价**：这张表的用途是「运维看最近死了什么、为什么死」，不是「完整归档」。
真要完整归档应该走日志系统（ELK / Loki），不是 MySQL。

## 2. 任务 B：库存自动对账

### 2.1 🔴 只修偏高，不修偏低 —— 这是整个任务的核心决策

先看两个方向各自的成因：

| 方向 | 怎么产生的 | 危险吗 | 该不该自动修 |
|---|---|---|---|
| **Redis 偏高**（`redis > db`） | ① confirm 超时但消息其实到了 → 消费者扣了 MySQL，Redis 没还<br>② 手工 `FLUSHDB` 后又 `preheat` 了部分课 | 🔴 **会超卖**：能抢到不存在的名额 | ✅ 修（`preheat` 成 db 值） |
| **Redis 偏低**（`redis < db`） | ① 消息丢了/消费者没跑 → Redis 扣了，MySQL 没扣<br>② 在途请求刚扣了 Redis 还没落单 | 🟡 只浪费名额，安全 | ❌ **不修** |
| **未预热**（`redis == null`） | 从没 `preheat` 过 | 中性 | ❌ 不修（预热是主动行为） |

**为什么偏低绝对不能自动修** —— 这是最容易写错的地方：

```
时刻 T1：请求 A 扣了 Redis（100 → 99），正在插订单，还没提交
时刻 T2：对账任务读到 Redis=99、MySQL=100（因为 A 还没提交）
        → 判定「偏低」→ 若此时 preheat 成 100
时刻 T3：请求 A 提交成功，MySQL 变 99
结果：Redis=100、MySQL=99 → 反过来变成「偏高 1」→ 下一个人能多抢一个名额 → 超卖
```

**自动修偏低，会把一个安全的不一致变成一个危险的不一致。**
所以偏低只 `log.warn`，让人知道「有课浪费了名额」，由人工决定是否 `preheat`。

那偏高自动修会不会有类似的竞态？会，但方向相反：

```
时刻 T1：请求 B 扣了 Redis（100 → 99），还没提交
时刻 T2：对账读到 Redis=99、MySQL=100 → 判定「偏高」？
        不会！99 < 100 是偏低，不修。
```

偏高只有在「Redis 真的比 MySQL 多」时才出现，而 Redis 比 MySQL 多意味着
**有人的扣减没落到 MySQL**。此时 `preheat` 成 db 值是在**收回虚报名额**，
即使中途有在途请求被抹掉一次扣减，结果也只会让 Redis 更少（偏低方向），不会更危险。

> 记住这句：**修偏高是纠错，修偏低是造错。**

### 2.2 一次对账要做多少事

```
1. SELECT course_id, capacity, stock, sold FROM course_stock   ← 一次全表，100 行
2. for each row: redisStock = stockCacheService.getStock(courseId)   ← 100 次 GET
3. 比较 → 分类计数
4. 偏高的调 preheat(courseId) 修正
5. 汇总打一行日志；有偏高/偏低时再单独 warn
```

**为什么不用 `selectList` 分页**：100 行一次拿完最简单，也不会漏。
课程数量级上去之后（万级）再改分页 + `MGET`，任务书 §6 的「明确不做」里写了这条。

**为什么 `getStock` 循环而不是 `MGET`**：`StockCacheService` 接口现在没有批量方法，
为 100 次 GET（每次约 0.1ms，合计 ~10ms）去改接口不值得。
真要优化，改的是接口不是这里。

### 2.3 代码

新建 `src/main/java/com/example/seckill/infra/schedule/StockReconciler.java`：

```java
package com.example.seckill.infra.schedule;

import com.example.seckill.entity.CourseStock;
import com.example.seckill.infra.cache.StockCacheService;
import com.example.seckill.mapper.CourseStockMapper;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.util.List;

/**
 * 库存自动对账 —— 定时比对 Redis 与 MySQL 的剩余名额。
 *
 * <p>🔴 只修「Redis 偏高」，不修「Redis 偏低」。理由见 docs/阶段8-任务书 §2.1：
 * 偏低可能只是「在途请求刚扣了 Redis 还没提交」，此时 preheat 会把这个扣减抹掉，
 * 等请求提交后反而变成偏高 → 超卖。修偏高是纠错，修偏低是造错。
 *
 * <p>压测时必须关掉（{@code --seckill.reconcile-enabled=false}），
 * 否则每轮都会跑一次全表 SELECT + 100 次 Redis GET，污染 QPS 和 P99。
 */
@Slf4j
@Component
@ConditionalOnProperty(name = "seckill.reconcile-enabled", havingValue = "true", matchIfMissing = true)
public class StockReconciler {

    private final CourseStockMapper courseStockMapper;
    private final StockCacheService stockCacheService;

    /** 单轮最多修几门课。Redis 整体被清空时不该一次改 100 个 key 把 Redis 打满。 */
    private final int maxFixPerRound;

    public StockReconciler(CourseStockMapper courseStockMapper,
                           StockCacheService stockCacheService,
                           @Value("${seckill.reconcile-max-fix-per-round:20}") int maxFixPerRound) {
        this.courseStockMapper = courseStockMapper;
        this.stockCacheService = stockCacheService;
        this.maxFixPerRound = maxFixPerRound;
    }

    @Scheduled(fixedDelayString = "${seckill.reconcile-interval-ms:300000}",
               initialDelayString = "${seckill.reconcile-initial-delay-ms:60000}")
    public void reconcile() {
        try {
            ReconcileResult r = reconcileOnce();
            if (r.redisHigher() > 0 || r.redisLower() > 0) {
                log.warn("库存对账发现不一致：{}", r);
            } else {
                log.info("库存对账通过：{}", r);
            }
        } catch (Exception e) {
            // 定时任务的异常必须自己吞掉：@Scheduled 的异常只会打日志，
            // 但会打断这一轮，下一轮照常跑。这里显式 catch 是为了日志更清楚。
            log.error("库存对账任务异常", e);
        }
    }

    /**
     * 执行一轮对账。抽成 public 方法是为了能在单测里直接调，不依赖调度器。
     *
     * @return 本轮统计
     */
    public ReconcileResult reconcileOnce() {
        List<CourseStock> rows = courseStockMapper.selectList(null);
        int consistent = 0;
        int higher = 0;
        int lower = 0;
        int notPreheated = 0;
        int fixed = 0;

        for (CourseStock row : rows) {
            Long redisStock = stockCacheService.getStock(row.getCourseId());
            if (redisStock == null) {
                notPreheated++;
                continue;
            }
            long dbStock = row.getStock().longValue();
            if (redisStock == dbStock) {
                consistent++;
            } else if (redisStock > dbStock) {
                higher++;
                if (fixed < maxFixPerRound) {
                    log.warn("Redis 偏高，收回虚报名额 courseId={} redis={} db={}",
                            row.getCourseId(), redisStock, dbStock);
                    stockCacheService.preheat(row.getCourseId());
                    fixed++;
                } else {
                    log.warn("Redis 偏高但已达单轮修正上限，留给下一轮 courseId={}", row.getCourseId());
                }
            } else {
                // 偏低只告警不修：可能是在途请求，修了会变成偏高。
                lower++;
                log.warn("Redis 偏低（安全方向，不自动修）courseId={} redis={} db={}",
                        row.getCourseId(), redisStock, dbStock);
            }
        }
        return new ReconcileResult(rows.size(), consistent, higher, lower, notPreheated, fixed);
    }

    /** 一轮对账的统计结果。record 让日志一行能打全。 */
    public record ReconcileResult(int checked, int consistent, int redisHigher,
                                  int redisLower, int notPreheated, int fixed) {
    }
}
```

⚠️ 构造器注入的三个理由（阶段 7 的 `PendingOrderSweeper` 已经这么写过，保持一致）：

1. **可单测**：`new StockReconciler(mapper, cache, 20)` 直接 new，不用起 Spring 上下文。
   字段注入（`@Autowired` 挂字段）就做不到这一点。
2. **依赖可见**：构造器签名就是依赖清单，扫一眼就知道它碰哪些外部资源。
   字段注入要把类从头读到尾才知道。
3. **`@Value` 参数可以直接写成构造器形参**：Spring 会按参数解析占位符，
   不需要在字段上挂注解再等反射注入。

## 6. 明确不做

| 不做 | 为什么 |
|---|---|
| 死信自动重投回业务队列 | 会无限循环（重投 → 又失败 → 又进死信），必须先有人看 reason 再决定 |
| 死信消费者改订单状态 | 与 `PendingOrderSweeper` 抢同一行，两边都 `incrementIfPresent` 会多还名额 |
| 偏低自动 `preheat` | 会把安全的不一致变成危险的（§2.1） |
| `MGET` 批量读 Redis | 100 次 GET ≈ 10ms，为它改 `StockCacheService` 接口不值得 |
| 对账结果写库 / 暴露成接口 | 现在只要日志。真要可视化应该接 Prometheus，不是再造一张表 |
| 死信超过 N 条时发告警 | 本机没有告警通道（邮件/webhook 都要配置），写了也验证不了。日志 `log.error` 已足够 |
| 给 `reconcileOnce()` 加 per-course try-catch | 见 §3.2 用例 7 的说明，保持异常冒泡 |

## 8. 做完能得到什么

两个都能在面试里讲，但讲法完全不同。

**死信消费者**（工程完整性题）：

> 「消息可靠性我做了三问：会丢、会重复、会失败。前两个用 confirm + 幂等表解决了，
> 第三个（消费失败）我一开始只做了 `basicNack` 进死信队列，以为就完了。
> 后来复盘发现死信队列没有消费者，等于把失败的消息扔进一个没人看的抽屉。
> 补消费者的时候踩了个坑：方法签名必须收 `Message` 而不是业务对象，
> 否则 Spring 的消息转换器会在坏 JSON 上抛异常，然后消息被丢弃 —— 而坏 JSON 恰恰是
> 死信里最常见的东西。最后定的是「只落库留证据，不改订单状态」，
> 因为改状态会和超时清扫抢同一行。」

**自动对账**（判断力题，比上面那个值钱）：

> 「Redis 和 MySQL 的库存会有不一致的窗口，我加了个定时对账。
> 但这里有个反直觉的地方：**Redis 偏高要修，偏低不能修**。
> 偏高意味着有人的扣减没落到 MySQL，是虚报名额，会超卖，必须收回来。
> 偏低看起来也是不一致，但它可能只是「一个请求刚扣了 Redis、还没提交」——
> 这时候你去 `preheat` 修正，等那个请求提交完，反而变成偏高。
> **修偏高是纠错，修偏低是造错。**
> 我给这条结论专门写了一个单测，谁将来顺手把偏低也修了，测试立刻变红。」

第二个故事之所以值钱，是因为它不是一个「我做了什么」的清单，
而是「我差点做错、想清楚了才没做」的判断过程。面试官更信这个。
