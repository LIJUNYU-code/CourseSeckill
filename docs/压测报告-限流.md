## 1. 这一轮要回答的问题

前几份报告问的是「准不准」「多快」。限流这一版要回答的是完全不同的问题：

| # | 问题 | 判据 |
|---|---|---|
| 1 | 限流会不会误伤正常流量？ | 1200 RPS 下 `biz_throttled` 必须是 **0** |
| 2 | 阈值调低之后真的会拦吗？ | 把全局桶压到 300/300，`biz_throttled` 必须显著 > 0 |
| 3 | 被拦的请求成本有多低？ | `throttled_latency` 必须远低于 `biz_latency` |
| 4 | 限流生效后 P95 会不会反而变差？ | `http_req_duration` 的 P95 不应劣化 |

**第 1 问和第 2 问是一对。** 只测「能拦住」是危险的——把阈值设成 1/s 也「能拦住」，但那是在砸系统。必须同时证明「该放的时候没拦」。

### 2.1 内存必须先腾出来（否则数据全部作废）

本轮开始前实测**可用内存仅 0.49 GB**（总 15.61 GB）。关掉 IDEA（1872 MB）与 PyCharm（819 MB）后回到 **6.86 GB**。

> ⚠️ 这个项目的所有压测数字都建立在「内存够」的前提上。可用内存低于 3 GB 时，测出来的 P95 里混着换页开销，不是服务的真实表现。`loadtest/precheck.ps1` 就是为此写的。

### 2.2 为什么新写一个脚本，不复用 `seckill-v3.js`

| 原因 | 说明 |
|---|---|
| 压力模型不对 | v3 用 `per-vu-iterations`，压力由 VU 数决定，没法指定 RPS。对比实验必须固定**到达速率**，否则三组之间的 RPS 都不一样，比不了 |
| 计数口径冲突 | v3 把 429 算进 `biz_rejected`，而 `biz_rejected` 挂了 `count<1` 的 threshold → 限流一生效脚本就判失败 |
| 缺少分层延迟 | 必须把 429 的延迟单独统计，才能回答「拦截的成本有多低」 |

新脚本用 `constant-arrival-rate`：`rate: RPS`，`timeUnit: '1s'`，`preAllocatedVUs: 300`，`maxVUs: 900`。

⚠️ **`maxVUs` 绝不能超过学生池大小（900）**。超了会让多个 VU 共用同一个学生，请求撞 `uk_student_course` 返回 409「你已选过」，把限流实验污染成唯一索引实验——这是 v4 阶段踩过的坑。

⚠️ `setupTimeout: '300s'` 也是必须的：900 个学生 × BCrypt 约 60 ms/次 ≈ 54 秒，默认的 60 秒会超时。

### 4.2 四条判据，逐条对账

| # | 问题 | 结果 | 判定 |
|---|---|---|---|
| 1 | 1200 RPS 会不会被误伤 | A 组 `biz_throttled = 0` | ✅ 不误伤 |
| 2 | 阈值压到 300 会不会拦 | B 组 `biz_throttled = 19125` | ✅ 会拦 |
| 3 | 被拦的请求成本多低 | `throttled_latency` P95 = **1 ms**（avg 412 µs） | ✅ 几乎零成本 |
| 4 | 限流后 P95 会不会劣化 | 60.12 → 60.59 → 58.55 ms | ✅ 无劣化（差异在噪声内） |

**第 3 条是这轮最有价值的数字。** B 组放行的请求 `biz_latency` P95 涨到 105 ms，被拦的只有 1 ms——两个数量级的差距说明限流的判定发生在业务逻辑**之前**，被拒绝的请求根本没进 Tomcat 的业务线程。如果限流挂在 `@Aspect` 上（请求已经进完 Spring MVC 才拦），这个数字会接近 105 ms，限流就白做了。

### 4.3 B 组为什么 `biz_latency` 从 2 ms 涨到 105 ms

不是变慢了，是**分母变了**。

- baseline / A：`biz_latency` 统计的 17000+ 个请求几乎全是「Redis 说没名额」的快速 409，所以 P95 = 2 ms。
- B：19125 个请求在限流层就被挡回（不进 `biz_latency`），剩下能进业务的是 4153 个 409 + 364 个 200。364 个 200 里有一部分真的走到了 MySQL 查重、发消息，成本高得多。

换句话说，B 组的 `biz_latency` 更接近「真实下单的成本」，前两组因为绝大多数请求在第一步就被挡回，反而看不出来。

## 5. 🔴 本轮发现的真缺陷：冷启动惊群，以及限流把它放大了

### 5.1 现象

`biz_queued`（HTTP 200，即「已受理、等待落单」）三组分别是 **100 / 299 / 364**，后两组远超 `capacity = 100`。

最终账目是对的（三组都是）：

```
course_id=88  capacity=100  stock=0  sold=100  （守恒）
订单 status=1（成功）→ 100 条
```

但 A 组多出 **199 条 `status=2`（失败）**，B 组多出 **200 条**。这些学生拿到了「受理成功」的响应，然后在消费者里被判失败。**没有超卖，但 Redis 门禁被击穿了。**

### 5.2 根因

`src/main/java/com/example/seckill/service/impl/SeckillServiceImplV3MqAsync.java:138-142`：

```java
//Redis 门禁
Long left = stockCacheService.tryDecrement(courseId);
if (left == -1L) {
    stockCacheService.preheat(courseId);   // ← 这里
    left = stockCacheService.tryDecrement(courseId);
}
```

`tryDecrement` 返回 `-1` 表示 **Redis 里没有这个 key**（未预热）。设计意图是「第一次访问时自动预热，用户无感」。

但 `StockCacheServiceImpl.preheat()` 是**非原子的覆盖写**：

```java
// StockCacheServiceImpl.java:51-62
public void preheat(Long courseId) {
    CourseStock stock = courseStockMapper.selectByCourseId(courseId);
    ...
    stringRedisTemplate.opsForValue().set(stockKey(courseId), String.valueOf(stock.getStock()));
}
```

`set` 不管 key 在不在都写。冷启动瞬间，N 个并发请求同时拿到 `-1`，**每个都去 preheat**，每个都写一次 `stock=100`。

危险的不是「写了 N 次 100」，而是**写的时机**：

```
情况一（无害）：所有 SET 挤在同一个瞬间完成，之后才开始扣减
  t0  200 个请求同时拿到 -1
  t1  200 个请求全部 SET 100（3 ms 内做完）
  t2  200 个请求各自 DECRBY → 100 个成功、100 个拿到 -2「名额已满」
  → 受理数精确 = 100 ✓

情况二（有害）：SET 被摊开，和 DECRBY 交错
  t0  请求 A 拿到 -1 → SET 100
  t1  A 扣到 99 ... 陆续扣到 40（已卖 60 个）
  t2  请求 B 才执行 SET 100  ← 已卖的 60 个名额凭空复活
  t3  继续扣 → 又能卖 60 个
  → 受理数 > 100 ✗
```

**决定是情况一还是情况二的因素，是「SET 的时间离散程度」。** 这正是这一轮最反直觉的发现。

### 5.3 日志证据（重跑，每组独立进程 + 独立日志区间）

第一版统计是错的，这里记录教训：第一版三组在**同一个应用进程里连续跑**，日志文件是同一份，我用正则做**全量匹配**，拿到的是**累计值**而不是每轮值（baseline 的 162 是跑到当时的累计，A 的 63、B 的 38 反而是各自单轮）。三组数字口径不同却当成可比，于是得出了「预热行数 = 超额数」这个**并不成立的结论**。

重跑后的正确做法：每组**独立启动应用进程 + 独立日志文件**，压测前记录 `(Read-Shared $log).Length` 作为 mark，压测后只统计 `$all.Substring($mark)`。

| 组 | 本轮预热行数 | 时间窗口 | 离散度 | `biz_queued` | 受理超额 | 失败订单 |
|---|---|---|---|---|---|---|
| baseline（无限流，1200 RPS） | **200** | 11:09:49.753 ~ .755 | **3 ms** | **100** | **0** | 0 |
| A（限流 2000/1500，1200 RPS） | **115** | 11:11:16.870 ~ .890 | **20 ms** | **299** | **+199** | 199 |
| B（限流 300/300，1600 RPS） | **50** | 11:12:55.790 ~ .892 | **102 ms** | **364** | **+264** | 200 |

三组预热行数分别是 200 / 115 / 50，**受理超额却是 0 / 199 / 264——完全反向**。这个反向关系恰恰是解开谜题的钥匙：

- baseline 预热 **最多**（200 次），但全部挤在 **3 毫秒**内 → 情况一 → 一次都没多卖。
- B 组预热 **最少**（50 次），却摊在 **102 毫秒**里 → 情况二 → 多卖 264 个。

**限流本身把请求「摊开」了，于是把原本无害的惊群变成了有害的。** 这是加限流时完全没预料到的副作用。

> 注：日志里的中文必须按 **UTF-8** 读。第一版我用 GBK（936）解码，`预热完成` 匹配数为 0，一度误判成「preheat 根本没执行」。应用 logback 输出是 UTF-8，只有 Maven/surefire 的控制台输出才是 GBK。

### 5.4 决定性对照实验

相关性不够，还需要因果。做了一组**只改一个变量**的对照：配置与 A 组完全相同（限流 2000/1500、1200 RPS × 15s、900 学生、课程 88），**唯一差别是压测开始前先用 `SET seckill:stock:88 100` 把 key 预热好**，让 `-1 → preheat` 这条路径根本不触发。

| 实验 | 压测前 Redis | 本轮预热行数 | `biz_queued` | DB 结果 |
|---|---|---|---|---|
| **A（冷启动）** | 删除 key | **115** | **299** | stock=0 sold=100，succ=100 **fail=199** |
| **A-hot（热缓存）** | `SET seckill:stock:88 100` | **0** | **100** | stock=0 sold=100，succ=100 **fail=0** |

**同一份配置、同一个脚本、同样的 RPS 与学生池，唯一差别是 key 在不在：299 → 100，失败订单 199 → 0，预热日志 115 → 0。**

这就是因果，不是相关性。三条数字同时归零/归位，没有别的解释。

### 5.5 还有一个更直接的证明（与并发无关）

手动把 Redis 扣到 40（模拟「已经卖掉 60 个」），然后调一次预热接口：

```
DB stock      = 100
调用前 Redis  = 40      ← 已经卖掉 60 个
POST /api/admin/cache/stock/88 → {"code":200,"message":"操作成功"}
调用后 Redis  = 100     ← 被重置回满额，60 个名额凭空复活
```

**管理员点一次「预热」按钮，就能让已经卖出去的 60 个名额重新可卖。** 这条 100% 可复现、与并发无关，是 `preheat()` 用 `SET` 覆盖写这一代码事实的直接后果。

### 5.6 为什么最终没有超卖

三道防线兜住了：

1. **消费者事务里的条件更新** —— `UPDATE course_stock SET stock=stock-1 WHERE stock > 0`，扣不动就回滚、把订单标成 `status=2`。这是真正守住正确性的那一道。
2. **`uk_student_course` 唯一索引** —— 同一学生同一课程只能一单（B 组那 359 个 `biz_duplicate` 就是它挡下的）。
3. **MySQL 的 `CHECK (stock >= 0)`** —— 兜底，但 v0 阶段已经证明过它**单独防不住**（v0 超卖 200 单时 stock 根本没到负数，因为它读-改-写的是绝对值）。

**这恰好说明了 v3 架构的设计意图：Redis 只负责「减少无效请求」，正确性由 MySQL 保证。** 所以门禁被击穿的后果是「多产生失败订单、多打无效请求」，而不是「超卖」。

但体验上有代价：**199 / 264 个学生收到了 200，最后订单却是失败状态。** 对一个抢课系统来说，这比直接告诉他「名额已满」更糟。

### 5.7 正确做法（这是要改的地方）

问题不在「要不要预热」，而在「预热必须是幂等的、只在 key 不存在时写」。

**方案 A：`SETNX`（最小改动）**

```java
// preheat 里把 set 换成 setIfAbsent
Boolean written = stringRedisTemplate.opsForValue()
        .setIfAbsent(stockKey(courseId), String.valueOf(stock.getStock()));
// written == false 表示别人已经预热过了，什么也不做
```

本项目 key 不过期（`StockLuaScript.DECREMENT` 里没有 `EXPIRE`），所以不存在「key 过期后 `setIfAbsent` 拒绝写」的问题。**但要注意 `StockReconciler` 依赖 `preheat()` 做「用 MySQL 覆盖 Redis」的修正动作——如果直接把 `preheat` 改成 `setIfAbsent`，对账就修不动了。** 所以正确做法是**拆成两个方法**：

- `preheatIfAbsent(courseId)` —— 冷启动路径用，`SETNX` 语义。
- `overwrite(courseId)` —— 对账/管理端用，保持 `SET` 语义（它本来就是要覆盖）。

**方案 B：把「判存在 + 写」做成一个 Lua（推荐，和已有的扣减脚本同风格）**

```lua
-- PREHEAT: KEYS[1]=stock key, ARGV[1]=mysql stock
if redis.call('EXISTS', KEYS[1]) == 1 then
    return tonumber(redis.call('GET', KEYS[1]))   -- 已存在，返回现值，不覆盖
end
redis.call('SET', KEYS[1], ARGV[1])
return tonumber(ARGV[1])
```

好处是**返回值有用**：调用方拿到「预热后的真实库存」，可以直接拿它做第一次扣减判断，省掉「预热后再 `tryDecrement` 一次」的往返，也少一个竞态窗口。

**方案 C：启动时预热 + 冷启动直接拒绝**

最保守：应用启动时 `preheatAll()`，运行期遇到 `-1` 一律返回 503「系统初始化中，请稍后重试」。好处是运行期完全没有写 Redis 的路径；坏处是新增课程要重启或走管理接口。

> 我倾向 **方案 B + 拆分 `preheatIfAbsent` / `overwrite`**：改动小、和现有 Lua 风格一致、不破坏对账。但这个项目是你自己写的，方案你定。

### 5.8 这个缺陷值得写进面试话术

> 「压测时发现 Redis 受理了 299 单而课程只有 100 个名额，但数据库账目是守恒的——很容易就此判定『没问题』。查日志发现冷启动时 115 次缓存预热集中在一瞬间：每个并发请求都判断『key 不存在』然后各自 `SET` 覆盖写，把已经扣减的库存重置回满额。
>
> 但真正有意思的是对照实验：**不加限流时预热 200 次、受理数却精确等于 100；加了限流预热只剩 115 次、受理数反而涨到 299。** 原因是预热本身不危险，『所有 SET 挤在同一瞬间』反而无害（之后才开始扣）；而限流把请求摊开到 20 毫秒，`SET` 和 `DECRBY` 交错，才真的让名额复活。用『压测前手动预热 key』做单变量对照，受理数从 299 精确回到 100、失败订单从 199 归零，因果就闭合了。
>
> 结论两条：**缓存的写入路径也必须幂等**（『key 不存在就重建』在多线程下就是惊群）；**加一个保护性设施可能放大另一个隐藏缺陷**，所以每次改动都要重跑同一套判据。」

## 6. 学生桶单独验证（连打 10 次）

全局桶在 1200 RPS 下不误伤，学生桶还得单独证明。用同一个学生（`S000000001`）对课程 88 连打 10 次：

| 第几次 | HTTP | 说明 |
|---|---|---|
| 1 | 200 | 受理成功 |
| 2~5 | 409 | 「你已选过该课程」—— 学生桶还有令牌，进到了业务逻辑 |
| 6~10 | **429** | `Retry-After: 1`、`X-RateLimit-Remaining: 0` |

**第 6 次开始 429，精确吻合 `student-capacity = 5`。** 这个数字不是巧合，是配置项直接推出来的，所以这条验证的可信度比「看起来拦住了」高得多。

另外两条边界：

| 场景 | 结果 |
|---|---|
| 管理员（ADMIN）连打 8 次 | 全部 403（抢课需要 STUDENT 角色），**零 429** |
| 同一学生 cancel 连打 8 次 | 全部正常，**零 429**（`shouldNotFilter` 放行 `/cancel`） |

管理员那条尤其值得说：`sys_user.id = 1` 恰好等于 `S000000001` 的 id，如果 `currentStudentId()` 忘了判 `ROLE_STUDENT`，管理员会被当成学生 1 限流，而 429 是个看起来「很合理」的响应——**这种 bug 不会报错，只会让管理员莫名其妙被限流**。单测 `RateLimitFilterTest.adminNotLimitedByStudentBucket` 就是钉这个的。

## 7. 可靠性：fail-open 的意外实证

限流是**保护性设施，不是正确性设施**。Redis 挂了应该放行而不是全站 503。

这条本来只是设计意图，本轮意外拿到了真实证据：有一次本机 Memurai 进程退出，请求照常通过，日志里打出：

```
限流执行失败，降级放行（限流当前未生效） key=seckill:rate:global
```

`RateLimitServiceImpl` 的 `catch (Exception e)` 分支把异常吞掉并返回 `degradedPass()`，`RateLimitFilter` 收到 `degraded() == true` 就打这条日志然后放行。

对应的单测：`RateLimitServiceImplTest.redisThrows_failsOpen`（用 `thenThrow(new RedisConnectionFailureException(...))` 打桩）。变异测试里把 fail-open 改成 `throw new IllegalStateException(e)`，这条立刻变红。

## 8. 测试与变异验证

限流相关的三个测试类（本轮新增，共 20 条）：

| 类 | 条数 | 钉的是什么 |
|---|---|---|
| `RateLimitServiceImplTest` | 7 | 脚本返回值解析、fail-open、非法参数不碰 Redis |
| `RateLimitFilterTest` | 10 | 路径过滤、两层桶、429 响应体、管理员不被学生桶拦 |
| `RateLimitLuaScriptTest` | 3 | Lua 文本契约（关键语句还在不在） |

全量 `clean test` → **`Tests run: 99, Failures: 0, Errors: 0`**（原 79 + 20）。

### 8.1 为什么需要「文本契约测试」

`RateLimitLuaScriptTest` 看起来很奇怪——它不断言行为，只断言 `TOKEN_BUCKET` 这段字符串里有没有某几句话。理由很实在：

**Lua 脚本在单测里一行都不会执行。** 它被包在 `DefaultRedisScript` 里交给 `StringRedisTemplate.execute(...)`，而单测里 `StringRedisTemplate` 是 mock 的。也就是说，把 `math.floor(tokens)` 写回 Redis 这种致命改动，Java 侧单测照样全绿。

所以这一类只能测「这几句还在不在」：

- `scriptKeepsAllCriticalStatements`：断言含 `HMGET`、`if tokens == nil then`、`if elapsedMs < 0 then elapsedMs = 0 end`、`if tokens > capacity then tokens = capacity end`、`EXPIRE`、`return {0, math.floor(tokens), waitMs}`。
- `floorNeverWrittenBack`：断言**不含** `'tokens', math.floor(tokens)`，但含 `math.floor(tokens)`（反向确认，避免写成永远绿的断言）。理由：写回时取整，0.37 个令牌每次调用都被扔掉，10/s 的桶被削成 5/s，而且不报错。
- `cannotInstantiate`：反射构造抛 `AssertionError`（常量类不许 new）。

### 8.2 五项变异测试

| # | 变异 | 结果 |
|---|---|---|
| 1 | fail-open 改成 `throw new IllegalStateException(e)` | ✅ `redisThrows_failsOpen` 变红 |
| 2 | `currentStudentId` 去掉 `ROLE_STUDENT` 判断 | ✅ `adminNotLimitedByStudentBucket` 变红 |
| 3 | `shouldNotFilter` 去掉 `/cancel` 放行 | ✅ `cancel_passesThrough` 变红 |
| 4 | Lua 把 `math.floor` 写回 Redis | ✅ `floorNeverWrittenBack` 变红 |
| 5 | `script.setResultType(List.class)` → `Long.class` | ✅ **编译期就拦住**：`不兼容的类型: Class<Long> 无法转换为 Class<List>` |

第 5 项值得单独说：`setResultType(Long.class)` 接多值脚本时，Spring 拿到的是**最后一个元素**（`retryAfterMs`），会让判定完全反转（该放的拦了、该拦的放了）且日志零异常。这个 bug 在阶段 10 的 review 里被实测推翻过初稿。所幸改成 `Long` 会编译失败——但如果有人绕过泛型（比如 `@SuppressWarnings` 或反射），单测是抓不到的。

## 9. 踩过的坑（环境层，与业务无关但会毁掉实验）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | **RabbitMQ 密码两处不一致** | 应用启动即崩：`ACCESS_REFUSED - Login was refused using authentication mechanism PLAIN` | `application-local.yaml` 里的密码已过期，`.env` 里的是新的。**profile yaml 的字面值优先级高于 `${RABBITMQ_PASSWORD:}`，两处必须一致** |
| 2 | **5672 端口不是本机 RabbitMQ** | `Get-Service *rabbit*` 为空却连得上 | `Get-NetTCPConnection -LocalPort 5672` 显示 PID 是 `wslrelay.exe` + `com.docker.backend`，是 WSL 转发的容器 |
| 3 | **k6 的 stderr 被 PowerShell 当成致命错误** | `$ErrorActionPreference='Stop'` 下脚本中断，报 `NativeCommandError` | k6 只要往 stderr 写日志就触发。用 `cmd /c "\"$k6\" run --quiet \"$script\" > \"$out\" 2>&1"` 绕开 |
| 4 | **`-replace` 只接受 2 个元素** | `-ireplace 运算符只允许后面包含 2 个元素` | 拼接表达式被解析成 4 参数。用 `[regex]::Replace()` 或先算好字符串 |
| 5 | **`.ps1` 每次 edit 后 BOM 丢失** | 脚本里的中文变成乱码 | `New-Object System.Text.UTF8Encoding($true)` 补回 |
| 6 | **日志编码判断错，中文匹配全落空** | `预热完成` 计数为 0，误判「preheat 没执行」 | 应用 logback 输出是 **UTF-8**；只有 Maven/surefire 控制台是 GBK。用 `[System.Text.Encoding]::UTF8` 读应用日志 |
| 7 | **多组实验共用一份日志做全量正则** | 拿到的是**累计值**，三组口径不一致 | 每组独立进程 + 独立日志；压测前记 `.Length` 作 mark，只统计 `Substring(mark)` |

## 11. 结论

### 11.1 一句话

限流本身工作正常（不误伤、能拦、成本 1 ms），但这一轮**顺带挖出一个比限流重要得多的缺陷**：冷启动时非原子的缓存预热会惊群，把已扣减的库存重置回满额，导致 Redis 门禁被击穿、用户拿到「受理成功」却在消费者里失败。**而限流这个「保护性设施」反而把这个隐藏缺陷放大了——它把请求摊开，让预热与扣减交错。**

### 11.2 学到的东西

1. **限流要证明两件事**：「该拦的拦住了」和「该放的不误伤」。只做前者，阈值调成 1/s 也能通过。
2. **限流的价值体现在被拦请求的成本上**。1 ms vs 105 ms 说明它挡在业务逻辑之前；如果这个数字接近 105 ms，说明拦晚了。
3. **`biz_queued > capacity` 是个强信号**。账目守恒（`stock+sold=capacity`）只能证明「最终没超卖」，证明不了「门禁没被击穿」。两个判据必须同时看——这和 v1-pessimistic 那次「双扣但账目守恒」是同一类教训。
4. **缓存写入路径也必须幂等**。「key 不存在就重建」在多线程下就是惊群。`SET` 换成 `SETNX` 或者用 Lua 判存在；但要先分清「冷启动填充」和「对账覆盖」是两种语义，不能一刀切。
5. **对照实验比日志更有说服力**。这次我自己先写错了一版结论：把「预热 162 行」和「受理 120 个」当成因果，实际三组数字根本对不上，而且是**反向**的。单变量对照（热缓存 vs 冷启动：299 → 100，失败单 199 → 0）才是因果。
6. **统计口径比统计工具更容易出错**。同一份日志做全量正则拿到的是累计值；日志编码猜错会让匹配数直接变 0。这两次都差点让我得出相反结论。
7. **加保护性设施要重跑全部判据**。限流把 `biz_queued` 从 100 推到 299，不是限流坏了，而是它改变了请求的时间分布，暴露了另一个缺陷。
8. **测试写在缺陷之后**。这一轮的三个测试类都是在功能写完、review 完才补的，所以变异测试能立刻发现「哪条断言其实不咬人」。

### 11.3 面试话术

> **问：你怎么验证限流真的生效了？**
> 三组对照。基线关掉限流，A 组按线上预期配 2000/1500，B 组故意压到 300/300。判据不是「B 组有 429」，而是四条同时成立：A 组 429 必须为 0（不误伤）、B 组 429 显著大于 0、被拦请求的 P95 只有 1 ms 而放行的有 105 ms（说明拦在业务之前）、整体 P95 不劣化。
>
> **问：这一轮最大的收获？**
> 不是限流本身，是顺带发现的缓存惊群，以及「保护性设施会放大隐藏缺陷」这件事。压测时发现 Redis 受理了 299 单而课程只有 100 个名额，但数据库账目守恒——很容易就此判定「没问题」。查日志发现冷启动时 115 次缓存预热集中在一瞬间：每个并发请求都判断「key 不存在」然后各自 `SET` 覆盖写。
>
> 真正有意思的是对照：**不加限流时预热 200 次、受理数精确等于 100；加了限流预热只剩 115 次、受理数反而涨到 299。** 因为预热本身不危险，「所有 SET 挤在同一瞬间」反而无害；限流把请求摊开到 20 毫秒，`SET` 和 `DECRBY` 交错，名额才真的复活。用「压测前手动预热 key」做单变量对照，受理数从 299 精确回到 100、失败订单从 199 归零，因果闭合。
>
> 顺带一个方法论教训：我第一版结论是错的——三组实验共用了同一份日志做全量正则，拿到的是累计值，还得出了「预热行数 = 超额数」这个假规律。**先保证口径，再谈结论。**
