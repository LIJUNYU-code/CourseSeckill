# 压测报告 v2：Redis + Lua 库存门禁

> 项目：选课秒杀引擎 `seckill-course`
> 版本：`v2-redis-lua`
> 日期：2026-11-14
> 环境：Windows 11 Build 26200 / i7-14650HX（16 核 24 线程）/ 内存 15.61 GB / JDK 26.0.1 / Spring Boot 4.1.1 / MyBatis-Plus 3.5.17 / MySQL 8.0.45 / Memurai 8.2.10（Redis 8）/ k6 v0.55.0

---

## 1. 这一版要回答的问题

v1 结束时，系统已经**没有超卖**了。那 v2 还要解决什么？

v1 的数字：300 并发、100 个名额，成功 100、超卖 0。看着完美。但代价是 **P95 = 339 ms、P99 = 344 ms**，而且：

```
300 个请求 → 300 次 UPDATE → 200 次必然失败
```

**200 个注定失败的请求，每一个都占用了 MySQL 的一行锁、一条连接、一次磁盘相关操作**。它们的唯一作用就是被告知"名额已满"。

v2 的目标不是"更快"，是**把不该进数据库的流量挡在数据库外面**。

所以本报告真正要回答的是三个问题：

1. 门禁**真的挡住了**吗？（不是"变快了"，而是"少打了数据库"）
2. 挡住之后**还卖对了吗**？（成功单、超卖、守恒、Redis 对账）
3. 挡完之后**瓶颈去哪了**？

> 🔴 第 1 问是本阶段的灵魂。只看 P95 变快是不够的——变快可能是因为机器今天心情好。
> 必须直接测量 MySQL 少挨了多少次 `UPDATE`。

## 2. 环境与前提

### 2.1 关键前提：隔离级别必须是 REPEATABLE-READ

```sql
SELECT @@global.transaction_isolation;
-- REPEATABLE-READ
```

这一行决定了 v2 的行为是否符合预期。**如果谁把它改成 READ-COMMITTED，下面的结论全部作废**（v1 阶段已经吃过这个亏：CAS 版本在 RC 下"看起来"能跑通，其实是掩盖了重试边界的问题）。

### 2.2 Redis 必须活着，而且它不会自己起来

Memurai 重启后**不会自动启动**。这次验证的第一轮就全 500，日志：

```
org.springframework.data.redis.RedisConnectionFailureException: Unable to connect to Redis
  at com.example.seckill.infra.cache.impl.StockCacheServiceImpl.getStock(StockCacheServiceImpl.java:80)
```

手动拉起：

```powershell
Start-Process D:\tools\Redis\memurai.exe -ArgumentList "D:\tools\Redis\memurai.conf" -WindowStyle Hidden
D:\tools\Redis\memurai-cli.exe ping   # 必须是 PONG
```

**这个故障本身是有价值的**：Redis 挂着的时候，抢课返回的是 `500 系统繁忙，请重试`，**不是**假装"名额已满"。这正是 `StockCacheServiceImpl.tryDecrement` 里那个 `catch` 不把异常吞成 `-2` 的原因——**故障必须暴露成故障，不能伪装成业务拒绝**。

## 3. 🔴 最重要的证据：门禁真的挡住了

### 3.1 测量方法

`Com_update` 是 MySQL 的全局计数器，记录 `UPDATE` 语句执行了多少次。

```sql
SHOW GLOBAL STATUS LIKE 'Com_update';
```

压测前后各取一次，差值就是这个版本在压测期间真的执行了多少次 UPDATE。

> 注意：这是全库累计值。压测期间不能有别的程序在写这个库（IDEA 数据库窗口、其他服务）。本次测量前后确认无其他写入。

### 3.2 对照实验

同一场景、同一台机器、连续跑，只切换 `--seckill.strategy`：

| 版本 | `Com_update` 前 | 后 | **增量** | 成功单 |
|---|---|---|---|---|
| **v2-redis-lua** | 340 | 440 | **100** | 100 |
| v1-optimistic | 441 | 741 | **300** | 100 |

**增量比例 100 : 300。**

300 个请求里，v1 每一个都执行了 UPDATE（100 次成功扣减 + 200 次 `WHERE stock > 0` 不成立但语句确实执行了）。v2 只有 100 次——**另外 200 个请求在 Redis 就返回了，一次数据库都没碰**。

这个数字精确对应"200 个请求被挡在门外"，不是估算，是计数器。

### 3.3 为什么这条比 P95 更有说服力

P95 变快有很多种原因：机器更闲、GC 更配合、连接池预热了。**但 `Com_update` 增量不会骗人**——它是数据库自己记的账。

如果 v2 的 `Com_update` 还是 300，那就说明：Redis 门禁没生效，代码虽然调用了 Lua，但不管返回什么都继续往下走了数据库。这种情况下 P95 哪怕降到 100 ms，也是假象，200 个请求仍在消耗数据库资源。

**这一条是本阶段唯一不可替代的验收项。**

### 3.4 另一个证据：`min` 响应时间

| 版本 | `min` |
|---|---|
| v2-redis-lua | **13.17 ms** |
| v1-optimistic | 64.90 ms |

v2 的最小耗时 13 ms 就是那条最短路径：一次 Redis Lua 往返 → 返回 409。v1 的 64.9 ms 是它的物理下限——必须访问数据库。

## 5. 🔴 瓶颈转移：门禁挡住了，但瓶颈没消失

### 5.1 预测 vs 实测

任务书 §11.3 写的预测：

| 指标 | 预测 | 实测 | 偏差 |
|---|---|---|---|
| 成功单 | 100 | 100 | ✅ 准 |
| 超卖 | 0 | 0 | ✅ 准 |
| 守恒 | 100 | 100 | ✅ 准 |
| P95 | **< 200 ms** | **255.6 ms** | ❌ **偏高 28%** |
| P99 | **< 250 ms** | **330.4 ms** | ❌ **偏高 32%** |
| `Com_update` | ~100 | **100** | ✅ 精确 |

**门禁生效了（Com_update 精确 100），但延迟没降到预期。**

### 5.2 为什么没降到位

因为剩下的 100 个请求仍然全部串行在同一个 MySQL 行锁上：

```sql
UPDATE course_stock SET stock = stock - 1, sold = sold + 1
WHERE course_id = 88 AND stock > 0
```

这 100 条语句改的是**同一行**（`course_id = 88`）。InnoDB 的行锁让它们必须排队，一条一条执行。100 次 × 约 2 ms ≈ 200 ms，加上网络往返和 JSON 序列化，与实测的 255 ms 吻合。

**这就是"瓶颈转移"**：v2 解决了"数据库挨打太多"，但没解决"同一行串行更新"。每次优化只挪动瓶颈的位置，不会消灭瓶颈。

### 5.3 这恰好是 v3 的靶子

v3（MQ 异步削峰）要解决的就是这个：让 100 个成功请求不再同步等待 MySQL 写完，而是把订单丢进队列、立刻返回"排队中"，后台消费者慢慢扣库存、写订单。

**到那时 P95 会降到 50 ms 以下**，但代价是"响应不再代表最终结果"——用户看到"排队中"要等几秒才能查到自己选上了没有。这是一个**业务语义的让步**，不是纯性能提升。这也是为什么 v3 必须做，而不是可选。

## 6. 正确性验证（比性能更重要）

性能快 3 倍但卖错 1 单，这一版就是失败品。所以下面这组验证优先级更高。

### 6.1 七项逐条

| # | 场景 | 预期 | 实测 | 判定 |
|---|---|---|---|---|
| 1 | 预热课程 88 | Redis=100、DB `stock=100 sold=0`、`consistent=true` | 完全一致 | ✅ |
| 2 | 学生抢课 1 次 | 200、`status=1`、Redis 99、DB `stock=99 sold=1` | `orderNo=...5783`、一致 | ✅ |
| 3 | 退课 | 200、**`status=3`**、DB `stock=100 sold=0`、Redis 100 | `{"status":3}`、一致 | ✅ |
| 4 | 再退一次 | 409，DB/Redis 不变 | 409「该课程当前状态无法退课」，仍是 100 | ✅ |
| 5 | 退课后重选（R5） | 200、**同一个 `orderNo`**、订单数仍为 1 | 同 `orderNo`、订单数 1 | ✅ |
| 6 | 并发退课 10 次 | 1×200 + 9×409、`stock` 只 +1 | **1×200 + 9×409**、`stock=100`（不是 109） | ✅ |
| 7 | 对账接口 | `consistent=true` | 一致 | ✅ |

### 6.2 第 6 项为什么最关键

如果退课写成"读出订单 → 改状态 → 归还库存"的朴素实现，10 个并发请求都会读到 `status=1`，都会改成 3，`returnStock` 执行 10 次：

```
stock: 99 → 100 → 101 → ... → 109
守恒: stock + sold = 109 ≠ capacity = 100
```

**账目当场崩，而且没有任何报错**。防住它的是三条 `UPDATE` 里的状态条件：

```sql
-- 订单状态条件更新：只有当前是 1 才能改成 3
UPDATE seckill_order SET status = 3 WHERE id = ? AND status = 1;
-- 返回 0 行 → 抛异常 → 整个事务回滚 → returnStock 不会执行

-- 库存归还自带下界保护
UPDATE course_stock SET stock = stock + 1, sold = sold - 1
WHERE course_id = ? AND sold > 0;
```

`affected rows` 才是唯一可信的答案。这也是整个项目从 v1 开始贯穿到 v2 的主线。

### 6.3 退课的顺序问题（这一版最容易做错的地方）

退课要动两个存储：MySQL（订单状态 + 库存）和 Redis（余量）。顺序错了会超卖。

**判据只有一个：出错时 Redis 是偏高还是偏低？**

| Redis 状态 | 后果 | 性质 |
|---|---|---|
| 偏低（比 MySQL 少） | 少卖几个名额 | 只是浪费，**安全** |
| 偏高（比 MySQL 多） | 能抢到不存在的名额 | **直接破坏正确性** |

所以正确顺序是 **先 MySQL 提交，再还 Redis**：

```java
public SeckillResponse cancel(Long courseId) {          // ← 注意：没有 @Transactional
    SeckillOrder cancelled = transactionTemplate.execute(status -> {
        // 改订单状态 + 归还 MySQL 库存，事务在这里提交完
    });
    try {
        stockCacheService.incrementIfPresent(courseId);  // 提交之后才动 Redis
    } catch (Exception e) {
        // 不抛：MySQL 已提交，抛出去会让前端以为失败
        log.error("退课后 Redis 归还失败（Redis 偏低，不会超卖），需对账 ...", ...);
    }
    return ...;
}
```

三个关键点，每一个都对应一个曾经存在的 bug：

1. **`cancel` 方法上不能有 `@Transactional`**。有的话 `transactionTemplate.execute` 会以 `REQUIRED` 传播加入外层事务，返回时**并没有提交**，接着 `incrementIfPresent` 执行，然后方法返回才提交。如果提交失败，Redis 已经 +1 而 MySQL 回滚 → **Redis 偏高 → 超卖**。这条是结构性保证，不是时序运气。
2. **Redis 归还失败绝不能抛出**。MySQL 已提交，抛出去会让用户以为退课失败，但他再点一次只会得到 409，更困惑。Redis 偏低是安全方向，交给对账修。
3. **用 `incrementIfPresent` 而不是 `increment`**。`INCR` 在 key 不存在时会**创建它并设为 1**。如果这时 Redis 未预热，退一次课就把 `seckill:stock:88` 写成 `1`，明明有 100 个名额系统却认为只剩 1 个。

## 8. 过程中发现并修掉的问题

### 8.1 `cancel` 上残留 `@Transactional`（结构性隐患）

写了 `TransactionTemplate` 却忘了删方法上的 `@Transactional`，导致外层事务把内层包住，提交时机推迟到 `incrementIfPresent` 之后。**功能测试全过**（因为 MySQL 一直提交成功），只有结构分析才看得出来。

### 8.2 退课返回 `status: 1`

```java
return new SeckillResponse(cancelled.getOrderNo(), cancelled.getStatus());
```

`cancelled` 是事务开始前读出的 Java 对象，`updateStatusIfMatch` 直接发 SQL，**不会回写这个对象**。库里已经是 `status=3`，返回给前端却是 `status=1`。前端会当成"退课失败/没变化"。

改成常量 `SeckillOrder.STATUS_CANCELLED`。

> 同类坑在 `seckill` 的 R5 分支不存在，因为那里是 `exist.setStatus(...)` 先改对象再 `updateById`，对象和库一致。

### 8.3 `application.yaml` 里的 Redis 连接池是死配置

```yaml
lettuce:
  pool:
    max-active: 50   # ← commons-pool2 不在 classpath，这段配置从来不起作用
```

`commons-pool2` 未引入时，Lettuce 用的是单连接复用模式，`pool` 配置被静默忽略。已删掉，避免误以为「配了连接池」。

### 8.4 Memurai 不会自启

每次开工必须先确认 `ping` 返回 PONG。已写进 `reconcile.ps1` 的前置检查，Redis 连不上时直接报错并给出启动命令。

## 9. 已知局限

诚实列出这一版**没解决**的问题：

1. **P95 未达预期**（255 ms vs 预期 < 200 ms）。瓶颈已转移到 MySQL 单行串行更新，这是 v3 的靶子。
2. **Redis 故障时系统不可用**。当前策略是快失败（返回 500），不做降级。真要做降级需要一个"Redis 挂了就走数据库"的 fallback，但那会让代码复杂度翻倍，且降级路径本身也要压测——本阶段不做。
3. **预热的窄窗口**。按需预热时，A 拿到 `-1` 正在 `preheat`（读到 100），B 已经扣到 99，A 的 `SET 100` 覆盖 → 多卖一个。本阶段不解决，靠开局预热规避。
4. **`incrementIfPresent` 的 `hasKey` + `increment` 非原子**。极小窗口内 key 被删（只有运维接口 `clear` 会这么干），`INCR` 会建成 1。彻底解决要第二个 Lua 脚本。
5. **进程崩溃窗口**。Redis 扣了、MySQL 还没提交时进程被杀，Redis 会永久少一个名额。方向安全（偏低），但需要定时对账修。
6. **单机单 Redis**，无持久化（`appendonly=no`）。Redis 重启后所有 key 消失，必须重新预热。
7. **`Com_update` 是全库计数器**，本次测量期间已确认无其他写入，但多实例部署时不适用。

| ② | `stock + sold` | `= capacity`，`conservation_gap = 0` |
| ③ | Redis 余量 vs DB `stock` | 相等，`consistent = true` |
| ④ | `Com_update` 增量 | **≈ 100**（若为 300，门禁没生效） |

---

## 11. 结论

### 11.1 一句话

**v2 用 `Com_update` 增量 300 → 100 的硬证据，证明了 Redis + Lua 门禁真的把 2/3 的无效流量挡在了数据库之外；正确性（成功单、超卖、守恒、Redis 对账）四道全部守住；瓶颈按预期从"数据库挨打太多"转移到"同一行串行更新"，P95 因此只降到 255 ms 而非预期的 200 ms 以下。**

### 11.2 这一版真正学到的东西

1. **验证机制，不要只验证结果**。P95 变快可以是运气，`Com_update` 增量骗不了人。凡是"优化"，都要找到那个**只有该优化生效才会变**的指标。
2. **优化的收益会被下一个瓶颈吃掉**。挡住 200 个请求后，剩下的 100 个仍在行锁上排队。每次优化只挪动瓶颈位置。
3. **两个存储的一致性，方向比方法重要**。Redis 偏高 vs 偏低不是对称的：一个破坏正确性，一个只是浪费。所有不确定性都要往"偏低"倒。
4. **功能测试通过 ≠ 结构正确**。`cancel` 上多一个 `@Transactional`，7 项测试全过，但存在一个只在 MySQL 提交失败时才出现的超卖窗口。

### 11.3 面试话术

**Q：你这个秒杀怎么保证不超卖的？**

> 分两层。第一层是 Redis 门禁：库存预热到 Redis，用 Lua 脚本把"判断 + 扣减"做成一个原子操作，`if tonumber(redis.call('GET', KEYS[1])) <= 0 then return -2 end; redis.call('DECRBY', KEYS[1], ARGV[1])`。这一层挡掉 2/3 的无效请求，我用 `Com_update` 增量证明过——从 300 降到 100。
> 第二层是 MySQL 兜底：条件更新 `UPDATE ... SET stock = stock - 1 WHERE stock > 0`，看 `affected rows` 是不是 1。两层都过了才建订单，订单表还有 `(student_id, course_id)` 唯一索引防重复。

**Q：Redis 和 MySQL 数据不一致怎么办？**

> 先分方向。Redis 偏高会超卖，必须杜绝；偏低只是浪费名额，可以容忍。所以所有时序都设计成"不确定时往偏低倒"：扣减时 Redis 先、MySQL 后；归还时 MySQL 先提交、Redis 后。另外有对账接口和脚本，定期比对两边的库存并输出差值。

**Q：加了 Redis 之后 P95 降了多少？**

> 从 339 ms 降到 255 ms，降了 25%，没到我预期的 200 ms 以下。原因是瓶颈转移了——门禁挡住 200 个请求后，剩下 100 个成功请求仍然串行在同一条 MySQL 行锁上，100 次 × 2 ms ≈ 200 ms，这就是新的下限。再往下优化要换成异步，但那会牺牲"响应即结果"的语义。

**Q：这一版还有什么问题？**

> 三个。一是 P95 受限于单行锁的串行更新，这是 v3 要解决的；二是 Redis 挂了系统直接不可用，我做的是快失败而不是降级；三是预热有窄窗口，并发预热可能多卖一个，目前靠开局预热规避。
