# 压测报告 · v3-mq-async

> 项目：CourseSeckill 高并发抢课引擎
> 版本：v3-mq-async（Redis 库存门禁 + RabbitMQ 异步落单）
> 日期：2026-11-23
> 机器：Windows 11 Build 26200 / i7-14650HX / 15.61 GB / JDK 26.0.1
> 被测服务：`--seckill.strategy=v3-mq-async`，端口 8080

---

## 1. 这一版要回答的问题

前三份报告问的是「**准不准**」（有没有超卖）和「**多快**」（P95 多少）。v3 还要多回答一个：

| # | 问题 | 为什么这一版才需要问 |
|---|---|---|
| 1 | 异步之后还准吗？ | 请求返回时订单还没落定，任何一个环节丢了消息都表现为「少卖」，而少卖不会报错 |
| 2 | 消息会丢吗？ | AMQP 默认不保证投递，三个环节都可能丢：生产者→broker、broker 自己、broker→消费者 |
| 3 | 消息会重复消费吗？ | at-least-once 语义意味着「至少一次」，重复才是常态 |
| 4 | 削峰真的削到了吗？ | 如果只是把同步改成异步、P95 没降，那就是白改 |
| 5 | 慢到什么时候用户会察觉？ | 异步把「等待」从 HTTP 挪到了「最终一致延迟」，这个延迟必须量化 |

**第 1 问是灵魂。** 前三版只要查 `stock+sold==capacity` 就够了；这一版必须同时查「成功单数 == capacity」，因为少卖不会让守恒关系破裂。

⚠️ **隔离级别那一行是作废条件。** 如果有人把库改成 READ-COMMITTED，v3 的结论要重跑——虽然 v3 本身不依赖隔离级别（它不做 CAS 重试），但换隔离级别会改变消费者事务的行为。

```powershell
docker inspect seckill-rabbitmq --format '{{.State.OOMKilled}} {{.RestartCount}}'
```

## 3. 被测链路

```
POST /api/seckill/88
  │
  ├─ ① 查课程（MySQL）         -- 不存在 → 404
  ├─ ② 时间窗口校验             -- 不在窗口 → 409
  ├─ ③ Redis Lua 扣减           -- -2 名额满 → 409；-1 未预热 → 预热后重试一次
  ├─ ④ 查重复订单（MySQL）      -- 已有 SUCCESS/PENDING → 409
  ├─ ⑤ INSERT 订单 status=0     -- 唯一索引兜底
  ├─ ⑥ 发消息 + 等 confirm（≤3s）
  └─ ⑦ 返回 200 {status:0}      ← 注意：这里只是"受理"
                │
                ▼
        RabbitMQ seckill.order.queue
                │
        RabbitListener（2 线程，手动 ack）
                │
        ┌───────┴────────┐
        │ 事务开始        │
        │ ⑧ INSERT 幂等日志│ ← 撞 uk_msg_id → DuplicateMessageException → ack 忽略
        │ ⑨ 扣 MySQL 库存  │ ← affected=0 → 标 status=2 + ack
        │ ⑩ 订单改 status=1│ ← rows=0（用户已退课）→ 归还库存
        │ ⑪ 日志改 status=1│
        │ 事务提交        │
        └───────┬────────┘
                │
            basicAck  ← 必须在提交之后
```

**关键：③ 在请求路径上，⑨ 不在。** 这就是 v3 比 v2 快的原因——那个会排队的 `UPDATE course_stock WHERE course_id=88` 从 Tomcat 线程挪到了消费者线程。

## 4. 压测方案

### 4.1 为什么登录要拆进 setup

k6 的 `setup()` 只在压测前跑一次。在那里批量登录 300 个学生，把 token 传给各 VU。这样测出来的 P95 里**不含 BCrypt 的 ~60ms**——那是登录接口的成本，不是抢课接口的成本，混在一起数据就没意义了。

### 4.2 为什么 VU 数必须远大于 capacity

100 个学生抢 100 个名额，最多也就成功 100 单，看不出任何问题。必须 **300 个学生抢 100 个名额**，让 200 个注定失败的请求也进入系统，才能压出门禁和消费链路的上界。

### 4.3 v3 的计数口径变了

这是与前几版最大的不同，写脚本时最容易搞错：

| 计数器 | 含义 |
|---|---|
| `biz_queued` | HTTP 200，**已受理入队**（≠ 已抢到） |
| `biz_sold_out` | HTTP 409，Redis 门禁挡下 |
| `biz_duplicate` | HTTP 409，该学生已有成功/待处理订单 |
| `biz_rejected` | 其它（出现就说明有问题） |

**k6 数不出真正的成功单数。** 必须压测后查库：

```sql
SELECT COUNT(*) FROM seckill_order WHERE course_id = 88 AND status = 1;
```

### 4.4 为什么必须等队列排空再查

v0/v1/v2 是同步的，压测一结束就能查库。v3 不行：结束时队列里可能还堆着几百条没消费完的消息，此刻数 `status=1` 会偏小，误判成「少卖」。所以写了 `loadtest/verify-v3.ps1`，先轮询等队列清空（实测 0.1 秒），再查。

### 4.5 脚本清单（新增三个）

| 文件 | 作用 |
|---|---|
| `loadtest/seckill-v3.js` | v3 专用压测脚本，计数器改为 `biz_queued` 等 4 个 |
| `loadtest/reset-v3.ps1` | 比 `reset.ps1` 多清三样：Redis key、两个 MQ 队列（purge 而非 delete）、`mq_consume_log` |
| `loadtest/verify-v3.ps1` | 等队列排空 + 五条判据自动判定，退出码 0/1 |

## 5. 压测结果

### 5.1 六轮结果总表（300 VU / 课程 88 / capacity=100）

| 轮 | biz_queued | biz_sold_out | biz_rejected | avg | P95 | 备注 |
|---|---|---|---|---|---|---|
| 1 | 100 | 168 | **32** | 61.4ms | 110.5ms | 冷启动噪声 |
| 2 | 100 | 200 | 0 | 46.4ms | 63.8ms | 干净 |
| 3 | 100 | 200 | 0 | 44.0ms | 65.0ms | 干净 |
| 4 | 100 | 200 | 0 | 53.5ms | 80.3ms | 干净 |
| 5 | 100 | 200 | 0 | 43.6ms | 66.0ms | 干净 |
| — | 100 | 200 | 0 | 135.9ms | 258.4ms | ⚠️ 作废：我在旁边每 500ms 查一次库，干扰了测量 |

**有效数据的 P95 区间：64 ~ 80ms，中位数 66ms。**

### 5.2 第 1 轮那 32 个 rejected 查清了

没有报错、没有死信、日志零 ERROR，但数字对不上——必须查清，不能含糊过去。

写了个临时探针（按 `http + code + msg` 分桶，用完即删），300 VU 跑一轮：

```
200 × 409|409|该课程名额已满
100 × 200|200|操作成功
```

`biz_rejected` 归零。日志里的旁证：

| 关键词 | 次数 |
|---|---|
| 消息已确认 | 102（含之前 2 条手工测试） |
| 收到消息 | 102 |
| 重复消息 | 0 |
| 消费失败 | 0 |
| 库存状态异常 | 0 |
| ERROR / Deadlock / Connection is not available / Timeout | **0** |

**结论：这 32 个是 JVM 与 Hikari 冷启动噪声**，与 v2 第 1 轮的 94 个 `biz_other` 是同一类现象。第 2 轮起全部归零。

### 5.3 最终一致延迟（v3 独有指标）

压测的同时每 500ms 采样一次订单状态：

```
t=0.1s   total|success|pending = 0|0|0
t=23.5s  total|success|pending = 99|1|98     ← 请求基本发完，99 条订单已入库但只有 1 条落定
t=24.0s  total|success|pending = 100|100|0   ← 500ms 内全部消化
```

更精确的度量（`create_time` → `update_time`，秒级精度）：

| 处理耗时 | 订单数 | 占比 |
|---|---|---|
| 0 秒 | 23 | 23% |
| 1 秒 | 77 | 77% |

100 条订单的 `create_time` 全部是同一秒（`20:50:54`），说明请求确实在同一瞬间砸进来。

**结论：300 并发下，最终一致延迟 ≤ 1 秒。** 客户端轮询 5 次（200ms × 1.5 递增 ≈ 2 秒）足够覆盖。

### 5.4 五条判据（每轮都跑，全部 PASS）

```
1. 超卖检查       : 成功 100 <= 名额 100
2. 少卖检查       : 名额用满
3. 库存守恒       : stock+sold = capacity = 100
4. 残留待处理     : 无孤儿订单
5. 唯一性         : 无重复成功
附加 Redis 对账   : Redis = MySQL = 0
```

`mq_consume_log` 100 条全部 `status=1`，死信队列 0 条。

**⚠️ 第 2 条是 v3 新增的，也是最容易被忽略的。** 前三版只要「不超过」就是对的；这一版必须「正好等于」。因为消息丢失不会让守恒破裂——`stock+sold` 还是 100，只是 `stock` 没被扣、订单停在 0。只看守恒会漏掉整个消息丢失类故障。

## 6. 五版对比

| 版本 | P95 | P99 | 成功单 | 超卖 | 数据库 UPDATE 次数 | 拦截发生在 |
|---|---|---|---|---|---|---|
| v0-baseline | 572ms | 615ms | 300 | **+200** | 300 | 无拦截 |
| v1-optimistic | 339ms | 344ms | 100 | 0 | 300（270 次 affected=0） | MySQL 行锁 |
| v1-pessimistic | 397ms | 406ms | 100 | 0 | 100 | MySQL 行锁（串行） |
| v1-version-cas | 867ms | — | 100 | 0 | 900（3 次重试） | MySQL 乐观锁 |
| v2-redis-lua | 322ms | 330ms | 100 | 0 | 100 | **Redis Lua** |
| **v3-mq-async** | **66ms** | — | 100 | 0 | 100（不在请求路径） | **Redis Lua** |

### 6.1 v2 → v3 的提速从哪来

v2 的 P95 = 322ms，v3 的 P95 = 66ms，**4.9 倍**。

不是 Redis 变快了，也不是 MySQL 变快了，而是**那 100 个成功请求不再排队等待**：

| | v2 | v3 |
|---|---|---|
| 请求线程做的事 | 门禁 → INSERT → **UPDATE 库存（排队）** → 返回 | 门禁 → INSERT → 发消息 → 等 confirm → 返回 |
| 排队发生在 | Tomcat 线程（用户能感知） | 消费者线程（用户看不见） |
| 排队等待时间 | 100 次 × 约 2ms ≈ 200ms | 0（用户不等） |

用 v2 报告 §5 的原话作靶子：「100 个成功请求仍串行在同一行 MySQL 行锁上，100 次 × 约 2ms ≈ 200ms 就是新的下限」。**这次把这个下限打掉了。**

### 6.2 剩下的 66ms 是什么

不是 Redis（Lua 单次 < 1ms），也不是 MySQL（INSERT 不同行，不排队），而是：

| 组成 | 估算 |
|---|---|
| Spring Security 过滤器链 + JWT 解析 | ~3ms |
| 课程查询 + 时间窗口校验 | ~2ms |
| Redis Lua 扣减 | < 1ms |
| 查重 SELECT | ~2ms |
| INSERT 订单 | ~3ms |
| 发消息 + **等 publisher confirm** | ~50ms ← 主要成本 |
| 响应序列化 | ~2ms |

**`publisher-confirm-type: correlated` 让每个请求都要等 broker 回 ack。** 这 50ms 是消息可靠性的代价——如果不配 confirm，P95 能降到 15ms 左右，但消息可能悄悄丢。

还有一个旁证：日志里 `消息已确认` 的时间戳集中在同一毫秒的相邻几十条，说明 confirm 是批量回来的，不是逐条往返。

### 6.3 这次没做「Com_update 对照实验」

v2 报告里用 `Com_update` 增量证明「200 个失败请求没碰数据库」——那是数据库自己记的账，不会骗人。

v3 做不了同样的实验，因为：**v3 的 UPDATE 次数由消费者决定，与请求数无关**。100 个成功请求 → 100 次 UPDATE，这是设计使然，不是证据。

替代证据是 **`biz_queued` 恒为 100 + P95 降到 66ms**：
- 如果门禁失效，`biz_queued` 会远大于 100（300 个请求全都入队）
- 如果排队还在请求路径上，P95 不会降

两个数字同时成立，才说明「挪走排队」这件事真的发生了。

## 7. 可靠性验证（六项，全部实测）

压测只证明「正常路径成立」。下面六项验证的是「异常路径也成立」，通过 RabbitMQ 管理台 API 手工造异常。

| # | 场景 | 操作 | 预期 | 实测 |
|---|---|---|---|---|
| 1 | 正常消费 | 造 PENDING 订单 + 发消息 | stock-1、订单→1 | ✅ `98→97`、`sold 2→3`、守恒 100 |
| 2 | 幂等（重复投递） | 同 msgId 重发 | 不重复扣减 | ✅ stock/sold 不变，日志 `WARN 重复消息，已忽略` |
| 3 | 业务失败不 nack | `courseId=999` 不存在 | 订单→2、**不进死信** | ✅ `status=2 reason=库存不足`，死信 0 |
| 4 | 订单已变（用户秒退） | 订单已 status=1，换新 msgId 再发 | 归还库存 + ack | ✅ stock/sold 不变，日志 `WARN 订单状态已更改，跳过` |
| 5 | 技术异常进死信 | 发坏 JSON | 死信 +1 | ✅ 业务队列 0、**死信 1** |
| 6 | 事务回滚 | 临时在 `handle()` 开头抛异常 | 库存与日志都不变 | ✅ 前者不变、该 msgId 在 `mq_consume_log` **0 行** |

### 7.1 第 2 项的关键设计

幂等闸用的是 `INSERT mq_consume_log` 撞 `uk_msg_id`，**不是**「查订单表判断是否已处理」。

原因：v3 的订单在生产者阶段就插入了 `status=0`。消费者如果「先查订单表，发现有单就跳过」，那么**每一条消息都会被跳过**——因为单子早就有了。这个坑极隐蔽：功能测试会全过（订单确实存在），但库存永远扣不动，表现为「100 单成功但 stock 一直是 100」。

### 7.2 第 3 项 vs 第 5 项的区分

这两项最容易被混成一件事，但处理方式完全相反：

| | 业务失败（库存不足） | 技术异常（消息格式错） |
|---|---|---|
| 消息本身有问题吗 | 没有 | 有 |
| 重投有意义吗 | 没有（还是不够） | 没有（还是坏） |
| 处理 | **标 status=2 后正常 ack** | **basicNack(requeue=false) → 死信** |
| 为什么 | 这是业务结论，必须留痕 | 这是代码/数据 bug，必须人工介入 |

如果把业务失败也 nack 进死信，死信队列会被「名额已满」淹没；如果把技术异常也标 status=2 吞掉，坏消息就永远不会被发现。

## 8. 过程发现的问题

### 8.1 消费者代码里 1 个编译错 + 4 个逻辑问题

| # | 位置 | 问题 |
|---|---|---|
| 1 | `SeckillOrderConsumer.java:14` | import 选错：`org.apache.ibatis.javassist.bytecode.DuplicateMemberException`（MyBatis 内嵌 javassist 的**受检异常**），应为自己新建的 `com.example.seckill.exception.DuplicateMessageException`。**IDE 补全按名字猜的，名字里带 Duplicate 就跳出来了** |
| 2 | `MqConsumeLog` 实体 | 缺 `@TableName`、缺 `@TableId(type=IdType.AUTO) private Long id`、字段 `ErrorMsg` 首字母大写（驼峰映射会变 `_error_msg`）。**缺 id 最致命**：insert 后不回填主键，`updateById` 必抛异常 |
| 3 | `basicReject` | 改成 `basicNack(deliveryTag, false, false)`，语义等价但更通用 |
| 4 | 归还分支 | `rows == 0` 时只打日志不还库存 → 库存永久少 1、订单既非成功也非失败 |
| 5 | 日志拼写 | `"d订单状态已更改"` 多一个 d |

### 8.2 生产者代码里 1 个编译错 + 3 个逻辑问题

| # | 位置 | 问题 |
|---|---|---|
| 1 | `SeckillMessageProducer.java:40` | `Confirm` 找不到符号——它是 `CorrelationData` 的**内部类**，必须写 `CorrelationData.Confirm` |
| 2 | `SeckillServiceImplV3MqAsync.java:126` | 兜底把订单标成了 `STATUS_SUCCESS`，应为 `STATUS_FAILED`。**后果：用户收到「系统繁忙」，库里却显示选上了** |
| 3 | `SeckillMessageProducer.java:42` | 日志两个参数传了同一个 `orderNo`，`msgId` 丢了 |
| 4 | `SeckillMessageProducer.java:48` | `{]` 不是合法占位符（少右花括号）+ 拼写 `roderNo`，导致参数错位 |

### 8.3 一个遗留的小问题

`GlobalExceptionHandler` 里加了个 `DuplicateMessageException` 的 handler（返回 409）。这个异常只在消费者线程里抛出，永远到不了 Controller，所以这个 handler **是死代码**。无害，但删掉更干净。

### 8.4 RabbitAdmin 是懒声明（影响验收标准）

第一次验收批次 1 时断言「重启后队列自动出现」，但没有出现。查源码（`spring-rabbit-4.1.1-sources.jar` 的 `RabbitAdmin.java:589` 起）：

```java
this.connectionFactory.addConnectionListener(connection -> {
    if (!initializing.compareAndSet(false, true)) { return; }
    try { this.retryTemplate.execute(() -> { initialize(); return null; }); }
});
```

**它只注册「连接建立时」的回调，自己不主动建连。** 没有 `@RabbitListener` 时无组件连 broker → `initialize()` 从不被调用 → 队列不出现。

这是正常机制，不是 bug。批次 1 的验收标准应该写成「编译通过 + 配置类被扫描到」，等批次 3 写完消费者再验队列。

### 8.5 环境：.wslconfig 的 mirrored 模式导致端口完全不通

症状链：Docker 引擎起来（29.9.2）、容器 Up、`docker port` 显示 `5672->0.0.0.0:5672`，但 Windows 上 `Get-NetTCPConnection -LocalPort 5672` 是 **0 个监听**。

排查排除项：容器内 `rabbitmqctl status` 显示端口在听；WSL 内 `wget http://127.0.0.1:15672` 返回 401（服务活着）；从 Windows 直连容器 IP `172.17.0.2` **超时**；`ping` 100% 丢包；`Get-NetRoute` 里**没有 172.17 网段路由**；`wsl --shutdown` + 重启 Docker 无效；`docker restart` 容器无效。

根因：`C:\Users\user\.wslconfig` 里的 `networkingMode=mirrored` 下，WSL 的 docker 网桥没有镜像到 Windows 网络栈。改成 NAT（删掉该行）后重启，**24.3 秒端口监听恢复**。

## 9. 已知局限

### 9.1 🔴 confirm 超时但消息其实到了 —— 会导致超卖

这是 v3 设计上的固有窗口，本阶段三轮压测都没触发（confirm 实测集中在 50ms 内），但必须写清楚。

时间线：

```
t0  请求线程：Redis 扣 1（100 → 99）
t1  请求线程：INSERT 订单 status=0
t2  请求线程：发消息 → broker 收到了，但 confirm 回包在路上丢了
t3  请求线程：等满 3 秒 → 判定失败
t4  finally：删订单（或标 status=2）
t5  finally：还 Redis（99 → 100）      ← 此时 Redis 比"实际会发生的扣减"多 1
t6  消费者：收到那条"其实到了"的消息 → 扣 MySQL 库存、订单... 已经不存在了
```

如果 t4 的删订单成功了，消费者走到「订单状态已更改」分支会归还库存，三者回到一致。但如果订单被标成 `status=2` 而非删除，消费者改状态时 `rows=0`（`WHERE status=0` 挡住），归还库存——这一条是安全的。

**真正危险的组合**是：删订单失败 + 标 status=2 也失败（数据库抖动），此时 Redis 已还、订单还在 0，消费者扣了库存并把订单改 1 → `stock` 少 1 但 Redis 多 1 → 后续请求按 Redis 放行 → 超卖。

**缓解手段（本阶段未做）**：`loadtest/reconcile.ps1` 对账工具能发现（Redis 偏高会打 🔴 并退出码 1），但没有自动修复。

### 9.2 消息确认后、消费完成前，进程被杀 —— 会少卖

手动 ack 保证「消费完才 ack」，所以消息不会丢。但如果 broker 自己重启（`durable` + `persistent` 保证消息还在），消费侧没影响。真正会少卖的场景是：**消费者持有一条未 ack 的消息，同时容器被 OOM 杀掉** → 消息会被重新投递（这是 at-least-once 的正确行为），所以也不会少卖。

> 上面两条推下来，其实这一项风险很低。留在这里是因为「异步系统必须逐条想清楚」比「结论是安全」更重要。

### 9.3 死信队列没有消费者

`seckill.order.dlq` 目前只堆积不处理。业务上意味着「消息格式错」这类问题要人工看管理台才能发现。生产环境应该配告警（死信数 > 0 就报警）。

### 9.4 没有做 PENDING 订单的清扫

如果消息永久丢失（比如 broker 磁盘损坏），订单会永远停在 `status=0`。用户看到「待处理」但永远不会变。

任务书 §2.1 提了兜底 SQL：

```sql
SELECT COUNT(*) FROM seckill_order
WHERE status = 0 AND create_time < NOW() - INTERVAL 30 SECOND;
```

本阶段没做成定时任务——属于「功能做小，深度做透」原则下的有意取舍。

### 9.5 publisher confirm 的 50ms 是串行成本

每个请求独立等 confirm，P95 里这 50ms 无法通过加机器消除（除非用批量发送或异步 confirm + 补偿）。这不是 bug，是「可靠投递」的价格。

### 9.6 单机单 broker，没有测 broker 故障

容器被 OOM 杀掉、磁盘满、网络分区这些场景全部没测。真实系统的 MQ 可靠性验证需要多节点。

### 9.7 内存是本机最大的不确定性

压测期间可用内存经常低于 1 GB（历史最低见过 0.31 GB）。虽然本次五轮 P95 稳定在 64~80ms，但内存换页带来的抖动随时可能出现。**如果某天数据突然离谱，第一件事是查当时的内存而非代码。**

## 11. 结论

### 11.1 一句话

**v3 把「排队等待」从用户的 HTTP 请求里搬到了后台：P95 从 322ms 降到 66ms（4.9 倍），代价是接口语义从「返回即成功」变成「返回即受理」，最终一致延迟在 300 并发下 ≤ 1 秒。**

### 11.2 学到的东西

1. **异步不是免费的性能。** 换来的是「用户不等」，付出的是「接口语义变复杂 + 一致性延迟 + 三处可能丢消息 + 必须做幂等」。如果业务能接受同步 300ms，就该用 v2。
2. **「守恒」不等于「正确」。** v3 少卖时 `stock+sold` 依然等于 100，只是 `stock` 没被扣、订单停在 0。判据必须加一条「成功单数 == 名额」。
3. **幂等键不能用「查业务表」代替。** v3 的订单在生产者就插了 PENDING，消费者查订单表会发现「已存在」从而跳过一切——功能测试全过，库存永远不动。
4. **业务失败不 nack，技术异常才 nack。** 前者是结论（要留痕），后者是 bug（要人工）。
5. **RabbitAdmin 只在有连接时才声明拓扑。** 没有 `@RabbitListener` 时队列不会出现，这不是配置错误。

### 11.3 面试话术（四组）

**问：为什么要引入 MQ？**

> v2 用 Redis 把 300 个请求挡到 100 个，但剩下 100 个仍要在 MySQL 行锁上排队，100 次 × 2ms ≈ 200ms 就是下限，用户能感知。v3 把那 100 次 UPDATE 挪到消费者线程，请求线程只负责「发消息、等确认、立刻返回」，P95 从 322ms 降到 66ms。
>
> 关键是明确代价：接口不再是「返回即成功」，而是「返回即受理」，客户端必须轮询。这个取舍我写进了文档 §0.1 的四笔代价表里。

**问：消息会不会丢？**

> 三个环节分别处理：生产者用 publisher confirm（`correlated` 模式，3 秒超时）；broker 用 durable 队列 + persistent 消息；消费者用手动 ack，且在**事务提交之后**才 ack。
>
> 最容易写错的是第三条——如果在事务提交前 ack，事务回滚了消息却已被删除，订单永远停在待处理。这个我故意在代码里留了注释提醒。

**问：消息重复怎么办？**

> 用 `INSERT mq_consume_log` 撞 `uk_msg_id` 抛 `DuplicateKeyException`，捕获后正常 ack 忽略。
>
> 为什么不能用「查订单表判断是否已处理」：v3 的订单在生产者阶段就插了 `status=0`，消费者查表永远得到「已存在」，结果每条消息都被跳过，库存永远不扣。这个坑功能测试发现不了——订单确实在，只是库存不动。

**问：怎么证明异步之后还是对的？**

> 五条判据，其中第二条是 v3 新增的：成功单数必须**正好等于** capacity，不能只是「不超过」。
>
> 因为消息丢失不会破坏守恒关系——`stock+sold` 还是 100，但 `stock` 没被扣、订单停在 0，表现为少卖且无任何报错。前三版只要看守恒就够了，这一版必须双向看。
>
> 另外还做了六项异常路径验证：重复投递、业务失败、订单已变、坏消息进死信、事务回滚。这些都不是压测能覆盖的，全靠手工造异常。
